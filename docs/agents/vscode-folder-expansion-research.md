# VS Code folder expansion source research

Inspected upstream `microsoft/vscode` HEAD `c198526d8e64ba6f9944e9f7bcc079ed1f6d7fcc` on 2026-10-31. These are source observations, not measured latency results or an implementation proposal.

- **Lazy, cached directory contents.** `ExplorerItem.fetchChildren` resolves an unresolved directory, merges its contents into the existing model and marks it resolved. Later calls reuse those children until invalidation; `forgetChildren` clears children and resets the resolved flag. Only Modified sorting requests child metadata. The resolve option also follows chains of single-child directories, so this is not strictly one directory read per click. [Explorer model](https://github.com/microsoft/vscode/blob/c198526d8e64ba6f9944e9f7bcc079ed1f6d7fcc/src/vs/workbench/contrib/files/common/explorerModel.ts#L312-L338), [invalidation](https://github.com/microsoft/vscode/blob/c198526d8e64ba6f9944e9f7bcc079ed1f6d7fcc/src/vs/workbench/contrib/files/common/explorerModel.ts#L408-L413).

- **Complete listing, rather than child-by-child delivery on this path.** `FileService` awaits `provider.readdir`, resolves the entry array with `Promises.settled`, then assigns the completed children array. It uses the entry type directly unless metadata was requested; it does not always stat every child. This code supports recursive resolution for requested targets and single-child chains. [File service](https://github.com/microsoft/vscode/blob/c198526d8e64ba6f9944e9f7bcc079ed1f6d7fcc/src/vs/platform/files/common/fileService.ts#L207-L297).

- **Sort before publishing children.** The Explorer supplies `FileSorter` to a compressible asynchronous tree. The tree awaits the data source result and sorts the complete iterable before setting its children; refresh then renders. Thus the inspected expansion path does not progressively append arrival-order chunks. [Explorer tree setup](https://github.com/microsoft/vscode/blob/c198526d8e64ba6f9944e9f7bcc079ed1f6d7fcc/src/vs/workbench/contrib/files/browser/views/explorerView.ts#L528-L552), [await and render](https://github.com/microsoft/vscode/blob/c198526d8e64ba6f9944e9f7bcc079ed1f6d7fcc/src/vs/base/browser/ui/tree/asyncDataTree.ts#L1084-L1094), [children processing](https://github.com/microsoft/vscode/blob/c198526d8e64ba6f9944e9f7bcc079ed1f6d7fcc/src/vs/base/browser/ui/tree/asyncDataTree.ts#L1185-L1200), [sorting](https://github.com/microsoft/vscode/blob/c198526d8e64ba6f9944e9f7bcc079ed1f6d7fcc/src/vs/base/browser/ui/tree/asyncDataTree.ts#L1371-L1377).

- **Deduplicate work and preserve node identity.** The asynchronous tree shares an in-flight child request for a node. It reuses matching child nodes by stable ID, including their collapsed state. This is separate from the Explorer model's resolved-directory cache. [Request deduplication](https://github.com/microsoft/vscode/blob/c198526d8e64ba6f9944e9f7bcc079ed1f6d7fcc/src/vs/base/browser/ui/tree/asyncDataTree.ts#L1185-L1200), [identity reuse](https://github.com/microsoft/vscode/blob/c198526d8e64ba6f9944e9f7bcc079ed1f6d7fcc/src/vs/base/browser/ui/tree/asyncDataTree.ts#L1224-L1263).

- **Loading indicators have a delay; data does not wait for that delay.** The tree marks an outstanding asynchronous request slow after 800 ms and cancels that timer on completion. Its renderer substitutes a loading twistie while slow. Explorer-wide progress separately uses 800 ms after layout restoration or 1500 ms during restoration. [Slow-state timer](https://github.com/microsoft/vscode/blob/c198526d8e64ba6f9944e9f7bcc079ed1f6d7fcc/src/vs/base/browser/ui/tree/asyncDataTree.ts#L1141-L1182), [twistie renderer](https://github.com/microsoft/vscode/blob/c198526d8e64ba6f9944e9f7bcc079ed1f6d7fcc/src/vs/base/browser/ui/tree/asyncDataTree.ts#L118-L126), [Explorer progress](https://github.com/microsoft/vscode/blob/c198526d8e64ba6f9944e9f7bcc079ed1f6d7fcc/src/vs/workbench/contrib/files/browser/views/explorerViewer.ts#L117-L166).

- **Virtualized rendering is independent of listing completeness.** The list computes a visible range from scroll position and height, inserts rows entering that range and removes rows leaving it; row templates are allocated/released through a cache. A selection can widen the render range. A complete child model therefore does not imply a DOM row for every child. [Range rendering](https://github.com/microsoft/vscode/blob/c198526d8e64ba6f9944e9f7bcc079ed1f6d7fcc/src/vs/base/browser/ui/list/listView.ts#L963-L1015), [row allocation](https://github.com/microsoft/vscode/blob/c198526d8e64ba6f9944e9f7bcc079ed1f6d7fcc/src/vs/base/browser/ui/list/listView.ts#L1034-L1048), [row release](https://github.com/microsoft/vscode/blob/c198526d8e64ba6f9944e9f7bcc079ed1f6d7fcc/src/vs/base/browser/ui/list/listView.ts#L1150-L1165), [render range](https://github.com/microsoft/vscode/blob/c198526d8e64ba6f9944e9f7bcc079ed1f6d7fcc/src/vs/base/browser/ui/list/listView.ts#L1630-L1649).

No application changes or performance benchmarks were made. Provider-specific filesystem costs, end-to-end IPC timings and perceived expansion latency remain unmeasured.

## escode comparison and recommendation

At local commit `d12d8466f2d71201f830c3d81921dd85c8ad478c`, `apps/desktop/host/project.ts` (`files`/`filteredFiles`) sorts the complete listing and completes bulk Git ignore classification before returning. `apps/desktop/src/files.tsx` (`load`) publishes that listing in one cache update, and `listing` maps all immediate children together. There is no stagger animation in the inspected tree styles. This does not reproduce or explain the reported visual symptom.

The reachable-expanded-directory effect loads remembered descendants after their parents become available, publishing each directory separately. Watch readiness also triggers revalidation. These are candidates for staged subtree changes, requiring runtime evidence. Unlike VS Code, the recursive JSX mounts every expanded row. Cached expansion already retains its old listing while revalidating; retain that behavior.

Recommended sequence:

1. Record animation-frame row counts and listing/React commit timings for a cold folder, cached reopening, remembered expanded descendants and a large flat directory. Distinguish siblings arriving separately from nested groups appearing in successive rounds. Measure click-to-first-content and longest frame; do not infer improvement from total request time alone.
2. Keep complete, sorted sibling publication. If remembered-descendant rounds explain the symptom, stage the newly revealed expanded subtree and publish its results together, while loading only reachable remembered expansions. Preserve error rows and generation guards; a slow descendant must not indefinitely hide available immediate children. Do not preload the checkout.
3. Delay the loading indicator so quick reads do not insert a transient loading row; VS Code's 800 ms is a reference value, not a measured optimum for escode. Show results as soon as ready.
4. Add viewport virtualization only if measurements show row mounting dominates. Preserve tree keyboard navigation, selection, active-descendant accessibility, inline editing, reveal/scroll restoration and drag targets; wrapping labels currently make fixed-height windowing a behavioral decision.

The initial implementation belongs in `files.tsx`; no new transport or dependency is needed for delayed feedback or staged cache publication. Cover click, keyboard, hover expansion and active-file reveal through the existing Files tree/watch/reveal/drag scenarios. Add a focused frame-observation check for complete sibling publication and slow/error/stale subtree results if staging is introduced. Virtualization requires separate accessibility and scroll verification. No product concepts change, so the glossary needs no amendment.
