# Reliable multi-client execution architecture

Status: specification amendment, 2026-10-31. The user selected fresh-state cutover and directed retention and restart behavior to copy T3. Decision owner: [Resolve execution retention, cutover and recovery guarantees](https://github.com/ejjsharpe/escode/issues/159), under [Specify reliable multi-client execution architecture](https://github.com/ejjsharpe/escode/issues/157). This document authorizes no application implementation and claims no runtime acceptance.

## Authority and scope

Adopt Effect-native host orchestration, one Execution authority, retained execution and normalized-content events, transactional follow-up work and snapshot/catch-up synchronization. React, Monaco and pure decisions/projections remain ordinary TypeScript. Provider-native conversation context remains provider-owned; recorded visible content cannot reconstruct it.

The [architecture research](https://github.com/ejjsharpe/escode/blob/9bdf7cbbf1818e5fa4305ba2077de963db6d7568/docs/research/execution-architecture.md) supplies the ownership and transaction design. T3 policy means upstream commit `54c5f25249961a1aa0b61932329092eadbd9d6fc`, not an unversioned promise to follow future changes or the user's installed binary.

This amendment supersedes the foundation's exclusion of the application event store/restart continuation and the durable-state specification's current-state-only execution authority. It also supersedes the research proposal's additional same-boot/independent-control-evidence restart requirement: the user's latest direction is to copy T3's policy. WAL `NORMAL`, exact context identities, independent client recovery, file checkpoints, historical restoration safeguards and uncertain-effect protection otherwise remain.

## Execution ownership and transactions

Execution owns authenticated admission, deduplication, revision checks, scheduling, receipts, resource concurrency, recovery and shutdown. Files retains path authority, native identity and save-conflict rules; Chats retains conversation decisions; provider adapters retain protocol translation. These modules cannot independently launch durable work outside Execution. Reads and ephemeral observations need no execution journal.

Use one host runtime and scoped Effect resources for provider processes, connections, storage and watchers. Host work outlives client subscriptions. A disconnected RPC cancels its wait, not the execution. Keep pure decisions and projections free of external effects. Expected failures have explicit wire/receipt outcomes; interruption does not prove external termination. Resource finalization is bounded and retains uncertainty.

An immutable command binds ID, authenticated client/system origin, host/store identity, target, expected revision and payload. Repetition returns the existing receipt; a changed payload under the same ID is rejected. One short SQLite transaction reserves the receipt, appends facts/content, updates projections and inserts required follow-up jobs. Publish and wake workers only after commit. Recover missed wakeups from pending jobs. Admission is distinct from provider acceptance and completion.

Serialize conflicting chat/resource decisions; never hold a database transaction across provider or filesystem work. Preserve one foreground provider turn per chat and a separate title lane. Independent chats may run concurrently, including the existing disclosed shared-checkout behavior. Stop/shutdown must remain serviceable when ordinary workers are occupied. Fence stale workers and retain uncertainty if ownership of an old external process cannot be established.

Jobs retain identity, cause, target, dependencies, attempt and recovery classification. Completion records resulting facts, projections and dependent jobs atomically. Copy T3's selective outbox recovery: replay only explicitly safe work; cancel/reconcile recovered non-idempotent provider effects rather than retrying them because a lease expired. Preserve escode's exact filesystem-operation journals. No transaction provides exactly-once external effects.

## Events, content and rebuild

Retain execution/chat transitions, receipt lifecycle and observed normalized user/assistant messages and tool content. Events carry stable identity, host sequence, entity revision, schema version and command/execution causation. Commit order, not wall-clock time, orders facts. Do not event-source keystrokes or every filesystem notification.

Keep provider/thread/turn/item identities and explicit content coverage. Backfill is a recorded, deduplicated observation; missing output is not empty output. Native context and complete provider history remain separate from escode's recorded observations. Initial retained content belongs in SQLite; this amendment introduces no external blob framework.

Rebuild declared shared chat/activity/content/execution projections in a side store from retained facts, validating schema and sequence before publication. Replay cannot invoke providers, mutate project files or create new outbox jobs. Client drafts, editor buffers and file checkpoints retain their own authority; they are not reconstructed from shared chat events. An old store, deleted coverage or unavailable provider context cannot acquire complete-history status through a rebuild.

## T3 retention and capacity policy

Copy T3's selective compaction, not an invented age-based transcript expiry. Preserve creation/deletion events; compact superseded whole-chat state and keyed message/node/eligible turn-item versions according to the pinned rules, including their first/latest and commanded-item exclusions. Intermediate revisions can disappear: rebuild promises current declared projections, not every past streaming revision or an immutable complete audit trail. Keep current normalized-content projection rows. The inspected T3 paths impose no age-based execution/content expiry or total retained-content disk quota. Adopt that policy; growing database size is an accepted limitation. [Compaction rules](https://github.com/pingdotgg/t3code/blob/54c5f25249961a1aa0b61932329092eadbd9d6fc/apps/server/src/orchestration-v2/ProjectionMaintenance.ts#L199-L397), [content projection](https://github.com/pingdotgg/t3code/blob/54c5f25249961a1aa0b61932329092eadbd9d6fc/apps/server/src/orchestration-v2/ProjectionStore.ts#L2416-L2534).

Archive is not expiry. T3 deletion records a tombstone and schedules resource cleanup; it does not physically erase all retained database events or message/tool rows. Therefore neither archive nor deletion promises secure erasure of escode's recorded content. Copy these retention semantics without adding unrelated T3 product features or changing escode's existing archive eligibility/file-removal safeguards. Content can include sensitive messages and tool output. Provider-history deletion, external-resource removal and file-checkpoint expiry remain independent. [Archive path](https://github.com/pingdotgg/t3code/blob/54c5f25249961a1aa0b61932329092eadbd9d6fc/apps/server/src/orchestration-v2/Orchestrator.ts#L3907-L4040), [deletion path](https://github.com/pingdotgg/t3code/blob/54c5f25249961a1aa0b61932329092eadbd9d6fc/apps/server/src/orchestration-v2/ThreadDeletion.ts#L56-L238).

Prune succeeded/cancelled outbox rows strictly older than seven days, in batches of 500 with hourly repetition. Failed, pending and running rows are not eligible. This is outbox maintenance, not receipt or conversation expiry; never apply it to unresolved escode operation evidence. T3's legacy-v1 import cleanup is irrelevant to the selected fresh-store cutover. [Outbox cleanup](https://github.com/pingdotgg/t3code/blob/54c5f25249961a1aa0b61932329092eadbd9d6fc/apps/server/src/orchestration-v2/EffectOutbox.ts#L668-L708).

Use these concrete T3 values for the corresponding new execution paths; unaffected escode file/checkpoint and authenticated-frame bounds remain. Values are initial settings from source, not measured escode capacity:

- Event reads page at 500. App-wide replay allows a sequence gap of 1,000 and 8 MiB raw payload; chat replay allows 128 events and separate 1 MiB raw/encoded payload budgets. Excess or future cursors select snapshots. [Event reads](https://github.com/pingdotgg/t3code/blob/54c5f25249961a1aa0b61932329092eadbd9d6fc/apps/server/src/persistence/OrchestrationEventStore.ts#L157), [app replay](https://github.com/pingdotgg/t3code/blob/54c5f25249961a1aa0b61932329092eadbd9d6fc/apps/server/src/ws.ts#L718-L744), [chat replay](https://github.com/pingdotgg/t3code/blob/54c5f25249961a1aa0b61932329092eadbd9d6fc/apps/server/src/orchestration-v2/ThreadStream.ts#L18-L26).
- Each live subscription buffers at most 1,000 items / 8 MiB serialized payload. Overflow fails the subscription and resumes from its last sequence with snapshot fallback as needed. This is not a whole-process memory bound. [Live buffer](https://github.com/pingdotgg/t3code/blob/54c5f25249961a1aa0b61932329092eadbd9d6fc/apps/server/src/orchestration-v2/LiveStreamBudget.ts#L18-L100).
- History pages use 10 user turns, 75 items in windows without a user turn, 500 turn items in user-turn windows and 1 MiB encoded payload. Inline work items are limited to 150, older-thread user turns to 20, raw-turn scans to 150 and cursors to 4,096 characters. Paging is not expiry. [History paging](https://github.com/pingdotgg/t3code/blob/54c5f25249961a1aa0b61932329092eadbd9d6fc/apps/server/src/orchestration-v2/threadHistoryPaging.ts#L9-L35).
- Ordinary detail strings retain a 32,768-byte prefix; dynamic values use a 16,384-byte threshold; on-demand detail uses 256 KiB. Preserve truncation markers and T3's field-specific projection rules. In particular file-change diff/old/new strings are truncated before storage; recorded normalized content cannot promise full file diffs. This does not truncate separate file-checkpoint snapshots. [Wire projection](https://github.com/pingdotgg/t3code/blob/54c5f25249961a1aa0b61932329092eadbd9d6fc/apps/server/src/orchestration-v2/WireProjection.ts#L24-L220), [ingestion](https://github.com/pingdotgg/t3code/blob/54c5f25249961a1aa0b61932329092eadbd9d6fc/apps/server/src/orchestration-v2/ProviderEventIngestor.ts#L655-L670).
- Live command output uses 100 ms frames, 500 ms replacements when behind, 16 Ki characters per accumulated append, 64 live commands and 16 finished tails. A tail is 64 Ki characters, with a final-source bound of four tails. This ephemeral stream bypasses ordinary execution events; it is not a promise to retain every output byte. [Output hub](https://github.com/pingdotgg/t3code/blob/54c5f25249961a1aa0b61932329092eadbd9d6fc/apps/server/src/orchestration-v2/CommandOutputHub.ts#L29-L41), [tail size](https://github.com/pingdotgg/t3code/blob/54c5f25249961a1aa0b61932329092eadbd9d6fc/packages/shared/src/terminalOutput.ts#L38).
- Four effect workers, five maximum attempts for retry-eligible work, 30-second missed-wakeup polling and retry delay `min(30_000, 100 * 2 ** max(0, attemptCount - 1))` milliseconds. These do not authorize retrying ambiguous external effects or cap active provider turns at four. No new bounded durable-job-count claim is made. [Worker policy](https://github.com/pingdotgg/t3code/blob/54c5f25249961a1aa0b61932329092eadbd9d6fc/apps/server/src/orchestration-v2/EffectWorker.ts#L580-L900).
- Compaction repeats six hours after completion with persisted last-run time, first delay clamped between one minute and six hours, pages of 50 and cooperative yielding. At 25 ms of work, sleep nine times elapsed work; incremental-vacuum reclamation is at most 1,024 pages per minute when enabled. These limit maintenance work, not total database size. [Maintenance scheduling](https://github.com/pingdotgg/t3code/blob/54c5f25249961a1aa0b61932329092eadbd9d6fc/apps/server/src/persistence/DatabaseStorage.ts#L20-L150).

Storage failure blocks new ordinary admission; retain existing emergency Stop and disclose content gaps. Do not silently purge protected control evidence to create space. The absence of a total T3 content quota supersedes the earlier proposed quota requirement for this retained-content store only; existing bounded file checkpoints and client recovery remain applicable.

## Independent clients and catch-up

Snapshots identify store, projection version, subscription scope and committed high-water sequence. Subscribe before reading the snapshot/replay cut, buffer overlap, catch up through that cut and deduplicate the live tail. Use explicit snapshot reset when replay is unsuitable or coverage is missing. Filtered streams carry a cursor-through watermark: unrelated global sequence gaps are legitimate. Apply projection changes and cursor advancement together.

Entity revisions arbitrate competing commands independently of stream cursors. A stale client refreshes without losing its composer. Reconnection queries the original command receipt; it never creates a replacement Send identity. Authenticate each client and bind all identities to the host. Store replacement requires a new snapshot and receipt reconciliation.

Composer text, file buffers, selections and workspace views remain client-owned. Another client's Send cannot clear unsent text, and another client's Save cannot replace dirty bytes or their baseline. Preserve each client's move/Trash acknowledgements and existing explicit-save conflict workflow. This is synchronization of shared host state, not collaborative text editing.

## Restart continuation and durability

Copy T3's restart continuation policy for concepts supported by escode: default enabled with project override; resume the exact saved native conversation and admit a new visible system-origin execution saying “Continue where you left off.” Derive continuation message/command identities deterministically from the source execution. Do not resend the old command or imply restoration of its interrupted stack.

Retain T3's existing-continuation, newer-work, native identity/state, archived/deleted/settled/snoozed, pending/non-resumable request, explicit interruption and native-maintenance guards. Settings read failure or malformed settings disables continuation. Copy the guard against three continuation ancestors within the five-minute window anchored to the source completion/request time, and the special treatment of still-awaited background work (including note-only dispatch for settled work). Unsupported delegation/secret/snooze features are not new product scope; unknown outstanding requests cannot be classified as safe. Use the pinned source's eligibility and dispatch predicates rather than a simplified one-attempt policy. [Restart policy](https://github.com/pingdotgg/t3code/blob/54c5f25249961a1aa0b61932329092eadbd9d6fc/apps/server/src/orchestration-v2/RestartContinuation.ts#L33-L328), [settings recovery](https://github.com/pingdotgg/t3code/blob/54c5f25249961a1aa0b61932329092eadbd9d6fc/apps/server/src/serverSettings.ts#L706-L725).

Reconcile startup state before workers admit continuation. Recheck revision, cancellation and context at dispatch so a concurrent user action can invalidate eligibility. A continuation's uncertain dispatch is not blindly retried. Ordinary Send, approval and file mutation still require persisted admission. Emergency Stop remains available after persistence failure, with its non-durable/uncertain outcome disclosed. Backup restoration remains quarantined; it is not an ordinary restart.

Keep SQLite WAL `NORMAL` and supported checkpoint full flushing. Copying T3 does not add a same-OS-boot prerequisite, a stronger control journal or proof that no committed control state was lost. An OS crash/power loss can roll back acknowledged Stop, approval, newer-work or continuation-budget records while leaving a consistent database. Consequently the retained-state guards cannot guarantee that all acknowledged Stop decisions survive such failure. Record this accepted limitation explicitly; do not describe missing retained evidence as independently proven safety.

Explicit user Stop and escode's Stop-and-Close Quit/host-shutdown path retain their recorded interruption semantics. An orderly server restart alone is not a blanket blocker: T3 can prepare continuation during orderly shutdown as well as startup recovery. Client loss leaves host-owned work running and does not trigger restart continuation. Fresh approval is required when provider policy requests it; old approval responses are never replayed. [Runtime recovery](https://github.com/pingdotgg/t3code/blob/54c5f25249961a1aa0b61932329092eadbd9d6fc/apps/server/src/orchestration-v2/ProviderRuntimeRecoveryService.ts#L652-L824), [SQLite durability](https://github.com/pingdotgg/t3code/blob/54c5f25249961a1aa0b61932329092eadbd9d6fc/apps/server/src/persistence/Sqlite.ts#L25-L35).

## Fresh-state cutover

Initialize a distinct versioned store without importing old host state, receipts, associations, settings, composers or recovery drafts. Preserve old stores, project files, provider histories and existing worktrees. Existing application associations and unsaved recovery do not automatically appear in the new store.

Before switching, stop active work and save or export unsaved edits. Do not silently switch a running host or reuse old admission authority. Old stores remain available as recovery artifacts, not live fallback authorities. No migration framework, dual dispatch or backward-compatible transition release is required. Within the new format, restart recovery, schema validation, consistent recovery copies and exact identity preservation remain mandatory.

## Implementation handoff and acceptance

Application implementation is a subsequent effort. First consolidate Execution admission/lifecycle and Effect ownership with current behavior intact; then introduce one complete transactional Send/control slice, remaining durable mutations, retained content/rebuild and multi-client catch-up. Enable automatic continuation last, after recovery and guard qualification. Replace superseded routes as slices land; avoid parallel authorities.

The change must reach contracts, host composition, ChatService, DurableSend/DurableFiles, SQLite storage, recovery-copy inventory, client runtime, composer/buffer recovery, lifecycle UI, provider adapters and their affected fixtures. Preserve native file safeguards and historical workflows. Track copied T3 files, pin, adaptations and applicable attribution.

Required focused qualification:

1. Competing client admissions: one revision winner, both drafts intact, duplicate command returns one receipt.
2. Crashes before/after transactional commit and lost publication: no partial receipt/event/projection/job set; required jobs remain discoverable.
3. Provider accepts before result loss: exact reconciliation or visible uncertainty, never a second old Send.
4. Stop racing queued continuation, emergency Stop during storage failure and approval-wait recovery: exact target, retained uncertainty and no replayed approval.
5. Restart policy parity, deterministic identities, newer-work exclusion and the three-link/five-minute guard. OS-loss tests document NORMAL rollback exposure rather than claiming detection of erased controls.
6. Snapshot/catch-up overlap, filtered cursors, slow-client overflow and store replacement converge without clearing independent client edits.
7. Save/move/Trash with another client's dirty buffer preserves bytes, baselines and acknowledgement obligations.
8. Projection rebuild matches retained facts and makes zero provider/filesystem calls or new jobs; retention/deletion behavior preserves its declared coverage.
9. Filesystem mutation loss uses existing operation evidence; full disk and oversized/stalled delivery retain control and disclose unavailable content.
10. Fresh cutover preserves old stores and external resources; recovery-copy restoration remains quarantined; packaged Electron and installed-provider checks cover the changed paths.

No runtime tests, upstream execution, stress measurement or power-loss qualification are implied by this specification. Distributed hosting, collaborative editing, generic workflow machinery and reconstructed native context remain out of scope.
