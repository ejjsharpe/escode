# Synchronization and command protocol research

Research for [What synchronization and command protocol preserves chat work across disconnects and slow clients?](https://github.com/ejjsharpe/escode/issues/55), retrieved 2026-10-30. Recommendations and numeric starting limits below are provisional engineering inputs, not accepted product policy or implementation evidence. No glossary changes are proposed as agreed terminology.

## Evidence and scope

Read README, GLOSSARY, tracker instructions, the [Effect foundation map](https://github.com/ejjsharpe/escode/issues/49), the complete ticket and prerequisite resolutions. In particular, the [agreed lifecycle amendment](https://github.com/ejjsharpe/escode/issues/53#issuecomment-6520435690) governs this proposal: closing a window retains edits and host work; disconnect is not Stop; provider replacement invalidates callbacks; host restart starts no turn automatically. Current code polls every saved chat at 300 ms per subscribed project store, retrieving whole snapshots and notifying listeners after each result. Send persists draft/context and marks acceptance uncertain before `turn/start`; Stop uses the live session without directory validation; replies validate live tokens and context. Files watches share native watchers by directory identity, coalesce at 100 ms and release after the final listener. Source Control refreshes at two seconds. These are the concrete seams to replace, not evidence that a network protocol already exists. ## Recommended protocol

Use validated RPC commands and separate bounded subscription streams over the authenticated local WebSocket path recommended by the boundary research. Keep the host service graph transport independent. Adapt T3's budget, snapshot/replay/live handoff and scoped cleanup together; do not copy its application event schema or treat provider history as an application event log. First delivery can use snapshot fallback with bounded in-memory replay. Persist the existing domain records plus command intents/receipts, rather than requiring a durable transcript event log merely to reconnect. Restart rotates the stream epoch and rebuilds available state from saved associations, provider history and operation reconciliation. That loses transient replay across restart honestly, without losing the durable facts it claims to preserve.

Every envelope carries negotiated protocol version, stable host ID, random host-incarnation epoch, connection ID and operation/subscription ID. Resource keys include host and exact saved chat/checkout identity. A provider-session generation is separate from the connection and stream epoch. Every new subscription has a generation; late responses from disposed generations cannot update another view. Validate resource authority server-side on each request, not from a client-supplied path. Version/auth negotiation details belong to the existing authority ticket; incompatible peers must not receive a partially understood mutation API.

Host scope owns provider sessions, admitted mutations, storage and process groups. Provider scope owns wire IDs and pending callbacks. Connection scope owns authentication, delivery budgets, heartbeat and subscriptions. View scope owns detail interest and client reducer lifetime. Releasing a view or connection cancels its reads, timers and watch references, never host-owned accepted commands. Cancelling an RPC waiter after command admission does not cancel the command. Explicit Stop is separate.

### Streams, facts and representations

An app-wide summary stream supplies paged chat metadata and small replaceable status rows: chat identity, project/context availability, running/needs-input/interrupted status, request count and revision. Include closed-project and No project chats; do not copy transcript text or reply payloads into every row. Summary counts are current state, not a durable audit record. Visible conversations subscribe to detail; multiple local views of one chat share one detail subscription in the client runtime. Later multiple clients each own delivery interest independently.

Persist saved chat associations, draft text, provider identities, worktree/scratch reservations, uncertain-send intent, recovery drafts/baselines, file-operation intents and outcome acknowledgements. A live approval is transient even if its existence was logged: only the surviving provider callback makes it answerable. Token chunks, progress, connection state, watch notifications, replay buffers and intermediate summary replacements are transient. Provider-owned history remains the source for saved conversation contents; incomplete local rendering must be labelled partial/unavailable rather than fabricated as completed history. Existing durable file-operation facts cannot be discarded by an older client snapshot. Source: [operation reconciliation](https://github.com/ejjsharpe/escode/blob/a2752152a8a32db7477f99178ef89c9e9744c772/apps/desktop/host/file-operation-state.ts), [workspace persistence](https://github.com/ejjsharpe/escode/blob/a2752152a8a32db7477f99178ef89c9e9744c772/apps/desktop/host/workspace.ts).

Use full item-state replacements after accumulating provider deltas, keyed by chat/turn/item and item revision. Batch up to 50 ms, flushing before terminal, permission/input, identity-change and synchronization barriers. Never drop arbitrary append deltas or coalesce request transitions into text. Large bodies are paged/chunked by immutable body revision; the reducer commits a replacement only when all chunks validate. A terminal event contains the final revision, not merely a timer flush. Interrupted partial text remains explicitly partial.

### Snapshot and event handoff

Each stream has a monotonic sequence scoped to `(hostId, hostEpoch, resource, streamKind)`. Sequences are not globally ordered across chats and are not wall-clock timestamps. Use lossless integer encoding and validate bounds. Every delivery batch carries `fromExclusive`, `throughInclusive`, and resource revisions; empty synchronization barriers can advance coverage. This permits coalescing within a covered interval without confusing intentionally omitted intermediate replacements with packet loss.

1. Under the same resource serializer used by all projection writers, register a bounded tail subscription and capture an immutable projection plus high-water sequence S. Release the lock before encoding/network I/O. Publisher mutation, revision increment and tail insertion must share that serializer. Do not hold it while awaiting a client ACK.
2. Send a bounded snapshot at S, in revision-pinned pages if necessary. Drain racing tail events into the charged queue while pages are read. Pages from a different revision cannot be combined. Overflow during snapshot aborts that generation; it cannot silently omit a tail.
3. Discard overlap at or below S; deliver tail batches starting from S. Send `synchronized(S or later covered cursor)` only after the initial state and required catch-up have been applied. Client may resume only from a complete projection and its applied coverage cursor, never a received-but-unapplied cursor.
4. Client applies matching-generation batches only when `fromExclusive` equals its cursor. Ignore fully covered duplicates; a partial overlap or forward gap requests resynchronization. An old epoch is rejected; an ahead cursor, expired replay window, partial snapshot or missing projection triggers a new snapshot. Do not buffer arbitrary out-of-order packets indefinitely.
5. ACK means validated, applied state through a cursor; it is neither provider acceptance nor durable file-operation acknowledgement. Restarted clients without that projection request snapshot even if they retained a cursor. History paging must not delete rows absent from a partial page.

For reconnect to the same host incarnation, replay from a complete client's cursor only when the retained contiguous range fits the replay budget. Otherwise snapshot. Connection recovery never calls Send. Provider reconnect is a different command: invalidate old callbacks, preserve known thread/context identity, reload available history and reflect interruption; it never resends a prompt. A host restart rotates epoch, reconciles durable records and requires explicit user action before another turn.

This adapts the sequencing and synchronization barriers in [ws.ts](https://github.com/pingdotgg/t3code/blob/305a90dce44b8b7813d951662f13ce8510a3c669/apps/server/src/ws.ts), [ThreadStream.ts](https://github.com/pingdotgg/t3code/blob/305a90dce44b8b7813d951662f13ce8510a3c669/apps/server/src/orchestration-v2/ThreadStream.ts) and [subscribeBeforeSnapshot.ts](https://github.com/pingdotgg/t3code/blob/305a90dce44b8b7813d951662f13ce8510a3c669/apps/server/src/utils/subscribeBeforeSnapshot.ts). The helper's mutex variant is safe only if every writer uses that mutex; its name alone is no guarantee.

### Provisional numeric budgets and overflow

These are initial experiment settings, not measured capacity, accepted performance targets or a limit on retained user history. Count serialized UTF-8 bytes before enqueue, including in-flight batches until ACK. Measure actual heap separately.

- Per detail subscription: 1,000 retained records or 8 MiB, whichever first; at most one unacknowledged batch, at most 64 records/256 KiB per batch. Snapshot/history page at most 256 KiB with explicit continuation. Oversized text bodies chunk at 64 KiB; don't serialize an entire unbounded entity before testing its size.
- Summary: at most 128 rows per page and 256 KiB per page; 100 ms replacement window. Retain at most 1 MiB/1,000 pending rows. On overflow emit a reset requirement and snapshot; never silently retain a misleading needs-input count.
- Replay: per resource at most 1,000 records/8 MiB/60 seconds; evict oldest at any bound. Resume only up to 128 records/1 MiB; otherwise snapshot. Across the host replay cache cap 32 MiB, evicting cold resources first. Eviction cannot delete durable command or operation records.
- Per connection: at most 16 view streams and 16 MiB total charged delivery; host delivery total 64 MiB and 32 active client connections. Reject additional subscriptions/connections explicitly. Account shared objects conservatively per logical delivery. Directory interests capped at 256 per connection and 1,024 distinct native watchers per host; report unavailable coverage when exhausted, retaining Refresh.
- No ACK progress for 15 seconds closes the affected stream; repeated connection-level overflow closes the connection. Reconnect backoff 250 ms doubling to 10 seconds with jitter; reset after synchronization. Recovery attempts do not enqueue commands.
- Reserve 32 control messages/256 KiB per connection for ACK, stale/reset errors and command status; still cap decoded frames at 512 KiB and close a wedged socket rather than accumulating errors. Send retains the current 100,000-character input validation within that byte envelope. Large file writes use separately bounded transfer chunks and a final checked commit, preserving the 2 MiB editor limit; file transfer design is not implemented here.

Detail overflow fails/resets only the subscription, leaving host work running. Watch invalidations collapse to one dirty marker per checkout; overflow means rescan all loaded directories. Git refresh collapses to one dirty bit. Durable outcomes are queried from storage after reset. No stream overflow may discard an operation intent, supply an approval or cancel a turn.

The transport must gate pulls on ACK; otherwise next-pull release is premature. Bound socket outbound buffers and provider ingress/writer queues separately, and reject new producers on exhausted host admission budgets. A stalled client must never block the host's provider ingestion. Provisionally cap provider text caches at 8 MiB per active chat and 32 MiB per host, with at most 256 MiB of temporary body spool per host. Provider text caches must have a bounded resident window and page older bodies from provider history or a bounded disk spool. If history/spool cannot recover a large body, expose partial/unavailable text, keep Stop available and record the limit; never report a complete transcript. Decide and verify disk quota/error behavior before claiming sustained end-to-end bounded memory. Above limits bound delivery retention only; they do not bound Electron, Monaco, provider processes or all host heap.

## Commands, deduplication and uncertainty

Mutation envelope: random command ID, host ID, stable authenticated principal/client identity, resource ID, command type, expected resource revision, canonical payload digest, and command-specific live generation/turn/request tokens. Scope the durable key to `(hostId, principalId, commandId)`; bind its digest and target. Same key with different content is conflict, not a new attempt. Recheck authorization even when retrieving an old receipt; do not reveal another principal's result. Serialize concurrent admission with a storage uniqueness constraint and the resource mutation gate.

Recommended state machine:

`received -> rejected | durably-admitted -> preparing -> dispatch-intent -> provider-accepted -> completed | failed`

`dispatch-intent -> uncertain` on crash/transport loss without conclusive provider result. File commands use their existing operation intent/outcome states rather than pretending provider stages apply. Record known partial effects even when preparation fails. A protocol rejection precedes effects; a failed command can have partial effects and must report them.

A transport receipt means only decoded/received. `durably-admitted` means identity, input and intent are recorded before side effects; it does not mean the provider accepted a turn. Persist dispatch intent before invoking the provider, then provider identity/turn acceptance before reporting that stage. Final result reports actual domain outcome. State and corresponding durable receipt updates should share one local transaction where possible; an external provider/filesystem call cannot share that transaction. Persistence failure before intent means no side effect; persistence failure after an effect means uncertain until reconciled.

Client timeout after admission becomes `awaiting status`, not failed-and-retry. Query `commandStatus` and current snapshot/history using the same ID. Duplicate admitted/in-progress requests return recorded status and never dispatch again. On host restart, reconcile intents; do not run a recovered queued Send, continuation or reply. Undispatched recovered Send requires explicit new user action after showing retained draft/context; dispatch-intent without proof remains uncertain. Matching prompt text or absent history alone is insufficient proof of non-execution. A changed explicit Send gets a new ID only after unresolved earlier attempts are surfaced; automatic new-ID retries are forbidden.

Provisional receipts: retain terminal result bodies for 7 days, up to 10,000 terminal records/16 MiB per host; prune only terminal entries and return `outcome unavailable` for old queries. Use host-issued mutation-admission epochs valid for 24 hours: submissions from expired/rotated epochs cannot execute even when their receipts have been pruned. Apply the 10,000-record/16 MiB admission cap to total receipt/intent storage, reserving capacity before any effect. Reject new commands if required nonterminal records exhaust storage; never prune uncertainty or operation evidence to admit more work. Epoch expiry does not invalidate status queries or live turn identity. Revoking admission epochs after crash prevents replay through an empty receipt store. Client reconnect performs status lookup, never automatic mutation resubmission. Backups/rollback cannot safely revive old admission epochs. These rules bound the dedupe horizon without promising forever deduplication or exactly-once external effects.

This deliberately extends [T3 receipt schema](https://github.com/pingdotgg/t3code/blob/305a90dce44b8b7813d951662f13ce8510a3c669/apps/server/src/persistence/OrchestrationCommandReceipts.ts), which records accepted/rejected, aggregate/type and result sequence by command ID; that schema alone has no payload digest, principal scope or escode external-dispatch uncertainty states.

### Replies, Stop and concurrent control

Reply address is `(hostId, chatId, providerSessionGeneration, requestToken, turnId when present)`; the host maps a random token to the provider wire ID. Do not use wire ID alone. Client reconnect can rediscover a still-live request in the same provider generation; provider replacement/restart cannot resurrect it. Under the chat gate, verify request remains pending and answer shape/authority, consume it once and record reply dispatch intent. Competing replies get already-answered/stale/conflict, not two provider responses. Unknown delivery remains uncertain rather than automatically repeated. Context-sensitive replies retain current directory checks; no context validation should disable independent Stop.

Stop addresses host/chat/provider generation and captured turn ID, bypassing directory existence checks. Duplicate Stop for that turn is harmless status lookup; a delayed Stop must not interrupt a later turn. For Send still preparing before turn ID allocation, capture a host operation token: Stop marks that exact pending operation cancelled, checks between asynchronous preparation steps, and interrupts any turn that wins the dispatch race. Preserve reserved resources and partial outcomes. Stop acknowledgement means requested; completion/interruption is confirmed by actual provider/session outcome. Do not equate Stop with rollback or host shutdown.

Resource revisions, serialized command admission, reply consumption and operation acknowledgements are required hooks for the multi-client decision. This report does not choose edit ownership, takeover, simultaneous draft conflict UX or which client may approve/stop. The host must enforce the eventual policy, including invalidating affected clients on ownership changes. A stale full workspace snapshot must not erase newer command outcomes or another client's edits.

## Files and Source Control

Watch subscription registers/validates directory identity before listing, then lists while collecting invalidations. Return a listing revision plus dirty-generation; if invalidated during enumeration, schedule another listing, avoiding a false stable claim. External filesystem writes cannot join the host serializer, so this is convergence, not an atomic filesystem snapshot. Loaded folders only; deduplicate native handles by checkout/path/object identity and reference count. Last view/connection release cancels timers/listeners and closes unused handles. Watch errors expose degraded state, retry on focus/Refresh/re-expansion, and rescan missed events. A watch event is a hint, never authority or a file mutation result. Keep dirty buffers at their original identity if paths disappear.

Node explicitly documents platform caveats, unreliable network/virtualized watches, inode replacement and potentially absent filenames; thus names cannot be trusted as a complete change log. Source: [Node fs.watch caveats](https://nodejs.org/api/fs.html#caveats). Preserve escode's existing identity checks and explicit refresh recovery rather than inferring reliable delivery.

For Source Control, host owns one in-flight refresh per checkout plus a dirty bit. Refresh on relevant worktree/Git metadata invalidation, explicit Refresh, focus/reconnect and successful app mutations; keep a two-second fallback while Source Control is visible. Linked worktrees require common Git metadata invalidation as well as checkout-local metadata. Mark results stale when invalidated during a command; schedule one follow-up. Tag status/diff responses with checkout identity, request generation, HEAD/index/worktree observation tokens and resource revision; reject late results after checkout/diff selection changes. Git status plus diff are not one filesystem transaction. Revalidate before saves/mutations; retain accepted explicit-save conflicts. Use stable machine output (`--porcelain=v2 -z`) and `--no-optional-locks` for background status where appropriate; official docs describe porcelain stability and optional-lock concerns for background refresh. Source: [Git status](https://git-scm.com/docs/git-status/2.53.0). These proposed flags require parser parity tests before replacing existing parsing.

## Exact upstream divergences and reuse checks

- T3 [LiveStreamBudget](https://github.com/pingdotgg/t3code/blob/305a90dce44b8b7813d951662f13ce8510a3c669/apps/server/src/orchestration-v2/LiveStreamBudget.ts) defaults to 1,000 items/8 MiB and releases in-flight charge on next pull, relying on RPC ACK. Preserve its accounting/cleanup algorithm; add connection/host quotas, frame and producer limits, explicit applied-cursor semantics and local adapter ACK tests. Its bounds are serialized bytes, not heap.
- T3 [ThreadStream](https://github.com/pingdotgg/t3code/blob/305a90dce44b8b7813d951662f13ce8510a3c669/apps/server/src/orchestration-v2/ThreadStream.ts) bounds resume at 128 events/1 MiB encoded and 1 MiB raw payload. Retain bounded fallback and history paging. escode's proposed replay cache is transient and epoch-scoped; T3 uses persisted application events. Provider history is not a substitute log.
- T3 [ThreadLiveEventCoalescer](https://github.com/pingdotgg/t3code/blob/305a90dce44b8b7813d951662f13ce8510a3c669/apps/server/src/orchestration-v2/ThreadLiveEventCoalescer.ts) uses 50 ms/512 pending updates with full-state replacements and barriers. Adapt its event algebra and cursor semantics to covered batches, rather than assuming every domain sequence will be delivered individually. Its provider text accumulator retains full text without an overall byte bound; add resident-body accounting/paging before claiming bounded memory.
- T3 imports command receipt/event/projection persistence and compaction semantics. escode must retain its uncertain Send, exact directory identities and durable file-operation journal, adding explicit digest/admission/crash stages rather than copying accepted/rejected as external-execution truth. See [ProjectionMaintenance](https://github.com/pingdotgg/t3code/blob/305a90dce44b8b7813d951662f13ce8510a3c669/apps/server/src/orchestration-v2/ProjectionMaintenance.ts).
- The [lifecycle comparison](https://github.com/ejjsharpe/escode/blob/c50d774abcc8576820648d1698133aeda54c0237/docs/research/t3-lifecycle.md) identifies T3's default conditional restart continuation and project-removal semantics. Disable continuation for escode; project editor close cannot become thread deletion/cancellation. T3's file-buffer approach cannot replace explicit-save/recovery/intents. The agreed lifecycle amendment takes precedence.
- Upstream Effect 4.0.5 and generated Codex schema provenance require the prerequisite 4.1.0/runtime/provider compatibility experiments. Native RPC cancellation does not automatically establish host-owned lifetime. Do not use sliding raw provider notifications as an authoritative lossless feed.

## Executable-check specifications for the handoff

These are test designs, not executed results. Use fake clocks/providers/storage and fault injection, then real Electron/WebSocket/native checks. Retain upstream [budget tests](https://github.com/pingdotgg/t3code/blob/305a90dce44b8b7813d951662f13ce8510a3c669/apps/server/src/orchestration-v2/LiveStreamBudget.test.ts), [ws tests](https://github.com/pingdotgg/t3code/blob/305a90dce44b8b7813d951662f13ce8510a3c669/apps/server/src/ws.test.ts), [client synchronization tests](https://github.com/pingdotgg/t3code/blob/305a90dce44b8b7813d951662f13ce8510a3c669/packages/client-runtime/src/state/threads-sync.test.ts), coalescer, shell, history merge and bounded snapshot tests from the reuse report.

1. Pause before registration, at snapshot capture, while encoding and before live drain; publish in each gap. Assert the final client projection equals host at synchronized cursor, no lost item/request, zero duplicate append. Repeat snapshot paging overflow and cancellation at every yield; assert resource counters return to baseline.
2. Generate 10,000 seeded event histories; duplicate/drop/reorder batches, inject stale subscription/host/provider epochs and overlapping coverage. Compare reducer with an uncoalesced reference. Assert gap/reset instead of silent divergence and no resume from partially applied state.
3. Two clients, one ACK-stalled: produce 10,000 item updates/second for 60 seconds with variable payloads. Assert charged counts/bytes never exceed budgets, healthy client reaches terminal state, stalled subscription closes, provider work continues and queue/socket/provider counters remain bounded. Repeat 30 minutes with many chats and measure retained heap plateau after GC; set heap gate only after baseline variance is measured. A serialized counter pass alone is insufficient.
4. Disconnect before/after every Send journal write, provider dispatch, acceptance and response. Crash/restart at the same points. Assert at most one dispatch per admitted ID in the live host, zero automatic dispatch after restart, prompt/reservations/provider identity retained and unknown outcome displayed honestly. Duplicate with changed digest/principal/target must fail. Evict receipts, expire admission epochs and restore backup: old IDs must not execute as new.
5. Concurrent reply A/B, request expiry, provider replacement with reused wire ID, client reconnect to surviving provider and stale browser tab. Assert one valid response or explicit uncertainty; stale generations dispatch zero responses. Stop with deleted/replaced checkout must target its captured turn, never a newer turn. Cover Stop during preparation and dispatch races.
6. Disconnect/cancel a directory subscription during listing/watch setup; create/rename/delete directories between identity checks, suppress watch events and inject watcher failure. Assert no authority gained, dirty edits retained, focus/Refresh convergence, released watchers/timers and no late view update.
7. Burst Git invalidations while refresh blocks, change HEAD/index externally and switch checkout/diff selection. Assert one in-flight scan plus one dirty bit, stale results rejected, follow-up scheduled, two-second visible fallback and errors distinct from clean status. Test linked worktree common metadata and filenames with NUL-safe parsing.
8. Kill between durable file intent, filesystem effect, persisted outcome and client acknowledgement. Reconnect an older snapshot. Assert actual reconciliation, retained baselines/drafts, unresolved mutation blocked and completed batch facts not erased. Match existing file-operation/native-race tests.
9. Close/reopen last macOS window with dirty text/active approval; compare renderer death with host death; confirm/cancel Quit. Assert agreed retained edits, independent host work, no synthetic reply, no restart turn, preserved explicit-save conflicts and descendant process cleanup on confirmed Quit.
10. Measure baseline-relative production IPC/socket bytes, React commits, history serialization, navigation latency, event-loop delay, CPU and retained memory at 1/25/100 chats and 1/2/16 detail subscriptions. Assert background summaries exclude transcript payloads and unobserved chats create zero detail subscriptions. Re-run keyboard/VoiceOver preservation gates; do not infer accessibility or performance from source inspection.

Affected seams include host ChatService/Chats/main IPC dispatch, project watcher/Git/native adapters, workspace/file-operation acknowledgement storage, preload/contracts, renderer chat-state/Agents/ChatView/Files/Source Control, build/runtime composition and host/UI concurrency/recovery fixtures. Keep pure reconciliation and React presentation reusable. No edits to these seams were made in this research.

## Remaining decisions and limits

Existing authority, multi-client and phased-plan tickets own the remaining choices; no new out-of-scope product question was established. Newly precise questions to carry there: which client may mutate shared drafts or consume a pending reply; how does revocation invalidate already-admitted control; which immutable body paging/spool strategy meets sustained-memory tests under the selected Codex runtime; and what measured limits replace the provisional quotas? Engineering experiments can settle the latter without asking the user to pick queue sizes.

No implementation, dependency installation, live provider turn, runtime compatibility test, packaged lifecycle check, crash/power-loss experiment or performance measurement was performed. Source inspection and documentation validation support a protocol recommendation, not an end-to-end guarantee. In particular, exactly-once provider/filesystem effects, latest-keystroke recovery and transactional external filesystem snapshots are not established.
