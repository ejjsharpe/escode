## T3 Code: implemented mechanisms and limits

1. **Effect owns runtime structure; serialization is explicit.** Thread commands acquire a keyed lock before dispatch ([Orchestrator.ts:13467–13485](https://github.com/pingdotgg/t3code/blob/54c5f25249961a1aa0b61932329092eadbd9d6fc/apps/server/src/orchestration-v2/Orchestrator.ts#L13467-L13485)). The reusable lock uses a per-key semaphore, reference-counted users and `acquireUseRelease`; it is explicitly non-reentrant ([KeyedLock.ts:15–55](https://github.com/pingdotgg/t3code/blob/54c5f25249961a1aa0b61932329092eadbd9d6fc/packages/shared/src/KeyedLock.ts#L15-L55)). This establishes in-process ownership and cleanup, not a distributed lock or durable queue by itself.

2. **Command acceptance, events, projections and effects share a transaction.** `commitCommand` reserves a command receipt; duplicate IDs return the existing result. It appends events, applies projections, enqueues outbox effects and updates the accepted receipt together. Cancellation signals, worker wakeups and event publication follow commit ([EventSink.ts:635–708](https://github.com/pingdotgg/t3code/blob/54c5f25249961a1aa0b61932329092eadbd9d6fc/apps/server/src/orchestration-v2/EventSink.ts#L635-L708)). A semaphore orders commit/publication, and an interruption mask protects publication after SQL commits ([EventSink.ts:245–284](https://github.com/pingdotgg/t3code/blob/54c5f25249961a1aa0b61932329092eadbd9d6fc/apps/server/src/orchestration-v2/EventSink.ts#L245-L284)). **Limit:** an accepted receipt proves durable orchestration acceptance, not completion of provider work; interruption masking cannot prevent process death.

3. **Outbox scheduling has durable state and deliberate replay classes.** Claim eligibility blocks later same-thread work behind running or earlier pending effects, including retry backoff; title generation has a separate lane ([EffectOutbox.ts:313–353](https://github.com/pingdotgg/t3code/blob/54c5f25249961a1aa0b61932329092eadbd9d6fc/apps/server/src/orchestration-v2/EffectOutbox.ts#L313-L353)). Workers claim, race execution against cancellation, settle success, or retry with bounded exponential delay; the daemon defaults to four workers and periodically checks durable availability ([EffectWorker.ts:739–840](https://github.com/pingdotgg/t3code/blob/54c5f25249961a1aa0b61932329092eadbd9d6fc/apps/server/src/orchestration-v2/EffectWorker.ts#L739-L840), [884–930](https://github.com/pingdotgg/t3code/blob/54c5f25249961a1aa0b61932329092eadbd9d6fc/apps/server/src/orchestration-v2/EffectWorker.ts#L884-L930)). After process loss, pending/running provider start, interrupt, steer, restart and response effects are cancelled; running effects in the replay-safe allowlist are requeued ([classification:125–144](https://github.com/pingdotgg/t3code/blob/54c5f25249961a1aa0b61932329092eadbd9d6fc/apps/server/src/orchestration-v2/EffectOutbox.ts#L125-L144), [reconciliation:487–514](https://github.com/pingdotgg/t3code/blob/54c5f25249961a1aa0b61932329092eadbd9d6fc/apps/server/src/orchestration-v2/EffectOutbox.ts#L487-L514)). **Limit:** this is selective recovery, not blanket at-least-once replay or exactly-once external execution; provider effects and SQLite do not share the shown transaction.

4. **Recurring scheduling is distinct from command serialization.** The scheduler runs registered sources every five seconds, prevents overlapping invocations per source, binds fibers/registration to scope, and waits for startup activation ([Scheduler.ts:21–58](https://github.com/pingdotgg/t3code/blob/54c5f25249961a1aa0b61932329092eadbd9d6fc/apps/server/src/scheduling/Scheduler.ts#L21-L58)). Scheduled delivery marks the task running, derives command/message IDs from a firing or webhook delivery identity, and sends in queue mode ([ScheduledTaskService.ts:795–843](https://github.com/pingdotgg/t3code/blob/54c5f25249961a1aa0b61932329092eadbd9d6fc/apps/server/src/scheduledTasks/ScheduledTaskService.ts#L795-L843)). Failed intermediate delivery advances the schedule and records failure because dispatch may already have occurred ([694–714](https://github.com/pingdotgg/t3code/blob/54c5f25249961a1aa0b61932329092eadbd9d6fc/apps/server/src/scheduledTasks/ScheduledTaskService.ts#L694-L714)). **Limit:** no real-time deadline or exactly-once firing guarantee follows from this polling mechanism.

5. **Reconnect combines persistent replay, a live tail and snapshot fallback.** The replay helper subscribes before reading the high-water mark, buffers live events during database catch-up and filters overlap by sequence ([LiveStreamBudget.ts:333–387](https://github.com/pingdotgg/t3code/blob/54c5f25249961a1aa0b61932329092eadbd9d6fc/apps/server/src/orchestration-v2/LiveStreamBudget.ts#L333-L387)). The WebSocket thread subscription accepts an `afterSequence`, measures count/byte budgets, replaces unsuitable replay with a snapshot, then joins live events after high-water ([ws.ts:905–974](https://github.com/pingdotgg/t3code/blob/54c5f25249961a1aa0b61932329092eadbd9d6fc/apps/server/src/ws.ts#L905-L974)). **Limit:** these are per-subscriber convergence mechanisms; they do not establish a durable acknowledgement from every client, offline command reconciliation, unlimited retained history, or a process-memory bound. The code explicitly distinguishes replay payload limits from process memory.

6. **Runtime shutdown and provider continuation are separate policies.** Server shutdown closes the command gate, interrupts workers, prepares recovery, shuts down provider sessions and reconciles state; startup performs recovery before starting effect workers ([serverRuntimeStartup.ts:461–487](https://github.com/pingdotgg/t3code/blob/54c5f25249961a1aa0b61932329092eadbd9d6fc/apps/server/src/serverRuntimeStartup.ts#L461-L487), [533–555](https://github.com/pingdotgg/t3code/blob/54c5f25249961a1aa0b61932329092eadbd9d6fc/apps/server/src/serverRuntimeStartup.ts#L533-L555)). Native Codex continuation uses `thread/resume` and returns the provider's native identity ([CodexAdapterV2.ts:6985–7036](https://github.com/pingdotgg/t3code/blob/54c5f25249961a1aa0b61932329092eadbd9d6fc/apps/server/src/orchestration-v2/Adapters/CodexAdapterV2.ts#L6985-L7036)). Separately, restart continuation requires suitable native identity/state, checks the project setting and an existing deterministic message ID, and dispatches a new continuation message ([RestartContinuation.ts:140–201](https://github.com/pingdotgg/t3code/blob/54c5f25249961a1aa0b61932329092eadbd9d6fc/apps/server/src/orchestration-v2/RestartContinuation.ts#L140-L201), [250–328](https://github.com/pingdotgg/t3code/blob/54c5f25249961a1aa0b61932329092eadbd9d6fc/apps/server/src/orchestration-v2/RestartContinuation.ts#L250-L328)). **Limit:** restoring a provider conversation and asking it to continue does not restore its interrupted stack or guarantee that prior external side effects will not recur. One adapter is not evidence of identical guarantees across providers.

## VS Code Agent Host: implemented mechanisms and limits

1. **Promise queues and reducers provide orchestration here, rather than Effect.** Dispatch has a synchronous fast path; asynchronous preparation chains behind a queue keyed by client ID ([agentService.ts:12455–12485](https://github.com/microsoft/vscode/blob/53ab3ae2e4eb7bceaf797a7e4d05bd8c7a5c203d/src/vs/platform/agentHost/node/agentService.ts#L12455-L12485), [12603–12620](https://github.com/microsoft/vscode/blob/53ab3ae2e4eb7bceaf797a7e4d05bd8c7a5c203d/src/vs/platform/agentHost/node/agentService.ts#L12603-L12620)). Separately, per-chat queue draining waits for active turns/steering handoffs, blocks behind resumable errors, prioritizes steering and dispatches a turn-start action before provider startup ([queueDrainContribution.ts:249–310](https://github.com/microsoft/vscode/blob/53ab3ae2e4eb7bceaf797a7e4d05bd8c7a5c203d/src/vs/platform/agentHost/node/chatContributions/queueDrain/queueDrainContribution.ts#L249-L310)). **Limit:** per-client preparation ordering is not a global transaction across clients or providers; the queue primitive alone is not persistent execution.

2. **Live projections and durable projection synchronization are distinct.** Chat actions update in-memory state through a reducer; emission increments `serverSeq` ([agentHostStateManager.ts:2942–2971](https://github.com/microsoft/vscode/blob/53ab3ae2e4eb7bceaf797a7e4d05bd8c7a5c203d/src/vs/platform/agentHost/node/agentHostStateManager.ts#L2942-L2971), [3079–3091](https://github.com/microsoft/vscode/blob/53ab3ae2e4eb7bceaf797a7e4d05bd8c7a5c203d/src/vs/platform/agentHost/node/agentHostStateManager.ts#L3079-L3091)). A separate SQLite transaction writes session metadata and a pending catalog-sync snapshot together, rejects stale/conflicting revisions and recognizes exact replay ([sessionDatabase.ts:1418–1464](https://github.com/microsoft/vscode/blob/53ab3ae2e4eb7bceaf797a7e4d05bd8c7a5c203d/src/vs/platform/agentHost/node/sessionDatabase.ts#L1418-L1464)). Catalog synchronization acknowledges the receipt afterward, leaving failed acknowledgements pending ([agentHostCatalogSyncService.ts:537–558](https://github.com/microsoft/vscode/blob/53ab3ae2e4eb7bceaf797a7e4d05bd8c7a5c203d/src/vs/platform/agentHost/node/agentHostCatalogSyncService.ts#L537-L558)). **Limit:** this is a targeted catalog outbox. The inspected reducer/emission path does not itself persist every action before publication; that is not a repository-wide claim that VS Code lacks other event persistence.

3. **Multi-client reconnect uses bounded, client-specific replay or fresh snapshots.** Replay eligibility requires a recent cursor and a baseline for each requested channel. Restored subscriptions activate together, then the server returns projected actions or refreshed snapshots ([protocolServerHandler.ts:1373–1380](https://github.com/microsoft/vscode/blob/53ab3ae2e4eb7bceaf797a7e4d05bd8c7a5c203d/src/vs/platform/agentHost/node/protocolServerHandler.ts#L1373-L1380), [1542–1579](https://github.com/microsoft/vscode/blob/53ab3ae2e4eb7bceaf797a7e4d05bd8c7a5c203d/src/vs/platform/agentHost/node/protocolServerHandler.ts#L1542-L1579)). Broadcast retains envelopes in a bounded in-memory array ([4202–4220](https://github.com/microsoft/vscode/blob/53ab3ae2e4eb7bceaf797a7e4d05bd8c7a5c203d/src/vs/platform/agentHost/node/protocolServerHandler.ts#L4202-L4220)). The client resends pending optimistic actions, deduplicates them against its reconnect outbox by `clientSeq`, then drains queued messages ([agentHostProtocolClient.ts:1733–1771](https://github.com/microsoft/vscode/blob/53ab3ae2e4eb7bceaf797a7e4d05bd8c7a5c203d/src/vs/platform/agentHost/browser/agentHostProtocolClient.ts#L1733-L1771)). **Limit:** an in-memory replay window is not durable event history; local resend deduplication does not establish exactly-once provider execution after host loss.

4. **Cancellation targets execution identity; disconnection has separate cleanup.** Before abort side effects, the service checks that cancellation targets the currently active turn ([agentService.ts:13526–13534](https://github.com/microsoft/vscode/blob/53ab3ae2e4eb7bceaf797a7e4d05bd8c7a5c203d/src/vs/platform/agentHost/node/agentService.ts#L13526-L13534)). The Codex adapter sends `turn/interrupt` with thread/turn IDs and logs request failures ([codexAgent.ts:6841–6870](https://github.com/microsoft/vscode/blob/53ab3ae2e4eb7bceaf797a7e4d05bd8c7a5c203d/src/vs/platform/agentHost/node/codex/codexAgent.ts#L6841-L6870)). Disconnected-client tool ownership instead gets a grace timer before release/failure handling ([protocolServerHandler.ts:1713–1724](https://github.com/microsoft/vscode/blob/53ab3ae2e4eb7bceaf797a7e4d05bd8c7a5c203d/src/vs/platform/agentHost/node/protocolServerHandler.ts#L1713-L1724)). **Limit:** requesting interrupt does not undo completed external work or prove provider termination.

5. **Provider continuation preserves native identity, with lifecycle guards.** Codex resume shares an in-flight promise, rejects disposed sessions, checks connection identity and sends `thread/resume` for the retained backing thread; a configuration reload can first unsubscribe ([codexAgent.ts:7452–7554](https://github.com/microsoft/vscode/blob/53ab3ae2e4eb7bceaf797a7e4d05bd8c7a5c203d/src/vs/platform/agentHost/node/codex/codexAgent.ts#L7452-L7554)). **Limit:** these adapter mechanics do not verify the provider's transcript durability, exact context fidelity or recovery of an interrupted tool call.

## Recommendations for escode — inference, not upstream guarantees

- Specify command admission, durable acceptance, provider dispatch and observed completion separately. Effect scopes/locks simplify ownership; durable receipts and replay policy solve different problems.
- Keep a transactional outbox only where a durable state change must trigger recoverable follow-up work. T3 supplies an execution example; VS Code supplies a narrower catalog-projection example. Neither proves that adopting full event sourcing is necessary.
- Treat reconnect as convergence to host state, with explicit cursors, snapshot baselines and bounded replay. Decide command resend safety independently; VS Code's optimistic resend policy is not authority to retry an uncertain escode Send.
- Preserve exact provider/thread/turn identity for Stop and continuation. Distinguish client disconnect, host shutdown, crash recovery, native conversation resume and a newly submitted continuation turn. T3's automatic continuation is a policy reference. The user subsequently selected that policy as an amendment to escode's explicit-restart-action requirement; see the companion architecture proposal.

## Qualification limits

These findings cover the cited paths at the pinned commits, not every provider, subsystem or deployed release. No builds, tests, provider sessions, fault injection, multi-client stress tests or power-loss durability checks were run. SQLite synchronization settings, distributed ownership, end-to-end exactly-once execution and external side-effect rollback were not established. Absence claims are deliberately limited to inspected paths; recommendations require separate product decisions and validation.

## Follow-up: selected restart policy and durability

The user explicitly requested T3's continuation policy and retained WAL NORMAL with incomplete-evidence blocking. T3 defaults `continueThreadsAfterServerUpdate` to true ([settings.ts:1201–1203](https://github.com/pingdotgg/t3code/blob/54c5f25249961a1aa0b61932329092eadbd9d6fc/packages/contracts/src/settings.ts#L1201-L1203)); it supports project-level overrides. Its crash-loop check uses a maximum chain of three within a five-minute window, not one attempt per original user message ([RestartContinuation.ts:34–35](https://github.com/pingdotgg/t3code/blob/54c5f25249961a1aa0b61932329092eadbd9d6fc/apps/server/src/orchestration-v2/RestartContinuation.ts#L34-L35), [233–260](https://github.com/pingdotgg/t3code/blob/54c5f25249961a1aa0b61932329092eadbd9d6fc/apps/server/src/orchestration-v2/RestartContinuation.ts#L233-L260)). T3 also selects WAL NORMAL with checkpoint fullfsync, explicitly noting that power loss may roll back post-checkpoint commits ([Sqlite.ts:25–30](https://github.com/pingdotgg/t3code/blob/54c5f25249961a1aa0b61932329092eadbd9d6fc/apps/server/src/persistence/Sqlite.ts#L25-L30)). This does not establish detection of every lost Stop or approval record.
