# VS Code Explorer reference for escode

Researched **2026-10-29** against `microsoft/vscode` commit **`4ee2f856fed2dea20833a0dbea5c122ae877422e`** ([commit][commit], committed 2026-10-29 15:54:24 UTC). This is a snapshot of `main`, not a claim about a particular stable release. Every VS Code implementation link below uses that SHA; official documentation is supplementary and can change.

Scope: the desktop Files Explorer, especially macOS, as a planning reference for Electron/React/Monaco escode. Findings come from command handlers, tree/model consumers, underlying file/editor services, and selected upstream tests—not configuration declarations alone. VS Code was not built or interactively tested. The escode implications are recommendations/inferences, not accepted requirements. No tracker decisions or application changes accompany this report. No planning map was open when research was delegated; the parent subsequently opened [Specify the IDE-style Files view](https://github.com/ejjsharpe/escode/issues/27) and collected scope decisions on [Define Files view behavior and implementation plan](https://github.com/ejjsharpe/escode/issues/29). Those later decisions supersede the preliminary product questions below.

## Practical reference matrix

### Navigation and presentation

| Interaction | Supported behavior at the pinned commit | Default / optional behavior | Implication for escode |
| --- | --- | --- | --- |
| Expand/collapse | Folder labels/twisties toggle expansion; Alt/Option makes the toggle recursive. Right expands or enters a child; Left collapses or goes to the parent. Children resolve lazily. [Tree gestures][tree-gestures], [tree keys][tree-keys], [model loading][model-loading] | Folder-label expansion is single-click; double-click mode is configurable. Ordinary child folders start collapsed. [Tree defaults][list-defaults], [Explorer tree setup][view-tree] | Keep expansion independent of file selection/opening. Load directories on demand and support keyboard traversal. |
| Collapse all and restoration | The toolbar/command collapses folders. In a multi-root tree, the first invocation can collapse descendants while leaving expanded roots; another collapses roots. Expanded resource identities, focus, selection and scroll position are saved in workspace/machine storage and supplied when rebuilding the tree. [Collapse implementation][collapse], [storage and restore][view-state], [state fields][tree-state] | Restoration is automatic; editor auto-reveal may subsequently expand ancestors. A single-folder workspace hides its root row. [Input setup][view-state], [reveal][view-reveal] | Remember state per current checkout, using stable path identities; decide how reveal interacts with a user's collapsed tree. |
| Open, select, multi-select | File open events delegate preview/pinning/focus to editor services; directories do not open editors. Cmd-click on macOS/Ctrl-click elsewhere adds items; Shift selects ranges. Bulk commands obtain the selection, while rename/create use the focused context. Right-clicking an unselected row first selects that row without opening it. [Open events][view-open], [selection semantics][selection], [context menu][context-menu], [official gestures][ui-docs] | Single click previews; double click pins under normal editor settings. The multi-select modifier can be changed to Alt. [Official preview behavior][ui-docs], [modifier defaults][list-defaults] | Specify selection, focus and active document separately; preserve a multi-selection when its context menu opens. |
| Reveal and paths | Active-file reveal expands ancestors and selects the file. Explicit Reveal in Explorer uses `force` to bypass auto-reveal exclusions. Copy Path/Copy Relative Path handle multiple resources as newline-separated text. Native Reveal in Finder calls `showItemInFolder`. [Reveal command][reveal-command], [path copy][copy-path], [native reveal][native-reveal] | Auto-reveal is on; `node_modules` and `bower_components` are excluded from auto-reveal, not hidden by that setting. It can be off or focus without scrolling. [Defaults][reveal-defaults], [consumer][service-select] | Provide explicit reveal and path copying. Finder belongs behind the Electron host bridge. Separate reveal preferences from visibility filters. |
| Find/filter | Explorer Find supports highlight/filter and fuzzy/contiguous matching. Its file-search provider can find files inside unexpanded directories, creates temporary result nodes, and restores prior tree state when filtering ends. Searches combine `files.exclude` and `search.exclude`; `.gitignore` treatment follows `explorer.excludeGitIgnore`. Results can be capped with a warning. [Find sessions][find-sessions], [query construction][find-query], [exclude merge][search-excludes] | Highlight and fuzzy matching are the defaults. Find opens with Cmd+Option+F on macOS/Ctrl+Alt+F elsewhere. [Defaults][find-defaults], [binding][find-key] | Choose whether v1 filters only loaded rows or searches the checkout. They have different cost, exclusion and state-restoration requirements. |
| Excluded versus ignored | `FilesFilter` evaluates `files.exclude` globs, including sibling-dependent rules. Optional `.gitignore` parsing builds directory-scoped ignore rules and reacts to changes. A visible editor and its ancestor path can remain shown despite exclusion. [Filter implementation][filter] | Common metadata is hidden (`.git`, `.svn`, `.hg`, `.jj`, `.DS_Store`, `Thumbs.db`); ordinary dotfiles are not universally hidden. Git-ignored files remain visible unless `explorer.excludeGitIgnore=true`. [Visibility defaults][visibility-defaults], [ignore default][nest-defaults], [ignore consumer][filter] | Do not use Git's tracked-file list as the explorer listing. Treat hiding, Git status, and watcher exclusions as separate policies. |
| Sorting and compact folders | The sorter implements folders-first/name, mixed, files-first, extension, modified, and folders/nests/files modes, plus reverse and case-order options. Compact folders combine single-child directory chains and retain navigation/operation targets for individual segments. [Sorter][sorter], [compact navigation][compact], [compression rules][compression] | Folders-first/name sorting and compact folders are on; reverse is off. Compression is disabled in screen-reader-optimized mode. [Defaults][presentation-defaults], [tree setup][view-tree] | A simple folders-first tree is a useful baseline. Compression adds focus, accessibility, rename and drop-target complexity. |
| File nesting | Pattern-based related-file nesting is separate from compact directories. Collapsed nests include nested files in bulk copy/cut/delete and drag operations; expanded nests permit individual selections. [Model consumer][model-loading], [operation context][nested-context], [drag group][drag-group] | Nesting is off. If enabled, nests expand by default; both are configurable. [Defaults][nest-defaults], [consumer][view-tree] | Defer nesting unless group operation semantics are explicitly wanted. |
| Git decorations | The Git extension supplies status decorations from index, working tree, untracked and merge groups; resource badges/colors can propagate to parents. A separate ignored-file provider uses Git ignore checks. Explorer labels consume the decorations service. [Git status provider][git-decorations], [propagation][git-propagation], [ignored provider][git-ignore], [label consumer][labels] | Git status decorations and Explorer colors/badges default on. The ignore provider is registered separately from the status-decoration enable switch. [Git enablement][git-enablement], [Git default][git-default], [Explorer defaults][presentation-defaults] | Feed decoration data from checkout-specific Git status; do not derive Git state from the tree or equate “ignored” with “hidden.” |

### Creation and filesystem changes

| Interaction | Supported behavior at the pinned commit | Default / optional behavior | Implication for escode |
| --- | --- | --- | --- |
| New file/folder | Toolbar and folder-context actions insert an inline placeholder at the chosen folder (or focused file's parent). File creation opens a pinned editor; folder creation selects the result. Relative separators permit nested creation; a trailing `/` requests a folder. [Creation handler][create], [toolbar][toolbar] | No-folder New File falls back to an untitled editor; New Folder requires a workspace. Validation rejects empty/invalid names and known collisions. [Validation][validate], [creation][create] | Define the destination visibly; retain the entered name on failure and offer retry. Creation must validate again at the filesystem boundary. |
| Inline rename | Renames one focused item through a resource move. Filename stem is initially selected, leaving the extension; F2 cycles stem/all/extension selection. Enter commits, Escape cancels; moving DOM focus away commits valid input. Losing window focus alone keeps editing. [Rename handler][rename], [input rendering][rename-input], [input lifecycle][inline-input] | File/folder roots are excluded from rename menu/keybinding. Errors block acceptance; warnings such as whitespace do not. Relative separators can turn rename into a path change. [Menu/key conditions][file-keys], [validation][validate] | Specify blur, Escape, validation and path-separator semantics. A label rename must also migrate document/recovery identities. |
| Delete/trash | Delete uses OS trash when enabled and supported; desktop dispatches to Electron `shell.trashItem`. Permanent delete is separately available. Selection is reduced to distinct parents. Trash failure offers explicit permanent deletion; it does not silently fall back. [Delete handler][delete], [bulk deletion][bulk-delete], [native trash][native-trash] | `files.enableTrash` and `explorer.confirmDelete` default true. The ordinary confirmation can be disabled; provider capabilities affect the action offered. [Defaults][trash-default], [menu conditions][delete-menu] | Put trash in the host service and expose the affected paths. Make permanent deletion and failed-trash fallback explicit. |
| Dirty editors and deletion | A separate unsaved-change warning covers affected files, including descendants of selected folders, even when routine delete confirmation is off. Acceptance authorizes losing changes; this dialog does not offer Save. The working-copy layer soft-reverts before deletion so internal deletion can close editors. External deletion keeps editors open by default; dirty editors are excluded from automatic closing. [Warning][delete], [working-copy deletion][working-delete], [editor handling][editor-delete] | `workbench.editor.closeOnFileDelete=false` applies to external events, not an Explorer delete. [Editor consumer][editor-delete] | Reuse escode's explicit Save/Discard/Cancel and recovery policy deliberately; do not let a tree mutation silently dispose a dirty Monaco model. |
| Copy, duplicate | Copy/paste into the same folder or Option-drag on macOS/Ctrl-drag elsewhere duplicates. Copies normally obtain an available name such as `a copy.txt`, then `a copy 2.txt`. No separate core Explorer Duplicate menu action was found in the reviewed registrations. [Paste target/naming][paste-target], [upstream naming tests][paste-tests], [copy drag][drag-copy], [menus][file-menus] | `incrementalNaming=simple`; `smart` increments numbers; `disabled` asks before replacement. [Defaults][naming-default], [consumer][paste-target] | Decide on a deterministic duplicate naming rule and perform collision checks in the host, not just against loaded rows. |
| Cut/paste and conflicts | Cut marks a resource selection; paste moves it into the focused folder or file's parent. Descendant destinations are rejected. Under default naming, an existing move target raises an error rather than opening the drag-move replacement dialog; an upstream test asserts that error path. With incremental naming disabled, target selection asks about replacement. Cut state clears after an attempted move. [Paste implementation][paste], [conflict test][paste-tests] | Copy and cut use Cmd/Ctrl+C/X/V. Escape cancels the visual cut state. Native-file paste has an additional confirmation enabled by default. [Keys][file-keys], [native paste gate][native-paste] | Specify move collision handling independently of duplicate naming; report partial success/failure and reset clipboard state consistently. |
| Drag/drop | Internal drag moves by default; Option on macOS/Ctrl elsewhere copies. Moving prompts by default; copying does not use that move prompt. Targets reject self/descendant and same-parent moves; folders can auto-expand on hover. Multi-selection drops de-duplicate parents. Move collisions offer replacement; copy uses duplicate naming. [Target checks][drag-targets], [move/group handling][drag-group], [conflict handling][drag-copy] | Internal drag can be disabled; `confirmDragAndDrop=true`. [Defaults][drag-defaults], [consumer][drag-group] | Show the destination and operation before drop, especially for compressed paths. Keep keyboard move alternatives available. |
| External drop/paste | Native file drops copy into the checkout and ask about name collisions. Folder drops can offer copy versus adding a workspace root. A single imported file may auto-open. Native paste also supports disk paths or supplied file data. [Import path][external-import], [paste data][paste] | `autoOpenDroppedFile=true`; native-paste confirmation is separately configurable. [Defaults][naming-default], [native paste gate][native-paste] | Choose a narrow v1 scope for importing external items; adding a workspace root is a separate product capability. |
| Dirty buffers during move/copy | Text-file model management snapshots dirty source contents, calculates descendant targets for folder operations, and restores models at destination URIs after move/copy. Editor move handling replaces editor identities while retaining group placement/pinning. Destination working copies can be soft-reverted during overwrite. [Text model migration][text-migration], [working-copy operations][working-move], [editor rebinding][editor-move] | Moving a dirty source is not an implicit Save. Copy can leave the target model dirty over copied disk contents. This is distinct from promising recovery of a dirty destination being overwritten. | Coordinate disk operations, Monaco models, save baselines, selections and recovery drafts. Choose a protective overwrite policy for dirty destinations. |
| Undo and batch operations | File edits pass through bulk-edit/working-copy services. Undo stores eligible deleted file contents, capped here at **5,000,000 bytes**; deleted directory contents are not captured for restoration. Move/copy groups validate before executing individual filesystem calls in loops; they are not a cross-process transaction. [Delete size limit][delete], [bulk edits][bulk-delete], [working-copy loops][working-move], [undo dispatch][undo] | Explorer undo is enabled; default undo confirmation covers destructive operations. [Defaults][undo-defaults], [command consumers][undo-commands] | Do not promise full folder restoration or all-or-nothing batches. Specify what Undo, trash and partial-failure recovery each guarantee. |
| Watch and refresh | Workspace watchers recursively watch roots with their own include/exclude rules. Explorer applies internal-operation events, coalesces external changes for 500 ms, defers disruptive refresh during inline editing, and refreshes on window focus to compensate for missed events. Manual Refresh invalidates cached children; temporary Find results inhibit refresh. [Workspace watcher][watcher], [event reconciliation][service-events], [refresh][service-select], [toolbar command][refresh-command] | Watching and focus refresh are built in; watcher exclusions are independent of visibility exclusions. [Watcher consumer][watcher] | Separate tree freshness from dirty-buffer/save-conflict handling. Provide manual refresh and error states; scope subscriptions to each checkout. |

## Rename/move is separate from import refactoring

The Explorer rename handler issues a `ResourceFileEdit(oldURI, newURI)`; bulk editing maps that to the working-copy move service. That path change and its dirty-buffer migration do not require a language service. [Rename][rename], [bulk move][bulk-move], [working-copy move][working-move]

JS/TS import updates belong to the bundled TypeScript extension: it listens to **`workspace.onDidRenameFiles`**, asks tsserver for **`getEditsForFileRename`**, and applies a **separate refactoring workspace edit**. The default is **prompt**; `always` and `never` are options (`js/ts.updateImportsOnFileMove.enabled`, with legacy language-specific fallbacks). A declined import update does not undo the completed filesystem move. Other languages require their own support. [Extension implementation][import-refactor], [official documentation][ts-docs]

For escode, supporting file/folder rename must not imply “updates imports.” That would require a separately specified language-service integration, review/confirmation behavior, workspace edits and error/undo coordination.

## Reuse and architecture boundary

- **Reference behavior rather than importing the whole workbench.** `ExplorerView` constructs a service-injected `WorkbenchCompressibleAsyncDataTree`, renderer, filter, sorter and drag handler. `ExplorerService` coordinates workspace identity, clipboard, editor, file, working-copy, progress, decorations and undo services. This is an internal imperative DOM/workbench composition, not a ready-made React Explorer component. Monaco's standalone extraction begins at editor entry points, not the Explorer. [Tree construction][view-tree], [service dependencies][service-events], [standalone build][standalone]
- **Keep layers explicit.** A React tree can own rows, focus, selection and inline editing; an Electron host boundary can own validated filesystem/trash/watch/native reveal operations; a document layer must coordinate model URIs, unsaved contents and recovery. This is an escode design inference from the separate VS Code tree, working-copy and editor responsibilities above—not a recommendation to reproduce its dependency-injection system.
- **Source license differs from the branded product.** The pinned repository is MIT licensed; reuse of copies/substantial portions requires retaining its copyright and permission notice. Microsoft distributes Visual Studio Code under separate product terms, and third-party components can have separate terms. Record provenance and audit the notices/dependencies of any selected code/assets; the source license alone does not establish permission to redistribute the branded product or every bundled component. [Pinned license][license], [official product license][product-license]

## Questions raised by the reference before the scope interview

1. Which interactions are required now: basic tree/create/rename/delete, or also multi-select, clipboard moves, drag/drop, deep Find, compact folders and file nesting?
2. For deletion or replacement affecting dirty files: Save/Discard/Cancel, block the action, or VS Code's destructive confirmation? How do retained recovery drafts refer to renamed/deleted paths?
3. What is the collision policy for move, duplicate and imported files, including case-only renames and partial batches? Should cut/paste and drag behave consistently despite VS Code's differing paths?
4. Should ignored files show by default, which metadata is hidden, and what are the expectations for large folders, watcher failures, symlinks and permissions? This report does not establish exhaustive platform/filesystem edge-case behavior.
5. Should the active file reveal automatically after checkout/view changes, and which expansion/selection state persists per checkout?
6. Is language-aware import rewriting explicitly outside the initial Explorer work? It is separate from basic rename/move.

Validation still needed after scope selection: interaction checks on macOS for focus/VoiceOver, Finder paste/drop, case-insensitive and case-sensitive volumes, dirty source/destination overwrites, and external changes racing a batch. Source reading establishes supported code paths; it does not establish runtime reliability for all of these combinations.
