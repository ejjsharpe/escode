# Minimum Codex integration for escode

Investigated 28 October 2026 for [Verify the minimum Codex integration](https://github.com/ejjsharpe/escode/issues/2).

Scope: project tabs with Files, Source Control, and Codex Chats. Worktrees and a global agents view are deferred.

## Finding

**Codex app-server exposes the interaction primitives this client needs.** OpenAI directs custom clients needing authentication, history, approvals, and streamed events to app-server. Its TypeScript SDK instead emphasizes task automation, although it can start and resume threads; the Python SDK itself controls app-server. [Official SDK guidance](https://learn.chatgpt.com/docs/codex-sdk)

## Documented surface

| Need | Interface |
| --- | --- |
| Local connection | Default JSONL stdio; `initialize`, then `initialized` |
| Project directory | `thread/start.cwd`; later turns can override it |
| Conversation identity | Retain `thread.id`; `sessionId` can be shared by forks |
| History | `thread/read`, paginated turns/items, `thread/resume` |
| Project chat list | `thread/list.cwd`; explicitly include the `appServer` source |
| Live work | Turn/item events and agent-message deltas |
| Decisions and questions | Server requests scoped by thread/turn, including approvals and user input |
| Stop | `turn/interrupt`, followed by an interrupted completion |
| Authentication | `account/read` and login methods |

These are documented API capabilities, not results from executing Codex. WebSocket transport is experimental; the remote-host section also calls the app-server command experimental. Version-matched schemas can be generated by the installed CLI. [Official app-server documentation](https://learn.chatgpt.com/docs/app-server)

## Smallest candidate boundary

**Inference and recommendation for the foundation discussion:** let the desktop host own a local Codex process and route typed requests/events between it and the UI. The renderer needs project identity, chat identity, activity, and pending requests; it need not own a new agent/tool loop. Start by evaluating stdio rather than introducing a network listener for this local app.

Keep the selected project, Codex thread, turn, and individual pending request associated throughout the UI. A tab switch must not redirect an approval to another conversation. Treat filesystem permissions as a separate choice from working-directory selection: selecting a directory should not be used as evidence of an access boundary.

This is a candidate interface boundary, not a decision about Electron, Tauri, frontend libraries, sandbox settings, or process count.

## Checks still required before relying on runtime behaviour

1. Run two project conversations simultaneously against the selected Codex build; observe routing, completion, and resource behaviour. Listing multiple loaded threads alone is insufficient evidence of scheduling guarantees.
2. Quit or disconnect during streaming, a command, and a pending approval. Then reconnect and verify which work stopped, which output persisted, and which requests remain actionable. Persisted conversation history does not establish background-execution or crash-recovery guarantees.
3. Verify authentication and configuration discovery in the actual desktop launch environment, including unavailable/expired credentials. Do not assume launching the executable reproduces an already open client's context.
4. Regenerate/check protocol types for the build escode actually supports and determine its compatibility policy. The investigation does not select a supported release.

## Handoff

[Choose the desktop foundation](https://github.com/ejjsharpe/escode/issues/4) decides the host and process boundary. [Define project, editing, and chat behaviour](https://github.com/ejjsharpe/escode/issues/5) already covers concurrency, approvals, restart policy, and editing conflicts. No additional decision ticket is needed from this initial investigation.

Method: current official documentation reviewed, including the app-server method descriptions. No agent execution, authentication change, app implementation, concurrency test, or recovery test was performed.
