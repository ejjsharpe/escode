# T3 infrastructure adoption evidence

Research for [Which T3 Code infrastructure can escode adopt as coherent host and client layers?](https://github.com/ejjsharpe/escode/issues/50), within [Establish escode’s Effect host and client foundation](https://github.com/ejjsharpe/escode/issues/49). Inspected 30 October 2026. This is evidence and a recommendation, not an architecture decision or a change to accepted behavior.

## Recommendation

Adapt a **coherent transport foundation**, with the provider protocol package as a separate reusable unit: Effect Codex stdio transport; validated escode RPC contracts; budgeted snapshot/replay/live delivery; scoped client sessions and connection supervision. Keep these pieces together with their tests and explicit persistence/authority interfaces. Adopt the Effect-only algorithms substantially intact where compatible; adapt their contracts and integration. Keep escode’s chat identity, uncertain-send handling, files preservation and shutdown policy authoritative.

Do not adopt T3’s entire server plus client-runtime unchanged. It is a functioning alternative, not merely a pile of helpers, but its complete dependency closure includes orchestration/event persistence, command receipts/outbox, migrations, provider registry and managed installations, project/worktree machinery, auth, server configuration and client state projections. It would replace much of escode’s product model. Conversely, copying only throttling helpers would leave the hardest ordering, reconnect and slow-consumer guarantees unimplemented. The useful extraction boundary lies between these extremes. Evidence: [apps/server/src/orchestration-v2/runtimeLayer.ts](https://github.com/pingdotgg/t3code/blob/305a90dce44b8b7813d951662f13ce8510a3c669/apps/server/src/orchestration-v2/runtimeLayer.ts), [apps/server/src/ws.ts](https://github.com/pingdotgg/t3code/blob/305a90dce44b8b7813d951662f13ce8510a3c669/apps/server/src/ws.ts), [packages/client-runtime/src/state/threads.ts](https://github.com/pingdotgg/t3code/blob/305a90dce44b8b7813d951662f13ce8510a3c669/packages/client-runtime/src/state/threads.ts).

## Baseline constraints and affected seams

escode currently uses Bun 1.4.4/Nx, Electron 45.1.0, React 19.3.1, TypeScript 7.0.2, Vite Plus 1.4.0, Monaco and a bundled C filesystem helper; no Effect runtime dependency. Electron IPC is the local client boundary. Installed Codex minimum is 0.163.0, tested 0.165.0. Each connected chat owns an app-server process. The proposed infrastructure reaches host process management and chat services, preload/IPC validation, renderer connection/state handling, persisted chat/workspace identities, watcher subscriptions and shutdown tests; it must not be treated as a dependency-only edit. [Manifest](https://github.com/ejjsharpe/escode/blob/70347aab4dec182c1f32e1ba2544c52cbba420a5/apps/desktop/package.json), [tools/process management](https://github.com/ejjsharpe/escode/blob/70347aab4dec182c1f32e1ba2544c52cbba420a5/apps/desktop/host/tools.ts), [IPC](https://github.com/ejjsharpe/escode/blob/70347aab4dec182c1f32e1ba2544c52cbba420a5/apps/desktop/host/main.ts), [preload](https://github.com/ejjsharpe/escode/blob/70347aab4dec182c1f32e1ba2544c52cbba420a5/apps/desktop/host/preload.ts).

`SavedChat` persists project/checkout/provider thread, directory object identities, scratch/worktree ownership and reservation, draft and initial-send uncertainty. Codex owns transcript history. T3’s event store is not automatically a replacement for either store. Likewise escode’s durable file-operation intents and recovery drafts protect unsaved content and uncertain filesystem handoffs; a server projection cannot overwrite them merely because it is newer. Current quit stops active work and terminates process groups; a connection scope ending must not silently select a different host or redefine quit. [Chat persistence](https://github.com/ejjsharpe/escode/blob/70347aab4dec182c1f32e1ba2544c52cbba420a5/apps/desktop/host/chat.ts), [chat service](https://github.com/ejjsharpe/escode/blob/70347aab4dec182c1f32e1ba2544c52cbba420a5/apps/desktop/host/chat-service.ts), [file intent state](https://github.com/ejjsharpe/escode/blob/70347aab4dec182c1f32e1ba2544c52cbba420a5/apps/desktop/host/file-operation-state.ts), [accepted semantics](https://github.com/ejjsharpe/escode/blob/70347aab4dec182c1f32e1ba2544c52cbba420a5/GLOSSARY.md).

[packages/effect-codex-app-server/package.json](https://github.com/pingdotgg/t3code/blob/305a90dce44b8b7813d951662f13ce8510a3c669/packages/effect-codex-app-server/package.json).

## 2. LiveStreamBudget / bounded delivery — adopt algorithm as part of stream layer

**Actual paths:** `apps/server/src/orchestration-v2/LiveStreamBudget.ts`; consumers include `ThreadLiveEventCoalescer.ts`, `ShellStream.ts`, `EventSink.ts` and `persistence/OrchestrationEventStore.ts`. It is server source, not an independently published workspace package. Its own closure is Effect plus Node’s global `Buffer.byteLength(JSON.stringify(...))`; browser extraction needs a byte-length equivalent. [apps/server/src/orchestration-v2/LiveStreamBudget.ts](https://github.com/pingdotgg/t3code/blob/305a90dce44b8b7813d951662f13ce8510a3c669/apps/server/src/orchestration-v2/LiveStreamBudget.ts).

Default per-budget retained limits are **1,000 items / 8 MiB serialized payload**. Retain/replace account for queued and delivered-but-unacknowledged items; overflow fails the stream with resume guidance and closes source retention. WeakMap size caching assumes immutable event objects. This bounds serialized retention, not JS heap, concurrent-client total memory, provider queues, database pages or socket buffers. A single oversize entity still fails. [apps/server/src/orchestration-v2/LiveStreamBudget.ts](https://github.com/pingdotgg/t3code/blob/305a90dce44b8b7813d951662f13ce8510a3c669/apps/server/src/orchestration-v2/LiveStreamBudget.ts).

Crucially `deliver` releases in-flight accounting on the **next pull**, relying on RpcServer requesting a new batch only after ACK. An IPC adapter that eagerly drains the stream would defeat the intended bound. `bufferLatestLiveStream` replaces pending full states by key/sequence; the replay/live helper subscribes and starts draining **before** reading the high-water mark, charging the live tail even while a replay read or ACK blocks. Keep these functions, stream scope cleanup, RPC backpressure and resume behavior as one unit. [apps/server/src/orchestration-v2/LiveStreamBudget.ts](https://github.com/pingdotgg/t3code/blob/305a90dce44b8b7813d951662f13ce8510a3c669/apps/server/src/orchestration-v2/LiveStreamBudget.ts), [apps/server/src/orchestration-v2/ShellStream.ts](https://github.com/pingdotgg/t3code/blob/305a90dce44b8b7813d951662f13ce8510a3c669/apps/server/src/orchestration-v2/ShellStream.ts).

**Retain tests:** budget overflow/cleanup, retained in-flight charge, blocked replay/high-water read and subscription release in `LiveStreamBudget.test.ts`; coalescer and bounded transport tests; real RPC transport performance tests. Add escode checks for two clients (one stalled), disconnect during snapshot, oversize event, cancellation, snapshot rehydration without command replay, global budgets under many chats, and editor responsiveness during provider bursts. Limits require measurement; 8 MiB is an upstream default, not an escode acceptance threshold. [apps/server/src/orchestration-v2/LiveStreamBudget.test.ts](https://github.com/pingdotgg/t3code/blob/305a90dce44b8b7813d951662f13ce8510a3c669/apps/server/src/orchestration-v2/LiveStreamBudget.test.ts), [apps/server/src/orchestration-v2/boundedSnapshotTransport.test.ts](https://github.com/pingdotgg/t3code/blob/305a90dce44b8b7813d951662f13ce8510a3c669/apps/server/src/orchestration-v2/boundedSnapshotTransport.test.ts), [apps/server/src/orchestration-v2/ThreadTransportPerformance.test.ts](https://github.com/pingdotgg/t3code/blob/305a90dce44b8b7813d951662f13ce8510a3c669/apps/server/src/orchestration-v2/ThreadTransportPerformance.test.ts).

## 3. Batching/coalescing — adapt two distinct stages

**Provider stage:** `Adapters/ProviderTextDeltaCoalescer.ts` depends only on Effect Duration/Ref/Scope/Semaphore. It accumulates full text per `(turnId,itemId)`, schedules one flush, serializes emissions, supports authoritative final text/empty completion and flush-per-turn. CodexAdapterV2 and ClaudeAdapterV2 use it; Codex adapter tests exercise it (there is no dedicated same-name test file). Buffers retain full text and have no byte budget: throttling is not bounded delivery. Scope cancellation is not a promised final flush. [apps/server/src/orchestration-v2/Adapters/ProviderTextDeltaCoalescer.ts](https://github.com/pingdotgg/t3code/blob/305a90dce44b8b7813d951662f13ce8510a3c669/apps/server/src/orchestration-v2/Adapters/ProviderTextDeltaCoalescer.ts), [apps/server/src/orchestration-v2/Adapters/CodexAdapterV2.test.ts](https://github.com/pingdotgg/t3code/blob/305a90dce44b8b7813d951662f13ce8510a3c669/apps/server/src/orchestration-v2/Adapters/CodexAdapterV2.test.ts).

**Client delivery stage:** `ThreadLiveEventCoalescer.ts` adds contracts’ `OrchestrationV2ThreadStreamItem` and LiveStreamBudget. It uses a **50 ms** window, flushes at **512 pending updates**, coalesces selected running full-entity updates, preserves identity switches, terminal boundaries, sequence position and `synchronized` ordering. It must never concatenate or drop arbitrary deltas/approval requests as if they were whole-state replacements. The contract import is type-only here; copying the whole contracts barrel would still add its compilation/schema surface. [apps/server/src/orchestration-v2/ThreadLiveEventCoalescer.ts](https://github.com/pingdotgg/t3code/blob/305a90dce44b8b7813d951662f13ce8510a3c669/apps/server/src/orchestration-v2/ThreadLiveEventCoalescer.ts).

**Recommendation:** adopt the provider accumulator implementation with an escode adapter and explicit finalization policy; adapt the live coalescer to escode’s full-state event algebra. Keep these stages separate within the coherent stream foundation. Retain final-text, empty completion and turn flush tests, plus survivor-cursor equivalence, identity-switch, completion barrier, timer/cancellation and budget tests. Add interleaved chats, reasoning/assistant items, Stop/error during pending text, terminal snapshot equivalence, permission/input latency and dirty editor responsiveness. No performance win was measured here. [apps/server/src/orchestration-v2/ThreadLiveEventCoalescer.test.ts](https://github.com/pingdotgg/t3code/blob/305a90dce44b8b7813d951662f13ce8510a3c669/apps/server/src/orchestration-v2/ThreadLiveEventCoalescer.test.ts).

## 4. Snapshot/subscription synchronization — adapt complete protocol

**Small helper:** `utils/subscribeBeforeSnapshot.ts` has Effect-only closure. Despite the name, its mutex variant reads snapshot then subscribes **inside the same semaphore**; correctness requires all publishers/state writers use that semaphore. The variant without mutex subscribes first, then reads; overlaps require deduplication. It alone does not provide persistence, byte bounds or disconnected replay. Retain the race tests and document the chosen producer invariant. [apps/server/src/utils/subscribeBeforeSnapshot.ts](https://github.com/pingdotgg/t3code/blob/305a90dce44b8b7813d951662f13ce8510a3c669/apps/server/src/utils/subscribeBeforeSnapshot.ts), [apps/server/src/utils/subscribeBeforeSnapshot.test.ts](https://github.com/pingdotgg/t3code/blob/305a90dce44b8b7813d951662f13ce8510a3c669/apps/server/src/utils/subscribeBeforeSnapshot.test.ts).

**Working end-to-end implementation:** `ws.ts` thread/shell subscriptions → ThreadManagementService/EventSink/OrchestrationEventStore → wire projection, bounded snapshot/history paging → client `state/threads.ts`, `shell.ts`, `boundedThreadSnapshotHttp.ts`, history merge/projection reducers and dynamic RPC subscriptions. `threads-sync.test.ts` is a test file; **`threads-sync.ts` is absent** (implementation is in `threads.ts`). [apps/server/src/ws.ts](https://github.com/pingdotgg/t3code/blob/305a90dce44b8b7813d951662f13ce8510a3c669/apps/server/src/ws.ts), [apps/server/src/persistence/OrchestrationEventStore.ts](https://github.com/pingdotgg/t3code/blob/305a90dce44b8b7813d951662f13ce8510a3c669/apps/server/src/persistence/OrchestrationEventStore.ts), [apps/server/src/orchestration-v2/ThreadStream.ts](https://github.com/pingdotgg/t3code/blob/305a90dce44b8b7813d951662f13ce8510a3c669/apps/server/src/orchestration-v2/ThreadStream.ts), [packages/client-runtime/src/state/threads.ts](https://github.com/pingdotgg/t3code/blob/305a90dce44b8b7813d951662f13ce8510a3c669/packages/client-runtime/src/state/threads.ts), [packages/client-runtime/src/state/shell.ts](https://github.com/pingdotgg/t3code/blob/305a90dce44b8b7813d951662f13ce8510a3c669/packages/client-runtime/src/state/shell.ts), [packages/client-runtime/src/state/threadHistoryMerge.ts](https://github.com/pingdotgg/t3code/blob/305a90dce44b8b7813d951662f13ce8510a3c669/packages/client-runtime/src/state/threadHistoryMerge.ts).

The protocol combines a snapshot sequence, persisted replay, live subscription with overlap filtering, synchronized marker and optional bounded/compact/deduped representations. Too-large replay or an invalid/ahead cursor falls back to snapshot. Client state only resumes from a synchronized projection owned by its scope; snapshot/history reducers must understand partial history rather than treating absent rows as deleted. Snapshot HTTP, RPC and reducer versions must agree. This is materially more than “fetch then listen.” [apps/server/src/ws.ts](https://github.com/pingdotgg/t3code/blob/305a90dce44b8b7813d951662f13ce8510a3c669/apps/server/src/ws.ts), [packages/client-runtime/src/state/threads.ts](https://github.com/pingdotgg/t3code/blob/305a90dce44b8b7813d951662f13ce8510a3c669/packages/client-runtime/src/state/threads.ts), [packages/client-runtime/src/state/boundedThreadSnapshotHttp.ts](https://github.com/pingdotgg/t3code/blob/305a90dce44b8b7813d951662f13ce8510a3c669/packages/client-runtime/src/state/boundedThreadSnapshotHttp.ts), [packages/shared/src/orchestrationV2BoundedSnapshot.ts](https://github.com/pingdotgg/t3code/blob/305a90dce44b8b7813d951662f13ce8510a3c669/packages/shared/src/orchestrationV2BoundedSnapshot.ts).

**Persistence/retention:** T3 has a SQLite event/projection/command-receipt system and maintenance that compacts superseded events and deletes eligible receipts, retaining creation anchors. Neither replay nor deduplication is an infinite-history guarantee. Importing that protocol unchanged imports its projection schema, migrations and receipt policy. escode currently lacks this durable event log and retains provider-owned history; it must choose a compatible snapshot/replay source rather than pretend Codex history is T3’s application log. Retention duration and command retry policy remain design work in the existing protocol ticket. [apps/server/src/orchestration-v2/ProjectionMaintenance.ts](https://github.com/pingdotgg/t3code/blob/305a90dce44b8b7813d951662f13ce8510a3c669/apps/server/src/orchestration-v2/ProjectionMaintenance.ts), [apps/server/src/orchestration-v2/CommandReceiptStore.ts](https://github.com/pingdotgg/t3code/blob/305a90dce44b8b7813d951662f13ce8510a3c669/apps/server/src/orchestration-v2/CommandReceiptStore.ts), [apps/server/src/persistence/OrchestrationCommandReceipts.ts](https://github.com/pingdotgg/t3code/blob/305a90dce44b8b7813d951662f13ce8510a3c669/apps/server/src/persistence/OrchestrationCommandReceipts.ts).

**Retain tests:** ws subscription race/resume tests, boundedSnapshotTransport, ThreadStream, ShellStream, history paging and WireProjection, client threads-sync/shell-sync/history merge and bounded HTTP tests. ### B. Extract the coherent foundation (recommended)

Use an independently tracked Codex protocol package and an escode host/client transport layer. The latter carries contracts + session/supervisor + budgeted snapshot/live stream + explicit persistence/authority adapters as a unit. Retain current host services behind adapters until behavioral parity is demonstrated. Avoid inventing a generic configurable provider/host framework.

Small extraction dependency floor:

- Effect 4.0.5 itself has no npm runtime dependencies in its published metadata. Budget, text coalescer and mutex snapshot helper add no third-party packages beyond Effect; budget also assumes Node Buffer. Codex package adds generated protocol code and a supplied process service, not a database/native addon.
- Node service provisioning adds `@effect/platform-node 4.0.5` → platform-node-shared and undici; shared → ws and @types/ws. Registry peers: Effect `^4.0.5`; platform-node also declares a redis `>=5 <7` peer with no optional peer metadata in that registry response; ws declares optional bufferutil/utf-8-validate acceleration peers. This is an install-resolution cost even when escode does not use Redis. Existing T3 overrides resolve ws **8.22.0**, undici **8.11.2**, @types/ws **8.18.2**. Client HTTP/socket implementations can instead be provided by browser/platform services; Node modules must remain outside browser bundles. [Effect metadata](https://registry.npmjs.org/effect/4.0.5), [Node metadata](https://registry.npmjs.org/@effect%2fplatform-node/4.0.5), [shared Node metadata](https://registry.npmjs.org/@effect%2fplatform-node-shared/4.0.5), [ws metadata](https://registry.npmjs.org/ws/8.22.0).
- Auth adds JOSE **6.2.2** (no runtime dependencies in registry metadata), cryptographic/file-store services and a chosen repository. T3 repository implementation adds Node SQLite/worker threads and Effect SQL, not a magic portable storage API. Unchanged client routing/auth adds T3 contracts/shared; rewrite those interfaces deliberately to prevent importing the rest of shared/provider state. [JOSE metadata](https://registry.npmjs.org/jose/6.2.2), [apps/server/src/persistence/AuthPairingLinks.ts](https://github.com/pingdotgg/t3code/blob/305a90dce44b8b7813d951662f13ce8510a3c669/apps/server/src/persistence/AuthPairingLinks.ts), [packages/client-runtime/src/connection/resolver.ts](https://github.com/pingdotgg/t3code/blob/305a90dce44b8b7813d951662f13ce8510a3c669/packages/client-runtime/src/connection/resolver.ts).

Package metadata plus traced imports establish these source boundaries; an exact production bundle/native/optional dependency inventory cannot be certified before the extraction entry points, runtime and adapters are chosen. That is an explicit factual limit, not a claim that a whole workspace’s transitive dependencies disappear through tree shaking. Use the pin lockfile as reproduction evidence; regenerate a smaller dependency/notice inventory for the chosen slice rather than inheriting every T3 dependency.

### C. Retain only small helpers

Lowest source footprint: provider coalescer, budget, snapshot helper. It preserves current product code but leaves connection/session ownership, durable replay, command uncertainty, identity and auth integration to escode. Suitable only if the subsequent design demonstrates a materially simpler equivalent protocol with the same checks. It does not alone satisfy the map’s host/client direction or early non-chat path. Prefer B unless compatibility research disproves its seams.
