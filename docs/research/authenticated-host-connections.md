# Authenticated host connections: authority and compatibility

Research for [authenticated host connections](https://github.com/ejjsharpe/escode/issues/56), under [the Effect foundation map](https://github.com/ejjsharpe/escode/issues/49). Inspected 30 October 2026. Engineering recommendations below are proposed specification input, not implemented security, agreed terminology or new product trust policy.

## Recommendation and evidence boundary

Use an authenticated, host-bound WebSocket RPC connection with separately versioned application contracts, explicit feature capabilities, host-side authorization on every operation, and host-owned work independent of socket lifetime. Initially expose only the bundled host on literal loopback, bootstrapped through the existing sender-validated Electron bridge. Adapt T3's session/supervision and authorization structure; retain escode's approved-project, exact-directory, native-reference, recovery and uncertain-send authority. Future pairing and revocation should reuse a coherent security subsystem rather than isolated token helpers, but must remain unreachable in the first slice.

The [authoritative lifecycle amendment](https://github.com/ejjsharpe/escode/issues/53#issuecomment-6520435690) overrides upstream defaults: last macOS window closure retains host/work/edits; explicit Quit has preservation and active-work confirmation; link loss neither stops work nor answers requests; host restart never automatically resumes or replays a turn. Remote shutdown needs separate host-management authority and affected-work confirmation. Socket authorization is not that permission.

Read README, GLOSSARY, tracker conventions, full map/ticket and prerequisite resolutions [50](https://github.com/ejjsharpe/escode/issues/50#issuecomment-6519735730), [51](https://github.com/ejjsharpe/escode/issues/51#issuecomment-6519718673), [52](https://github.com/ejjsharpe/escode/issues/52#issuecomment-6519913527), [54](https://github.com/ejjsharpe/escode/issues/54#issuecomment-6520101829), and the full lifecycle discussion. No recursive delegation. No issue/map edits, application edits, dependency installation or PR.

## Observed authority and upstream fit

**E facts.** [main.ts](https://github.com/ejjsharpe/escode/blob/a2752152a8a32db7477f99178ef89c9e9744c772/apps/desktop/host/main.ts) validates sender webContents, main frame and exact document URL, uses sandbox/context isolation with Node disabled, denies permission requests/navigation/popups, and owns substantial authorization outside ChatService. It holds approved project objects and generations, verifies Git project/checkout relationships, checks mutation ownership around asynchronous preparation and protects persisted application state. Import capture is a distinct isolated-preload channel, not an arbitrary renderer path grant. Its native import tokens expire after 60 seconds; captured references are cleaned on navigation, renderer loss and window closure. File clipboard/drag state includes captured source identities.

[Project](https://github.com/ejjsharpe/escode/blob/a2752152a8a32db7477f99178ef89c9e9744c772/apps/desktop/host/project.ts) checks canonical roots, device/inode and repository identity, including checkout discovery; [filesystem.c](https://github.com/ejjsharpe/escode/blob/a2752152a8a32db7477f99178ef89c9e9744c772/apps/desktop/host/filesystem.c) uses descriptor-relative operations with `O_NOFOLLOW_ANY`, `O_RESOLVE_BENEATH`, identity reinspection and exclusive/no-follow rename flags. Do not replace these with lexical prefix checks or generic Node path operations. This does not establish immunity to all filesystem races: preserve the accepted check-before-save/removal guarantees rather than promising transactional external-process exclusion.

[ChatService](https://github.com/ejjsharpe/escode/blob/a2752152a8a32db7477f99178ef89c9e9744c772/apps/desktop/host/chat-service.ts) retains connection epochs and opaque live-request tokens mapped to provider wire IDs. Answer checks saved chat, connected session, pending token and turn before validating response/context and responding; consumed tokens are removed. Stop resolves the saved chat and active thread/turn without requiring an available checkout. [Chats](https://github.com/ejjsharpe/escode/blob/a2752152a8a32db7477f99178ef89c9e9744c772/apps/desktop/host/chat.ts) owns persisted context identities, scratch/worktree records and first-send uncertainty. The WebSocket migration must move all relevant main-process checks into host services, not expose ChatService alone.

**T facts.** [Environment authentication](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/docs/internals/environment-auth.md), [EnvironmentAuth](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/apps/server/src/auth/EnvironmentAuth.ts), [SessionStore](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/apps/server/src/auth/SessionStore.ts) and [RPC authorization](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/apps/server/src/auth/RpcAuthorization.ts) form a coherent reference: pairing grants narrow into scoped sessions, browser cookies/bearer/DPoP adapt that model, each RPC requires a scope, session revocation invalidates open connections. The [socket handler](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/apps/server/src/ws.ts) races socket handling against session invalidation, with connected/disconnected accounting. This does not roll back already admitted commands or external effects.

T's `filesystem:read` intentionally permits account-readable absolute files outside projects. Its documentation says terminal access/full-access agent execution can mint administrative sessions through the server account. Consequently a narrow-looking RPC permission is not an OS sandbox against a client allowed arbitrary execution. escode must preserve root authorization without claiming containment of full-access provider processes.

T's [auth policy](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/apps/server/src/auth/EnvironmentAuthPolicy.ts) distinguishes desktop local, browser loopback and remote-reachable modes. [Desktop bootstrap](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/apps/desktop/src/backend/DesktopLocalEnvironmentAuth.ts) obtains a bearer session using launcher-provided credentials, caches it in memory and serializes exchange. Its reusable bootstrap replaces prior desktop sessions transactionally. These are patterns to adapt; do not copy T3 constants, default grants, dev credential or state directory into escode.

## Machine binding, persistence and offline behavior (recommendation)

Persist a random installation identity on the execution host, independent of label, hostname, IP, URL, Git remote and socket port. Separately authenticate the host through the trusted local launcher now and a verified pairing/key binding later. A UUID reported by an untrusted endpoint proves nothing. T's [ServerEnvironment](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/apps/server/src/environment/ServerEnvironment.ts) is useful persistence/descriptor evidence; it is not alone cryptographic identity verification.

Bind every saved chat, draft execution context, provider thread association, worktree reservation, scratch folder, recovery draft and file-operation journal to its owning host. Namespace client storage and in-memory maps by host identity plus resource kind and opaque object ID. Directory/buffer keys additionally need the host's captured directory identity and relative file identity; repository URLs and equal absolute paths across machines never deduplicate them. Scope cursors/snapshots by host plus durable history generation, and pending callbacks by host, provider-session generation and request token. Credentials require a separate connection/trust-binding key; neither token nor endpoint is a resource cache key. Cache isolation includes errors, selection/view memory, permissions and capabilities, not only chat content.

Each command carries its intended host/resource context and a command identity; the authenticated connection selects the actual host. The host rejects a mismatch before lookup or mutation. Never accept an asserted host ID as permission to proxy. Late results apply only to their captured host/resource/generation, even after navigation or connection replacement. Two endpoints for the same verified host may share state only after verification, never on matching labels.

Legacy local records get the bundled host identity through one explicit migration owned by that host. Preserve provider IDs, reservations, text, baselines and uncertainty. Do not bind a restored backup silently to the machine currently reading it. A cloned store/key can duplicate identity: detect conflicting identities/connections and fail closed pending explicit restore/rebind procedure. A newly generated identity after state loss cannot acquire old chats just because paths match. Backup restoration versus clone enrollment is a later trust decision; do not auto-fix it with path matching.

Offline: show last known data as stale with owning host and connection error, retain edits/drafts and uncertain outcomes. No queued mutation automatically executes on reconnect; first slice should have no offline mutation outbox. Block reads requiring freshness and new execution/mutations while unavailable. Retry reconnects the original host and synchronizes/reconciles; it does not select local execution, allocate replacement context or resend prompts. Stop remains a target-specific control when the host is reachable even if the directory is missing; while host is unreachable report that interruption is unconfirmed, never claim success. Client loss does not cancel already admitted work. A host incarnation change invalidates live callbacks even if durable chat/provider IDs survive.

## Compatibility policy (recommendation)

Application release, RPC wire revision, per-feature schema revision, storage migration version and provider protocol version are different axes. Effect's schema decoder and WebSocket framing do not negotiate product semantics. The [Effect report](https://github.com/ejjsharpe/escode/blob/0ed01b5fdacdaa722881565ec15f8b357d4962ec/docs/research/effect-runtime-compatibility.md) recommends 4.1.0 while T0 uses 4.0.5; unstable RPC/socket APIs still need a real integration experiment.

T exposes protocol metadata in [environment contracts](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/packages/contracts/src/environment.ts), checks orchestration protocol before socket upgrade (426 on mismatch), and separately displays release skew through [versionSkew](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/apps/web/src/versionSkew.ts). Its [auth contracts](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/packages/contracts/src/auth.ts) retain legacy `scopes` while adding exact `permissions`; empty permissions do not fall back to broad legacy authority. This is concrete evolution evidence, not a universal independent-update guarantee.

Proposed escode rules:

1. Bootstrap authenticates a bounded metadata exchange: expected/verified host identity, server incarnation, app build, supported wire revisions, selected schema/features, grants and limits. Metadata must contain no project inventory before authorization. Select an explicitly supported intersection, not the numerically closest version. Bind the selected revision to the connection; no feature calls before readiness. Reject mismatch with a small stable error envelope and both supported sets, preserving local state.
2. Start with exactly one wire revision. Claim independent updating only for tested pairs; an exact-match first slice is honest and leaves space for later negotiated overlap. Do not promise support for “N minus one” until fixtures and CI cover it. Future compatibility additions require an explicit supported-pair ledger.
3. Capabilities describe implemented operations and their versions/limits, separately from the authenticated grant. Missing, unknown or empty grants authorize nothing. Client feature hiding is convenience; host checks feature support, current grant and object authority each call. Native Trash, watch, import and shutdown capabilities must be explicit. Read-only fallback is allowed only for a negotiated tested read contract, never by ignoring a handshake failure.
4. Add optional response fields only with defined defaults; tolerate unknown non-authoritative metadata. Reject unknown command variants, fields that could change authority, invalid values and unsupported required features. Handle unknown event variants by stopping that projection and requesting a compatible snapshot/error, not silently advancing its cursor. Version changed meanings, required fields, identity rules and mutation semantics. Preserve error categories across supported pairs; never turn an unknown denial into retryable success.
5. Storage migrations are host-only, validated and backed up, with single-writer exclusion and explicit minimum-reader/writer versions. Clients do not migrate host stores. Upgrade drains/reconciles operations and saves durable state; replacing host process invalidates live generations and requires explicit action before another turn. Capability reduction invalidates affected cached actions.
6. Downgrade must refuse newer storage before opening it for writes, or use a separately tested backward path. Isolate new stores from legacy binaries that do not honor new locks/version checks; do not let an old app rewrite migrated state. Backup rollback does not undo Git/filesystem/provider effects. Unsupported downgrade preserves records and explains recovery, never silently resets chats/identities. Host upgrade, provider upgrade and client upgrade remain independently checked.

## Threat model and transport/credential model

**Protected assets:** host files and application state, unsaved/recovery text, transcripts, provider credentials, ability to launch processes and perform Git/filesystem mutations, request approvals and machine-management actions. **Relevant adversaries:** malicious web page reaching loopback, compromised renderer, stolen pairing/session/ticket, forged native reference/path, stale or independently updated client, malicious endpoint impersonating an offline host, same-account process and proxy/LAN observer. Full host-account compromise is outside this connection boundary; same-account code may already read secrets/run Codex. That limit cannot justify exposing an unauthenticated socket.

Primary protocol/security evidence inspected by browsing:

- [RFC 6455 §§4, 7, 10](https://datatracker.ietf.org/doc/html/rfc6455): browser Origin participates in the handshake; non-browser clients can supply headers. Masking and the accept challenge provide neither client identity nor application command replay protection. TLS is the transport security mechanism for `wss`.
- [WebSocket constructor](https://developer.mozilla.org/en-US/docs/Web/API/WebSocket/WebSocket): browser API takes URL and subprotocols, without an arbitrary Authorization-header option. Plan an authenticated HTTP ticket exchange rather than requiring impossible browser headers.
- [OWASP WebSocket guidance](https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html): validate Origin, authentication and per-message authority; enforce session invalidation, payload/rate limits and sensitive-data redaction. These controls guide the proposal; this is not an audit certification.
- [Electron security](https://www.electronjs.org/docs/latest/tutorial/security): isolate renderers, narrow bridges and validate IPC senders. [safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage) supplies OS-backed local encryption with platform-specific limits; it is not a general defense against same-account compromise.
- [OAuth security BCP](https://datatracker.ietf.org/doc/html/rfc9700) supplies token audience, refresh/replay and sender-constraining guidance. escode does not become an OAuth implementation simply by borrowing that vocabulary; a remote OAuth/DPoP design needs its own complete validation.

### First local slice

Bind to literal `127.0.0.1` only, an ephemeral selected port, and verify the actual listener address. No `0.0.0.0`, `::`, hostname-based bind, LAN override, proxy, relay, port forwarding or unauthenticated fallback. If IPv6 loopback is later supported, test `::1` explicitly rather than inheriting dual-stack exposure. Keep HTTP routes minimal (bootstrap/ticket, bounded metadata and RPC upgrade); diagnostics, assets and downloads are authority surfaces too.

Generate an unpredictable per-host-run bootstrap secret in trusted main/launcher memory; exchange it through the sender/main-frame/document-validated bridge for a short-lived client session/ticket bound to intended local host and renderer lifecycle. Rotate/revoke bootstrap/session access on appropriate launch/navigation/loss boundaries without stopping host-owned work. Do not put a reusable bootstrap credential in renderer URL, command-line argument, logs, workspace JSON or localStorage. Keep long-lived credentials in main/native secure storage; provide only the minimum short-lived credential needed for the renderer's socket. An in-process host can call the session issuer internally, avoiding an exposed HTTP bootstrap endpoint. If HTTP bootstrap is used, require the secret and constrain origin/host/rate before exchange.

Require a deliberately enumerated Origin for browser-like connections and exact expected Host/port. Never trust client-supplied `X-Forwarded-*` on this direct listener. `file:` renderers can send opaque `null` origins: that string is shared by unrelated documents and grants no identity. A bootstrap-issued credential delivered to the exact authorized frame is mandatory; test actual packaged Electron Origin behavior before selecting a null-origin exception or app scheme. Reject missing Origin for the renderer path; a native adapter needs a separately authenticated path/policy. CORS is not WebSocket authorization. Tighten CSP connect-src to the actual local service without broad network wildcards; preserve all existing navigation and sandbox restrictions.

A one-use, short-lived upgrade ticket should be consumed atomically and bound to route, session and host incarnation; URL query values must be redacted from errors, proxy/access logs and telemetry. A ticket is itself a credential. Bound frame size, schema complexity, concurrent calls, subscriptions, queued bytes, handshake/auth failures and idle time. Rate-limit before expensive decoding/authentication, close malformed/unauthorized connections predictably, and release watches on disconnect. Keep Stop responsive under load.

### Later pairing, transport and revocation

T's pairing/session/ticket chain is the reference, including [PairingGrantStore](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/apps/server/src/auth/PairingGrantStore.ts), [ServerSecretStore](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/apps/server/src/auth/ServerSecretStore.ts), [DPoP](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/apps/server/src/auth/dpop.ts), persistence and HTTP handlers. Dependency cost includes JOSE/crypto, secure storage, transactional grant/session records, expiry/replay tracking, revocation signaling, client key storage, tests and maintenance; the complete T3 server adds much more. Shared client [credentialStore](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/packages/client-runtime/src/connection/credentialStore.ts) is an interface, not proof of encrypted storage. Preserve MIT attribution if extracting code.

T issues five-minute WebSocket tickets; RPC DPoP tickets bind the proof key and consume proof jti, while legacy unbound tickets and bearer media tickets remain supported. Therefore “T3 tickets are all one-use” or “all routes resist token theft” would be false. Its Origin helper accepts missing Origin and checks trusted origins/host/forwarded host for cookie sessions; bearer upgrades intentionally remain independent of page Origin. Reuse these only after explicit escode policy adaptation, not by importing all compatibility exceptions. See [EnvironmentAuth tests](https://github.com/pingdotgg/t3code/blob/32ecd71726fee16f335484c1f95cbce126d461f6/apps/server/src/auth/EnvironmentAuth.test.ts).

Future enrollment needs user-mediated verification of the intended host/device, a short-lived rate-limited one-use pairing grant, no authority escalation during exchange, a stable host trust binding, and individually revocable device sessions. Client labels/device metadata are display data, never authority. Store server verification material and nonrecoverable token digests where appropriate; keep required signing/encryption keys in protected host storage and client private keys in platform secure storage. Provider credentials remain on the execution host and never substitute for client login. Do not send Codex account tokens to a phone/client or reuse them as escode bearer tokens.

For LAN and internet require authenticated encrypted transport (`https`/`wss` with validated certificates, or a separately authenticated encrypted tunnel); plain LAN HTTP is not safe. A relay login authenticates the relay, not the execution host. A tunnel does not authorize project access. Certificate/key changes must not silently reset trust. Proxy headers require a trusted-proxy deployment model; never accept caller-asserted forwarding as host verification. Browser cookies need Secure/HttpOnly/SameSite and CSRF/Origin protection; bearer/DPoP needs explicit token audience, lifetime and key/replay validation. No remote security bypass for development convenience.

Revoking a device must deny new commands and updates, invalidate its sessions/tickets and close active links; watches release and cached permissions invalidate. Bound the propagation time and test it. Revocation racing admission must be serialized or rechecked at mutation handoff. Already executed effects cannot be undone. Whether revocation also stops work previously admitted under that device is a product decision, distinct from ordinary link loss. Revoking a pairing link must explicitly define whether derived sessions survive; do not assume token deletion revokes descendants. T exposes separate pairing/session revocation operations, so test the chosen semantics end to end.

## Operation authority and exact identities (recommendation)

Every handler follows: decode/limit → authenticate current session → check feature/grant → resolve host-owned object → validate exact context/generation → recheck at mutation handoff → record outcome → publish only authorized result. Reads, snapshots, history, subscriptions, assets and error details also require authorization. A client schema, signed-in identity or known path is never a project grant. Permission changes apply to subscriptions as well as mutations.

| Operation | Host must resolve and validate |
| --- | --- |
| List/read/watch/status/diff | Own host; approved project and exact checkout; relative path rules and current directory identity; authorized watch lifetime. Git read is not arbitrary shell execution. |
| Save/create/move/copy/Trash/worktree removal | Same authority plus current source/destination identities, conflict baseline, ownership, active work/draft gates, protected state and durable intent/outcome. Recheck after waits; never overwrite on stale client freshness claims. |
| First Send | Saved draft, approved original context, captured directory/project identities, reservation/scratch ownership and provider binding; preserve uncertain preparation/send without allocating substitutes. |
| Further Send/reconnect | Saved chat and provider identity on same host/context; current session generation; reconnect never replays mutation. |
| Approval/input reply | Exact chat, provider session, turn and pending opaque request token; validate reply against captured request; atomically consume once. Provider wire ID alone is insufficient. Stale or replaced session fails even if wire IDs repeat. |
| Stop | Authorized chat and exact active host/session/turn; directory availability is not a precondition. Never target current UI selection after an async wait. |
| Shutdown/update/access management | Separate management authority and required confirmation/affected-host state; ordinary chat control or native desktop access is insufficient. Remote routes remain disabled initially. |

Reject traversal, absolute paths where relative is required, NUL, malformed separators/encoding, symlink ancestors, replaced checkout roots and forged ownership/reservation records. Normalize using host filesystem rules, never client platform assumptions or string-prefix containment. Descriptor-relative helpers and inode/device checks remain behind host adapters; a copied client inode number grants nothing. Inode reuse, same-inode edits, hard links and external races mean object identity is not content freshness or a universal sandbox. Saves still need content baselines; native imports still need protected-state/ancestry checks.

Retain authorization generations across asynchronous work and invalidate them on project approval removal/reopen, directory replacement, context transition, credential revocation and host restart. A durable “approved” path must not approve a new directory occupying it. Explicit reapproval/rebinding must not silently change an already bound chat's context. Check Git repository identity as well as directory identity, while preserving existing no-Git chat execution where the original approved directory remains valid.

### Native capability boundary

The target execution host owns file/Git mutations and its Trash adapter. The client platform owns dialogs, File references, local clipboard, drag/drop, Finder and app-window lifecycle. A picker on machine A never authorizes a path on B. Finder reveal applies only on its own machine; unsupported remote reveal/Trash must report unavailable and never fall back to permanent deletion.

Local native-import/clipboard/drag tokens must be opaque, issuer/host/client-session/context-bound, short-lived and checked against captured live references, source identities and ancestry. Never serialize a file descriptor, trust a renderer-supplied absolute path as a native grant, or accept a token from another host/window/session. Revalidate destination authority and dirty-file conflicts independently. Capability consumption must preserve existing copy/cut retry and per-item outcome semantics rather than blindly making every operation one-shot. Disconnect cleanup cannot erase a durable operation outcome or trigger replay.

Future cross-machine import is an explicit upload/copy protocol with source consent, size/content/recursive validation, target authorization, staged data and honest partial outcomes; it is not native path forwarding. Keep it disabled in the local slice. Browser/phone support must discover absent native capabilities; no invented local path strings to simulate them.

## Product trust questions requiring human participation

Engineering can resolve token mechanics, host checks and migration gates. It cannot silently decide the following permissions or promises:

1. **What does pairing permit?** Owner-equivalent trusted device versus limited control; which projects/history/files may it discover, whether arbitrary agent execution is available, and who can enroll/manage other devices. Full execution can escape a nominal project grant under host-account permissions; explain that before promising limited access.
2. **What does device revocation do to admitted work and derived sessions?** Deny future control versus additionally Stop its work; whether revoking enrollment also revokes all resulting sessions. Ordinary disconnect must still follow the accepted lifecycle amendment.
3. **How is host identity recovered or replaced?** Lost keys, restored backup, cloned machine and legitimate host replacement need explicit user-verified trust/rebinding behavior without silently rerouting existing chats.

Graduate these to separate HITL tickets before remote delivery if the existing multi-client/trust decisions do not already cover them; parent should deduplicate and create/link them.
