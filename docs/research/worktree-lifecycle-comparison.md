# Worktree lifecycle: T3 Code and VS Code

Investigated 29 October 2026 for [Define worktree creation and lifecycle](https://github.com/ejjsharpe/escode/issues/9). This is evidence and a recommended v1 policy, not a user-approved resolution or runtime verification.

## Evidence boundary

T3 Code means the first-party [pingdotgg/t3code repository](https://github.com/pingdotgg/t3code), inspected at commit `a42bdd4e516433a16650b9401ab3c066544ca5cd`. VS Code evidence uses its current official documentation. VS Code has distinct generic Git worktree, editor-chat, and Agents-window flows: their behaviour should not be treated as one uniform feature. Live documentation can describe newer or experimental features; this report does not establish a released-version compatibility floor.

## Comparison

| Decision | T3 Code evidence | VS Code evidence | Recommended escode v1 policy |
|---|---|---|---|
| Starting point | Web new-worktree selector defaults to the repository default branch, falling back to the current branch. A separate start-from-origin setting defaults true and prefers the base branch’s tracked remote branch. [T1, T2] | Agents-window New Worktree asks for a base branch; generic Git flow asks for branch and location. [V1, V2] | Show an explicit base-branch selector, default to the repository default branch with current HEAD fallback, and show the resolved local commit. No implicit fetch/pull. Current HEAD also supports a detached checkout; empty repositories must get an actionable refusal. |
| Dirty original checkout | Core creation creates a branch at the supplied ref then invokes Git worktree add; the inspected core operation does not transfer dirty files or editor buffers. [T3] | Current Agents-window guidance says new worktrees start from committed state. Uncommitted files remain in the original directory except configured include-rule copying. [V3] | Committed state only; leave staged, unstaged, untracked, ignored and unsaved edits where they are. Explain this next to the choice. Defer include/copy rules. |
| Branch names and paths | Naming can later use a static prefix (default `t3/`), a model-generated semantic prefix, or custom instructions. Naming failure preserves the temporary branch; directories retain their original names. Managed directories sit under T3 home or a configured absolute root. Core path is root/repository-name/sanitized-branch. [T3, T4] | Generic worktrees allow user-chosen paths. Agents lifecycle has managed worktrees, but the cited docs do not prescribe their exact path/name contract. [V2, V3] | Generate a unique `escode/<short-id>` branch and a stable app-managed path outside the source checkout. Include repository identity to avoid same-name repo collisions. Display/copy branch and path. Defer AI naming and configurable roots. |
| Discovery and reuse | New thread in this worktree reuses a checkout. Branch selection explicitly reuses an existing worktree when its ref already has a path. [T5, T6] | Separate conversations can share a folder/worktree; isolation must be chosen explicitly. [V4] | Offer current checkout, new worktree, and an explicit way to start a chat in an existing project worktree. Discover with Git metadata; never silently substitute a shared checkout when new creation was requested. Preserve the existing shared-files notice. |
| Retention | Automatic cleanup is off by default. Its policies distinguish activity, settlement, merge state and local-file protection; active sessions and shared worktrees block cleanup. Branch/history survive cleanup. [T4] | Manual archive snapshots uncommitted work into commits before removing a worktree; restore reconstructs it. Failed preservation/removal leaves the folder. Shared worktrees survive while still needed. [V3] | Closing/completing/archiving a chat retains files and branch. No automatic Git commits or background cleanup. This follows T3’s conservative default and escode’s read-only Source Control boundary. |
| Cleanup safety | Default local-change protection includes tracked and untracked files, but can delete ignored files. Stronger policy protects ignored files too. Deleted-thread cleanup waits for sessions and terminals to stop. [T4] | Cleanup asks the user to save open file edits and excludes active/running/waiting sessions. Auto-cleanup is separately configured and conservative about unknown Git state. [V3] | A small manual remove action only for app-created worktrees, with branch retained. Block while any associated agent runs, unsaved buffers exist, or local files cannot be proven safe. Include ignored files in the preservation check; no force-delete option in v1. External Git remains the advanced escape hatch. |
| Missing checkout | T3 automatically recreates missing managed worktrees at turn start; if the branch is gone, inspected recovery can recreate it from the project’s current branch. [T7] | Documented archive restoration recreates retained worktrees; docs do not establish recovery semantics for arbitrary external deletion. [V3] | Preserve chat/drafts and disable writes/runs while missing, as already settled. Retry after restoration; never silently rebuild from another branch. Defer relocation and automatic reconstruction. |
| Creation failures | Core branch creation and checkout are separate operations, so branch creation can succeed before checkout fails. Submodule checkout failure becomes a warning and leaves the worktree available. [T3] | No complete partial-failure transaction contract found in the consulted docs. | Do not start an agent before creation succeeds. Preserve draft prompt, report what remains (branch/path), and permit retry/reuse after revalidation. Clean only conclusively app-owned empty leftovers, never overwrite an occupied path or fall back to current checkout. |
| Bringing work back | T3 has commit/push/PR/merge UI. [T8] | VS Code offers apply/migrate, branch integration, or continuing on a branch. [V5] | Keep integration in external Git/VS Code for v1; expose branch/path and explain commit then merge/cherry-pick. This is a scope choice, not full parity with either reference product. |

## What adopting the references settles—and what it does not

The references support a base selector, isolated committed-state worktrees, explicit reuse, visible branches/paths, protected cleanup, and an integration workflow. They do not yield one identical answer for defaults or archive semantics. For escode, automatic snapshot commits, rich cleanup policies, remote fetching, setup hooks, custom roots, AI naming, relocation, and integrated merge/apply controls would expand the agreed v1 scope. The recommended policy above deliberately defers them. It needs user confirmation before the grilling ticket closes.

No application was launched, no filesystem deletion was exercised, and no upstream test suite was run. Source inspection does not prove runtime safety. In particular, ignored files, linked chats, unsaved editor drafts, concurrent agents and partial checkout failure must be tested during implementation.
