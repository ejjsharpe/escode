# Pi Durable versus escode’s Effect execution architecture

Pi Durable is a credible replacement for substantial agent-loop infrastructure **if escode wants pi to own the agent loop**. It is a less compelling replacement when a task merely wraps a complete external coding agent: then escode retains most of its difficult admission, provider reconciliation, file preservation and client synchronization work. Neither adoption is a drop-in implementation of the accepted execution specification. My conditional recommendation is to retain the Effect-based Execution authority for the current handoff, while considering native pi as a deliberate product/architecture alternative after the narrow probes below.

## Evidence and comparison boundary

This is source research, not implementation or runtime qualification. **Fact** below means observed in pinned documentation, source or test assertions; **inference** means an architectural consequence; **unverified** means an integration property not demonstrated here. Tests cited were inspected, not run. No savings percentage, throughput claim or delivery estimate is inferred from code volume.

The baseline is the completed [execution decision map](https://github.com/ejjsharpe/escode/issues/157) and [implementation handoff](https://github.com/ejjsharpe/escode/issues/160), with normative [execution amendment](https://github.com/ejjsharpe/escode/blob/1dded83331d26ea9e5c2c5e148d48f061f605c8e/docs/specifications/execution-architecture.md) and [ADR 0004](https://github.com/ejjsharpe/escode/blob/1dded83331d26ea9e5c2c5e148d48f061f605c8e/docs/adr/0004-execution-events-and-t3-recovery.md). Those remotely accepted documents take precedence over this checkout’s older main documentation. No open `wayfinder:map` issue was returned. README, GLOSSARY and tracker conventions were read; this report proposes no terminology changes.

Pi is pinned to `8ffea8a1bfdc32523ab056549b26141018c1e700`, independently fetched from upstream, rather than trusting the supplied cache. Its durable package identifies itself as 1.4.0. Effect is pinned to the `effect@4.1.0` tag’s commit `9a91b1926a5fbfaffd302a7a41a94d4d53a1154e`. escode’s manifests and lockfile select 4.1.0; the official npm tarball was downloaded and its workflow/SQL/event source inspected alongside that tag. Its integrity matches the lockfile. This isolated checkout has no root `node_modules/effect`, so this verifies the locked dependency and published artifact, not an installed application’s loaded module. [escode lock](https://github.com/ejjsharpe/escode/blob/181097195a026d48b82758cee841ed8dd326db70/bun.lock), [Effect package](https://github.com/Effect-TS/effect/blob/9a91b1926a5fbfaffd302a7a41a94d4d53a1154e/packages/effect/package.json).

The accepted baseline already permits selective event compaction. It promises rebuilding declared current projections, **not** an everlasting immutable audit log. It retains independent client drafts and file checkpoints, exact native identities, uncertain-effect protection, and WAL NORMAL’s power-loss limitation. Codex app-server is not assumed mandatory in this comparison.

## Three materially different choices

**Native pi loop.** Harness owns conversation submissions, generation, tools, queued inputs, durable phases, retry sleeps, context compaction and task ownership. Pi-ai supplies model access; extensions supply tools and policy. This can retire a considerable amount of bespoke loop machinery, including work escode would otherwise delegate to a provider agent. It also transfers responsibility for agent behavior, permission enforcement and continuation context to pi plus escode’s integration. Provider feature parity does not follow from model access. [Harness concepts and examples](https://github.com/earendil-works/pi/blob/8ffea8a1bfdc32523ab056549b26141018c1e700/packages/durable/README.md#concepts).

**Durable task around a complete external agent.** A custom task checkpoints launch intent, starts/resumes a CLI or app-server session, observes it, and commits outcomes. Pi supplies task persistence, ownership, sleeps, waits and cancellation coordination. The external agent still owns its inner tools, approvals and native history. Pi cannot automatically checkpoint that hidden loop. A process can accept work before the wrapper records acceptance; recovering that gap requires provider-specific reconciliation or visible uncertainty. This is an inference from pi’s phase execution model, not a tested CLI adapter. [Task recovery example](https://github.com/earendil-works/pi/blob/8ffea8a1bfdc32523ab056549b26141018c1e700/packages/durable/test/harness-tasks-recovery.test.ts#L112).

**Effect Execution with realistic reuse.** Keep escode’s product transaction and recovery policy, using existing Effect resource management, RPC/schema facilities, SQL and selected upstream execution patterns. This does not mean writing a generic workflow engine. A short SQL admission transaction and a small classified outbox may fit better than introducing either pi’s document/task model or Effect’s cluster machinery. Conversely, Effect’s durable components deserve evaluation before recreating facilities they already provide.

Pi can also run over a model-facing CLI proxy. That is distinct from wrapping a full external coding agent: a proxy furnishing model completions leaves pi in charge of tools and context. Pi-ai supports custom providers and endpoints, but this investigation did not verify a particular CLI proxy’s fidelity, identity, authentication, cancellation or native-history capabilities. Its Codex Responses adapter is not evidence that it runs the installed Codex agent. [Custom provider documentation](https://github.com/earendil-works/pi/blob/8ffea8a1bfdc32523ab056549b26141018c1e700/packages/ai/README.md), [Codex provider](https://github.com/earendil-works/pi/blob/8ffea8a1bfdc32523ab056549b26141018c1e700/packages/ai/src/providers/openai-codex.ts).

## Atomic admission, authority and transaction composition

**Fact:** pi’s commit can append transcript entries, update documents, create submissions and create tasks together. `submit(tx, draft)` joins the caller’s transaction. SQLite applies storage writes and sequence allocation transactionally, and rollback tests cover their joint rollback. This is meaningful reuse for #160’s receipt/state/follow-up requirement, provided those records all live inside that transaction boundary. [Submission implementation](https://github.com/earendil-works/pi/blob/8ffea8a1bfdc32523ab056549b26141018c1e700/packages/durable/src/harness/submissions.ts#L80), [SQLite commit](https://github.com/earendil-works/pi/blob/8ffea8a1bfdc32523ab056549b26141018c1e700/packages/durable/src/storage/sqlite/storage.ts#L214), [rollback test](https://github.com/earendil-works/pi/blob/8ffea8a1bfdc32523ab056549b26141018c1e700/packages/durable/test/sqlite-storage.test.ts#L366).

**Important mismatch:** request deduplication looks up `(conversationId, requestId)`, rejects a different submission type, then returns the existing submission. It does not compare same-type content, expected revision, authenticated client or full command envelope. Thus a changed prompt under the same request ID is not #160’s required conflict. An escode receipt document/index must bind and compare the exact validated payload and authority before admission, including original retry handling after revisions advance. A digest alone needs a specified canonical encoding or retained payload comparison. [Exact lookup branch](https://github.com/earendil-works/pi/blob/8ffea8a1bfdc32523ab056549b26141018c1e700/packages/durable/src/harness/submissions.ts#L230).

Pi’s trusted in-process API is not escode’s authenticated client boundary. Host/store binding, client permissions, target validation, optimistic entity revisions, one-winner conflicts, receipt access and independent composers remain application work. Do these checks inside the admission authority, rather than an earlier check that can race. Pi’s conversation busy/queue policy also needs mapping to escode’s one foreground turn and separate title lane: automatically queuing or steering an overlapping request is not necessarily the chosen conflict behavior.

Pi serializes mutations within a Session and requires one owning process per storage; it supplies no cross-process ownership lock. escode must fence duplicate hosts. A per-chat SQLite file makes app-wide state/receipt transactions harder; one shared Session makes long commit callbacks affect unrelated chats. Transaction callbacks must contain bounded state work only, never network calls, subprocess waits or nested Session operations. Table reads must precede table writes; one submission admission precedes the transaction’s other table writes. These constraints matter when composing Files and Chats. [Storage ownership](https://github.com/earendil-works/pi/blob/8ffea8a1bfdc32523ab056549b26141018c1e700/packages/durable/README.md#storage), [API footguns](https://github.com/earendil-works/pi/blob/8ffea8a1bfdc32523ab056549b26141018c1e700/packages/durable/docs/spec.md#12-api-footguns).

Putting pi tables in the existing SQLite file is insufficient to share a transaction with escode. Pi’s storage calls its own `db.transaction`; the Node adapter serializes work and issues `BEGIN IMMEDIATE`. A second connection or sequential Effect transaction cannot produce one atomic commit. Options are to represent all jointly committed authority in pi documents/entries/tasks, or deliberately build and qualify a shared transaction/storage integration. The latter costs custom machinery and upgrade exposure. Table prefixes solve namespacing, not transaction composition. [SQLite adapter](https://github.com/earendil-works/pi/blob/8ffea8a1bfdc32523ab056549b26141018c1e700/packages/chord/src/sqlite/node.ts#L145).

## State, facts, projections and retention

Pi separates immutable transcript entries from mutable documents and task records. Documents choose latest-only or rewindable history and explicit fork semantics; live tasks replace current records, while terminal outcomes remain queryable. Durable’s design explicitly excludes a Session-kernel semantic event journal. Therefore reconstructing pi document state from retained bases/deltas is not the same as rebuilding escode’s shared projections from domain facts. [Storage model and non-goals](https://github.com/earendil-works/pi/blob/8ffea8a1bfdc32523ab056549b26141018c1e700/packages/durable/docs/spec.md).

**Inference:** native pi can make its transcript the authoritative agent history, but #160 still needs explicit admission, cancellation, revision, execution and file-operation facts, with causation/schema/sequence rules. Store those as application entries or another transactionally joined journal. A post-commit observer that writes a second journal leaves a crash gap; it cannot establish atomic admission. If escode instead accepts pi current documents as primary authority and abandons independent semantic rebuild, that is a specification change with a reduced repair promise.

Do not infer that retaining transcript entries reconstructs provider-native context for a wrapped CLI. Pi’s own context builder and external agent history have different ownership. Conversely, native pi need not pretend its own transcript is merely a partial observation of an unavailable Codex conversation: #160 should explicitly designate pi’s context authority and define what provider-specific opaque state remains required.

Three kinds of compaction must stay separate:

- Pi model-context compaction summarizes older input and changes the model-visible head; old transcript entries remain stored. Reset also does not erase those entries.
- Pi document checkpointing/reclamation controls bases and deltas according to history/fork policy. Latest-only storage cannot promise every prior state; disabling checkpoint decisions can permit growth.
- escode’s accepted T3 policy removes selected superseded execution/content versions while preserving sufficient current projection coverage. File-checkpoint inactivity expiry is a fourth, independent policy.

Thus “pi already compacts” does not implement #160’s retention settings, outbox cleanup or side-store rebuild acceptance. Nor does it imply a total disk quota, secure deletion or provider-history cleanup. Retained transcript and tool data still need disclosed privacy/size semantics and consistent backup coverage. [Context compaction](https://github.com/earendil-works/pi/blob/8ffea8a1bfdc32523ab056549b26141018c1e700/packages/durable/README.md#compaction), [document state](https://github.com/earendil-works/pi/blob/8ffea8a1bfdc32523ab056549b26141018c1e700/packages/durable/README.md#your-own-state), [accepted retention policy](https://github.com/ejjsharpe/escode/blob/1dded83331d26ea9e5c2c5e148d48f061f605c8e/docs/specifications/execution-architecture.md#t3-retention-and-capacity-policy).

## Durability, progress and failure

Pi’s Node backend uses WAL, `synchronous = NORMAL`, and a configurable WAL auto-checkpoint threshold, default 1,000 pages. This is persistent SQLite, not memory-only execution. It nevertheless shares the accepted risk that OS/power failure can erase recently acknowledged controls. Atomicity and ordinary process recovery do not establish power-loss preservation of Stop or approval records. Matching NORMAL alone does not qualify escode’s full-flush/checkpoint and recovery-copy behavior. [Backend configuration](https://github.com/earendil-works/pi/blob/8ffea8a1bfdc32523ab056549b26141018c1e700/packages/chord/src/sqlite/node.ts#L196).

The README’s opening durability description has a consequential exception. Stream partials/tool output update by default at most every 100 ms; deferred document commits can become visible before storage, with default persistence within approximately 1,000 ms. Only eligible existing latest/initial-fork document changes defer; entries, task changes and other ineligible writes force persistence. A crash can lose displayed progress and an early partial/its usage. Do not drive acknowledged admission, authorization or completed receipts from such progress. Preserve an explicitly ephemeral UI path or select stronger persistence for required facts. [Progress semantics](https://github.com/earendil-works/pi/blob/8ffea8a1bfdc32523ab056549b26141018c1e700/packages/durable/README.md#watching-a-conversation), [deferred writes](https://github.com/earendil-works/pi/blob/8ffea8a1bfdc32523ab056549b26141018c1e700/packages/durable/README.md#your-own-state).

A fatal storage error fails the Session; later calls cannot fix it by retrying the same handle. The inspected tests cover propagation to waits, views and running tasks, reads failing away from the mutation line, unknown commit outcomes, and containment of listener failures. That fail-closed behavior is valuable. It also means emergency Stop cannot depend solely on successfully committing a pi abort after storage failure. escode needs an independent exact-target live-process control path with previously validated authority, bounded lifetime and uncertainty disclosure. Reopening the failed store is recovery, not permission to repeat a launch. [Failure tests](https://github.com/earendil-works/pi/blob/8ffea8a1bfdc32523ab056549b26141018c1e700/packages/durable/test/harness-storage-failure.test.ts).

## Cancellation, unsafe effects and restart policy

Pi has more than a cancellation flag: task ownership/cascades, abort phases, waits and cancellation barriers are built in. Cancelling a caller’s wait does not cancel admitted work. Tests check that the next phase cannot start while the cascade marking it is uncommitted. These align well with host-owned work surviving client loss. [Cancellation barrier tests](https://github.com/earendil-works/pi/blob/8ffea8a1bfdc32523ab056549b26141018c1e700/packages/durable/test/harness-cancellation-barrier.test.ts).

However, close joins invocations; a non-cooperative tool or hook can keep it pending. Pi does not forcibly terminate arbitrary JavaScript extensions. Its Node execution environment does include process-group SIGKILL with PID fallback, so it would be inaccurate to say pi has no process termination support. That helper does not establish ownership of every detached descendant, external CLI session or orphan surviving a host crash. Emergency Stop and Stop-and-Close still require bounded host supervision and exact identity tests. [Close constraints](https://github.com/earendil-works/pi/blob/8ffea8a1bfdc32523ab056549b26141018c1e700/packages/durable/docs/spec.md#12-api-footguns), [process termination](https://github.com/earendil-works/pi/blob/8ffea8a1bfdc32523ab056549b26141018c1e700/packages/durable/src/env/node.ts#L285).

Pi’s built-in tool task records final arguments and replay policy **before** execution. Replay defaults to unsafe; recovery reruns only if both saved and current policies say safe. Otherwise it records an interrupted, possibly partially executed failure. This is a strong reusable safeguard, not blanket at-least-once tool replay. But a custom task phase reruns from its checkpoint: wrapping a non-idempotent CLI launch in an ordinary phase does not inherit the built-in tool’s safety automatically. A result memo cannot close the “effect succeeded, result not persisted” gap. Use an intent/reconcile/outcome protocol or abandon interrupted work and retain uncertainty. `abandonOnRestart` supplies task abandonment, not proof of external termination. [Tool intent and recovery](https://github.com/earendil-works/pi/blob/8ffea8a1bfdc32523ab056549b26141018c1e700/packages/durable/src/harness/tool.ts#L175), [abandonment](https://github.com/earendil-works/pi/blob/8ffea8a1bfdc32523ab056549b26141018c1e700/packages/durable/README.md#tools).

Built-in generation behaves differently: interrupted model requests can be retried, committed partials become aborted entries, deferred responses are polled again, and crash attempts/restart limits bound recurring failure. Close and crash have different accounting. Reopening alone is not synonymous with dispatch, but `resume()`, submitting and waiting can start scheduling. Consequently admission or inspection code must not accidentally start unfinished work before escode recovery guards finish. [Recovery assertions](https://github.com/earendil-works/pi/blob/8ffea8a1bfdc32523ab056549b26141018c1e700/packages/durable/test/harness-generation-recovery.test.ts#L75), [restart policy](https://github.com/earendil-works/pi/blob/8ffea8a1bfdc32523ab056549b26141018c1e700/packages/durable/README.md#failures-and-recovery).

#160 instead requires a **new visible system-origin continuation**, deterministic from the interrupted execution, in the exact saved native conversation. It checks retained Stop, newer work, unresolved approvals, native availability and settings; copies T3’s three-ancestor/five-minute guard; and rechecks before dispatch. Pi’s per-task restart limit is not that policy. Native pi adoption either preserves those product rules above its scheduler or explicitly replaces them with specified pi resume semantics. For an external agent wrapper, retain the no-blind-resend rule. Old approval responses must never become replayable activity results merely because a workflow library can cache them.

## Clients, files and external-agent responsibilities

Pi conversation/document watches capture a revision and deliver updates; slow watches fold changes and can replace accumulated operations with a whole value. These are useful local view primitives. They are not automatically #160’s authenticated remote protocol with store identity, high-water cut, cursor-through watermarks for filtered streams, bounded replay, overflow fallback and original-receipt reconciliation. A watcher may omit intermediate revisions and may carry deferred progress; a reconnect cursor must describe persisted authority, not whichever frame the UI last saw. Chord transport may offer further reuse, but this report does not qualify it against escode’s protocol. [Watch behavior](https://github.com/earendil-works/pi/blob/8ffea8a1bfdc32523ab056549b26141018c1e700/packages/durable/README.md#watching-a-conversation), [buffered-watch limits](https://github.com/earendil-works/pi/blob/8ffea8a1bfdc32523ab056549b26141018c1e700/packages/durable/docs/spec.md#12-api-footguns).

File preservation remains product work in every option. Pi’s read/write/edit/bash tools do not establish escode’s independent dirty buffers, exact checkout/native file identity, save-conflict checks, move/Trash acknowledgements, checkpoints, recovery-copy quarantine or managed-worktree reservations. Agent disk writes and editor recovery must reconcile through the existing rules. A pi transaction cannot atomically commit an operating-system file replacement. Keep operation evidence and uncertain outcomes across that boundary; replacing the task executor must not delete those journals. [Pi tools](https://github.com/earendil-works/pi/blob/8ffea8a1bfdc32523ab056549b26141018c1e700/packages/durable/src/tools/index.ts), [preservation baseline](https://github.com/ejjsharpe/escode/blob/1dded83331d26ea9e5c2c5e148d48f061f605c8e/docs/specifications/execution-architecture.md#independent-clients-and-catch-up).

A CLI/proxy integration must define credential ownership, supported model/options, native thread/turn IDs, acceptance acknowledgements, exact resume/fork/history support, approval requests and replies, process-group lifetime and cancellation. Pi’s persisted `pi.provider` UUID supplies provider session/cache affinity; it is not proof of an external CLI thread identity. Missing native history must remain unavailable rather than reconstructed from normalized output. For native pi, permission hooks must be mandatory at the host boundary: extensions are selected per conversation, and an omitted guard extension does not run. A convenient hook is not an unavoidable sandbox. [Provider identity](https://github.com/earendil-works/pi/blob/8ffea8a1bfdc32523ab056549b26141018c1e700/packages/durable/README.md#persist-and-resume), [guard-selection caveat](https://github.com/earendil-works/pi/blob/8ffea8a1bfdc32523ab056549b26141018c1e700/packages/durable/docs/spec.md#12-api-footguns).

## Effect’s actual reuse surface

Effect 4.1.0 includes `Workflow`, `Activity`, `DurableDeferred` and durable clocks. `WorkflowEngine` includes an in-memory implementation, **but that is not its only engine**. `ClusterWorkflowEngine` represents execution, activities, resumes, interrupts and clock wakeups as persisted cluster messages; `SqlMessageStorage` stores messages/replies and redelivers unprocessed work. Activities provide named result persistence and idempotency-key helpers, not exactly-once external side effects. [Workflow engine](https://github.com/Effect-TS/effect/blob/9a91b1926a5fbfaffd302a7a41a94d4d53a1154e/packages/effect/src/workflow/WorkflowEngine.ts), [cluster engine](https://github.com/Effect-TS/effect/blob/9a91b1926a5fbfaffd302a7a41a94d4d53a1154e/packages/effect/src/cluster/ClusterWorkflowEngine.ts), [SQL messages](https://github.com/Effect-TS/effect/blob/9a91b1926a5fbfaffd302a7a41a94d4d53a1154e/packages/effect/src/cluster/SqlMessageStorage.ts), [activities](https://github.com/Effect-TS/effect/blob/9a91b1926a5fbfaffd302a7a41a94d4d53a1154e/packages/effect/src/workflow/Activity.ts).

SQL facilities include transactional connections, nested savepoint handling and after-commit work; SQLite drivers are separate packages. `EventLog` supplies typed handlers/journals and replication infrastructure, and `SqlEventJournal` provides SQL persistence, sequences and remote checkpoints. Thus “Effect leaves all persistence to us” is false. However, EventLog runs handlers before journal completion and supports a broader replicated model. One must verify transaction participation, avoid external effects in projection handlers, and adopt escode’s particular authority/compaction semantics; installing it does not prove #160’s atomic receipt/event/projection/job transaction. [SQL client](https://github.com/Effect-TS/effect/blob/9a91b1926a5fbfaffd302a7a41a94d4d53a1154e/packages/effect/src/sql/SqlClient.ts), [EventLog](https://github.com/Effect-TS/effect/blob/9a91b1926a5fbfaffd302a7a41a94d4d53a1154e/packages/effect/src/eventlog/EventLog.ts), [SQL journal](https://github.com/Effect-TS/effect/blob/9a91b1926a5fbfaffd302a7a41a94d4d53a1154e/packages/effect/src/eventlog/SqlEventJournal.ts).

**Inference:** the lowest-risk starting point is existing Effect lifetimes/RPC plus the smallest transactional Execution store and classified outbox that satisfy the handoff. Evaluate workflow/cluster only where durable waits/coordination outweigh their additional schema, configuration and recovery model. Evaluate EventLog without importing unnecessary multi-writer replication. These advanced modules are marked unstable in 4.1.0; Effect familiarity does not eliminate their upgrade risk. The choice is selective reuse versus selective reuse, not a finished pi product versus a blank Effect canvas.

## Maintenance, tests, operations and exit costs

Pi’s reuse benefit includes upstream conformance and fault tests: SQLite reopen/rollback/index coverage, cancellation barriers, generation recovery, task recovery, storage failure, fake clocks and a custom-backend conformance suite. These reduce machinery escode must invent. They do not establish packaged Electron compatibility, real CLI uncertainty behavior, exhausted-disk cancellation, cross-client file safety or power-loss durability. Existing escode seam/acceptance checks remain necessary under either runtime. [SQLite tests](https://github.com/earendil-works/pi/blob/8ffea8a1bfdc32523ab056549b26141018c1e700/packages/durable/test/sqlite-storage.test.ts), [backend conformance](https://github.com/earendil-works/pi/blob/8ffea8a1bfdc32523ab056549b26141018c1e700/packages/durable/src/testing/storage-conformance.ts).

The pinned package explicitly warns of experimental APIs changing without notice. It requires Node >=22.19.0 and depends on Chord, pi-ai, pi-codemode, telemetry, photon, diff and TypeBox. Node SQLite availability, worker/image assets and ESM/package exports need packaged verification. Adoption alongside Effect adds two lifetime/cancellation idioms and a bridge; replacing Effect wholesale would exceed this research question and discard existing host reuse. [Package dependencies](https://github.com/earendil-works/pi/blob/8ffea8a1bfdc32523ab056549b26141018c1e700/packages/durable/package.json), [stability warning](https://github.com/earendil-works/pi/blob/8ffea8a1bfdc32523ab056549b26141018c1e700/packages/durable/README.md).

Both upstream roots use MIT licenses; preserve their notices for redistribution/copying. That observation is not a full transitive dependency/license audit. [Pi license](https://github.com/earendil-works/pi/blob/8ffea8a1bfdc32523ab056549b26141018c1e700/LICENSE), [Effect license](https://github.com/Effect-TS/effect/blob/9a91b1926a5fbfaffd302a7a41a94d4d53a1154e/LICENSE).

Operational ownership remains local: storage growth, backups, failed sessions, blocked/missing task definitions, schema upgrades, process cleanup and operator-visible uncertainty. Pin upgrades and review persisted task/document migrations. Pi can block tasks when compatible definitions are unavailable; dropping old extensions is not harmless cleanup. A custom Effect design has analogous event/schema/recovery obligations, but can keep the persisted vocabulary narrowly aligned with escode.

Exit costs depend on authority placement. If pi owns native context and current product documents, leaving requires translating entries, fork/head semantics, documents, task outcomes and opaque provider state. If pi only wraps external agents, native history remains external but in-flight wrapper checkpoints still require reconciliation. Keeping explicit product facts reduces exit ambiguity, while duplicating authorities increases it. Fresh-state cutover avoids importing old prerelease data; it does not remove obligations to preserve user files, recover new-format state or explain abandoned associations.

## Conditional recommendation and next decision

Retain the accepted Effect Execution direction **if #160’s current behavior remains the target**, particularly for complete external agents. Pi saves scheduler implementation there, but leaves the most consequential product boundaries and introduces transaction/model integration. This is a reasoned fit judgment, not a measured cost comparison.

Choose a native-pi evaluation **if escode is willing to adopt pi’s agent/context model** and values its loop, tools, compaction and durable task composition enough to revise the handoff. In that case the benefit is broader and plausible. A model-facing CLI proxy is a possible transport choice, subject to separate qualification; it should not quietly reintroduce an unobservable full-agent loop.

If adopted, #160 should change explicitly in these places before implementation:

1. Name pi or escode as the single durable authority, locate each receipt/fact/document/task, and prove their shared transaction. Retain exact-payload/client/revision checks.
2. Specify native-pi versus external-agent context, identities, approvals and historical operations. Name unsupported behavior rather than claiming provider parity.
3. Resolve phase resumption/model retry versus new guarded system-origin continuation, including scheduler start gates, shutdown, unsafe effects and emergency Stop.
4. Define which progress is ephemeral, what semantic facts rebuild projections, and the retention/catch-up/backup contract. Keep file preservation and independent-client obligations intact.
5. Replace implementation-specific worker/outbox choices only where pi substitutes equivalent behavior; retain the acceptance scenarios, pin/attribution record and fresh-store cutover safeguards.

The smallest future probes are deliberately bounded: (a) one competing-client admission with duplicate and changed payloads, crash cuts and atomic facts/tasks; (b) one stub external effect accepted before outcome loss, plus a native-pi interrupted request, demonstrating different recovery policies; (c) storage-failure emergency Stop and a subprocess ignoring graceful cancellation, with exact-target fencing; (d) one persisted snapshot/catch-up and side-store rebuild after deferred-progress loss, proving zero provider/file effects; (e) one packaged Electron SQLite reopen/backup and dirty-buffer file operation. Add a single real CLI/proxy identity/approval/resume check only for the selected integration. Run upstream tests for the pinned subset before relying on it; no broad prototype is needed to answer these seams.

No application implementation, prototype, issue/ADR/glossary edits, provider calls, benchmarks or crash/power-loss experiments were performed. Parent-side inspection of existing escode seams remains complementary evidence; this report does not claim that every seam can be removed or reused unchanged.
