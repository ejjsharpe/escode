# Monaco, CodeMirror, and Pierre for escode

Investigated 28–29 October 2026 for [Compare Monaco, Pierre, and CodeMirror for editing and diffs](https://github.com/ejjsharpe/escode/issues/8). Scope: a macOS-first Electron/React application, ordinary local file editing and read-only Git diffs. Full language tooling, extensions, Git mutations, and building the application are excluded.

## Recommendation

**Inference: start with Monaco for both editing and diffs.** It supplies the most ready-made editor interaction for this particular destination, including a command palette and documented accessible diff navigation. Its worker setup is a real integration cost, but it avoids selecting and composing additional editor behaviours immediately. This is a recommendation for the human foundation decision, not proof that Monaco is faster, smaller, or cheaper to implement.

**CodeMirror 6 is a credible alternative**, particularly if precise UI composition and explicit document-state ownership matter more than obtaining a familiar editor surface immediately. Its official merge package already covers both diff layouts; choosing it does not require inventing a diff viewer.

**Pierre is a credible review-first choice, including actual editing**, but its current Edit mode is labelled Beta. Its rendering and React integration are attractive; that does not establish the same confidence in everyday editing or accessibility. Prefer it if editing directly inside a highly customized review surface becomes the defining requirement and its remaining risks are accepted. [Monaco overview](https://github.com/microsoft/monaco-editor/blob/dbf1945df2ff7e46512d2f548cc5c0977a3eadd8/README.md), [Monaco accessibility](https://github.com/microsoft/monaco-editor/wiki/Monaco-Editor-Accessibility-Guide), [CodeMirror merge API](https://unpkg.com/@codemirror/merge@6.12.3/dist/index.d.ts), [Pierre docs](https://diffs.com/docs#edit-mode).

## What can be consumed directly

| Requirement | Monaco | CodeMirror 6 | Pierre |
| --- | --- | --- | --- |
| Editing | Standalone code editor, models, undo, search, selections, language integrations. | `EditorView` plus `basicSetup` supplies history, search, selections, brackets, folding and common bindings; add selected language packages. | `Editor` attaches editing to `File` or `FileDiff`; includes selections, undo/redo, search/replace and markers. It is not merely a syntax-highlighted viewer. |
| Read-only diffs | Built-in diff editor with original/modified models and split/inline layouts. | Official `@codemirror/merge`: split `MergeView` or `unifiedMergeView`. | `FileDiff` and `CodeView`, split/unified layouts, file-pair or patch inputs, annotations and virtualization. |
| Smallest integration | One library for both surfaces. | One library family, including the separate merge package. | One package with separate renderer, React, editor and worker exports. |

Sources: [Monaco public API, version 0.57.0](https://unpkg.com/monaco-editor@0.57.0/esm/vs/editor/editor.api.d.ts), [CodeMirror basic setup, version 6.0.2](https://unpkg.com/codemirror@6.0.2/dist/index.js), [CodeMirror merge declarations](https://unpkg.com/@codemirror/merge@6.12.3/dist/index.d.ts), [Pierre current package exports](https://github.com/pierrecomputer/pierre/blob/70d1e3487fb9413be4a51b72f367015a764edbaf/packages/diffs/package.json), [Pierre renderer documentation](https://diffs.com/docs).

For read-only Git views, suppress editing and mutation-looking controls. Monaco exposes `readOnly`, `originalEditable`, and revert-icon settings. CodeMirror distinguishes state `readOnly` from DOM `editable`; unified merge controls default on and should be disabled, while split revert controls are optional. Pierre does not need Edit mode for this view. None of these libraries selects the Git baseline or reads repository state for escode. [Monaco options](https://microsoft.github.io/monaco-editor/typedoc/interfaces/editor_editor_api.editor.IDiffEditorBaseOptions.html), [CodeMirror merge declarations](https://unpkg.com/@codemirror/merge@6.12.3/dist/index.d.ts), [CodeMirror view declarations](https://unpkg.com/@codemirror/view@6.43.15/dist/index.d.ts), [Pierre docs](https://diffs.com/docs).

## Integration and lifecycle

**Monaco:** ESM/Vite integration requires worker entry points and URL routing. An official React sample shows mounting the imperative editor; a third-party wrapper is optional. Keep document models independently of React component mounts, retain view state when switching files, and dispose editors/models deliberately. The API supports `setModel`, `saveViewState`, and `restoreViewState`; these should not be confused with durable undo serialization. No supported persisted-undo contract was established by this review. Use undo-aware edit operations for programmatic modifications. [ESM guide](https://github.com/microsoft/monaco-editor/blob/dbf1945df2ff7e46512d2f548cc5c0977a3eadd8/docs/integrate-esm.md), [React sample](https://github.com/microsoft/monaco-editor/blob/dbf1945df2ff7e46512d2f548cc5c0977a3eadd8/samples/browser-esm-vite-react/src/components/Editor.tsx), [public API](https://unpkg.com/monaco-editor@0.57.0/esm/vs/editor/editor.api.d.ts).

**CodeMirror:** the core is an imperative DOM view over immutable editor state, suitable for mounting in a React ref and cleaning up with `destroy()`. Keep each file's latest state and restore it with `setState`; scroll and focus need separate handling. `EditorState.toJSON/fromJSON` plus `historyField` support serializing undo history if restart persistence later requires it. This is an available mechanism, not a decision to persist history now. The standard basic setup needs no editor worker bootstrap. [System guide](https://codemirror.net/docs/guide/), [released view API](https://unpkg.com/@codemirror/view@6.43.15/dist/index.d.ts), [state API](https://unpkg.com/@codemirror/state@6.7.6/dist/index.d.ts), [history API](https://unpkg.com/@codemirror/commands@6.11.1/dist/index.d.ts), [basic setup](https://unpkg.com/codemirror@6.0.2/dist/index.js).

**Pierre:** first-party React components and a stable `EditProvider` manage attachment. Creation-time props are not live reconfiguration. Integrations handle `onEditChange` and `onEditComplete`; editing completion is distinct from saving a file. Stable `editStateKey` values retain drafts/history in memory with bounded LRU storage. A key cannot be active in two editors of the same type; file-diff retention additionally depends on a compatible original baseline. Current documentation explicitly excludes serializable undo history: a reload starts fresh history even when content/view state is restored. Older release examples should not be copied as the current lifecycle contract. [Current edit lifecycle](https://github.com/pierrecomputer/pierre/blob/70d1e3487fb9413be4a51b72f367015a764edbaf/apps/docs/app/%28diffs%29/docs/Edit/content.mdx), [initial Edit release](https://github.com/pierrecomputer/pierre/releases/tag/diffs-v1.3.0).

**Shared application work:** all three remain renderer components. escode must own file identity, dirty buffers, save errors, external modifications, binary/encoding limits, and the selected Git comparison. Retaining an editor's undo state does not solve file conflicts. Electron integration must verify clipboard, shortcuts, worker/assets and content security policy in the packaged app; browser examples alone do not demonstrate that combination.

## Language support and accessibility

Monaco derives from VS Code's editor, with language support and extension APIs, but ordinary VS Code extensions do not run in it. CodeMirror composes language packages with editor extensions. Pierre offers syntax highlighting through Shiki and other backends; syntax colouring, markers, and its optional prediction callback are not evidence of a complete language service. None requires adding LSP for this v1. [Monaco README](https://github.com/microsoft/monaco-editor/blob/dbf1945df2ff7e46512d2f548cc5c0977a3eadd8/README.md), [CodeMirror basic setup](https://unpkg.com/codemirror@6.0.2/dist/index.js), [Pierre highlighters](https://github.com/pierrecomputer/pierre/blob/70d1e3487fb9413be4a51b72f367015a764edbaf/apps/docs/app/%28diffs%29/docs/Highlighters/content.mdx).

- **Monaco:** documents keyboard operation, screen-reader mode, escaping Tab capture, and a diff review pane navigable with keyboard commands. This is the strongest directly documented diff-accessibility surface found here. [Accessibility guide](https://github.com/microsoft/monaco-editor/wiki/Monaco-Editor-Accessibility-Guide).
- **CodeMirror:** explicitly targets screen readers and keyboard users. Tab is not captured by default; if indentation bindings are enabled, the app should explain its Escape-then-Tab escape hatch. This does not prove the accessibility of our configured merge view. [Project feature statement](https://github.com/codemirror/website/blob/main/site/index.html), [Tab handling](https://codemirror.net/examples/tab/).
- **Pierre:** source supplies a multiline textbox role, editable DOM and a filename label. These are meaningful accessibility provisions, not a VoiceOver conformance result. A tested screen-reader workflow comparable to Monaco's guide was not established in this investigation. [Editor source](https://github.com/pierrecomputer/pierre/blob/70d1e3487fb9413be4a51b72f367015a764edbaf/packages/diffs/src/editor/editor.ts).

**No candidate was tested with VoiceOver, keyboard-only navigation, IME input, or macOS accessibility settings.** Such verification remains necessary after integration.

## Performance, maturity and licences

CodeMirror documents viewport rendering rather than drawing every line. Pierre provides virtualization and optional highlighting workers, but its actively edited file renders on the main thread. Monaco has worker integration and diff time/file-size limits. These are architectural facts, not comparative measurements. **Bundle size, startup time, memory, typing latency and large-diff behaviour were not measured.** npm unpacked sizes would not be a valid comparison of a configured Electron application. [CodeMirror viewport](https://codemirror.net/docs/guide/#viewport), [Pierre edit performance](https://github.com/pierrecomputer/pierre/blob/70d1e3487fb9413be4a51b72f367015a764edbaf/apps/docs/app/%28diffs%29/docs/Edit/content.mdx), [Monaco diff options](https://microsoft.github.io/monaco-editor/typedoc/interfaces/editor_editor_api.editor.IDiffEditorBaseOptions.html).

Monaco documents its public API boundary; relying on internal modules increases upgrade risk. CodeMirror's released packages expose explicit state/view/merge contracts. Pierre's renderer package is released, but Edit mode remains labelled Beta in current docs; its initial release explicitly warned of API changes. Pin supported versions and verify upgrades whichever library is selected. [Monaco API policy](https://github.com/microsoft/monaco-editor/blob/dbf1945df2ff7e46512d2f548cc5c0977a3eadd8/README.md), [CodeMirror merge release](https://registry.npmjs.org/@codemirror/merge/6.12.3), [Pierre docs](https://diffs.com/docs#edit-mode), [Edit release](https://github.com/pierrecomputer/pierre/releases/tag/diffs-v1.3.0).

Monaco and the inspected CodeMirror packages declare MIT licences. Pierre declares Apache-2.0. Preserve the relevant notices when distributing; no licence incompatibility assessment of a final dependency tree was performed. [Monaco licence](https://github.com/microsoft/monaco-editor/blob/dbf1945df2ff7e46512d2f548cc5c0977a3eadd8/LICENSE.txt), [CodeMirror metadata](https://registry.npmjs.org/@codemirror/merge/6.12.3), [Pierre licence](https://github.com/pierrecomputer/pierre/blob/70d1e3487fb9413be4a51b72f367015a764edbaf/packages/diffs/LICENSE.md).

## Decision boundary and evidence snapshots

A mixed stack has **no demonstrated saving for v1**: each candidate already handles a single selected file plus its diff. Adding Pierre to Monaco or CodeMirror introduces another rendering/theme/lifecycle integration. Revisit only for a concrete requirement such as a virtualized multi-file review feed that saves more work than it adds. This is scope-based inference, not an extraction benchmark.

The recommendation changes toward CodeMirror if explicit serializable state, UI composition, or measured resource results become decisive; toward Pierre if in-place review editing becomes central and its Beta/accessibility uncertainty is acceptable. The user still chooses the editor.
