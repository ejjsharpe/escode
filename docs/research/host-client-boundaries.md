# Host, client and platform responsibility boundaries

Research for [Where should Effect, storage and platform responsibilities live across host and clients?](https://github.com/ejjsharpe/escode/issues/54), under [Establish escode’s Effect host and client foundation](https://github.com/ejjsharpe/escode/issues/49). Inspected 2026-10-30. **Engineering recommendations, not ratified architecture, product policy or terminology.** Report only; no application changes, installs, ADRs, issue edits or runtime experiments.

## Recommendation

Use one execution-host service graph for Chats, Files and Source Control; one validated contract layer; one shared client connection/synchronization runtime; and separate client-platform and host-platform adapters. Initially compose the host inside the desktop main process, with an authenticated loopback WebSocket boundary used by the renderer. Keep Electron IPC for trusted local bootstrap and desktop capabilities. A separate executable/service is a later composition choice, not a prerequisite for establishing the ownership boundary. The [phased handoff question](https://github.com/ejjsharpe/escode/issues/58) explicitly requires WebSocket commands and streams in the first slice, so an IPC-only chat refactor is insufficient.

Adapt T3’s coherent contracts/session/supervision/bounded-synchronization layer and adopt its tracked Codex transport source unit, while preserving escode’s authorization, saved associations, uncertain-send handling, filesystem helper and recovery journals. Keep React, Monaco and suitable pure TypeScript independent of Effect. This reconciles the [upstream adoption evidence][reuse] with the [runtime recommendation][runtime] and [baseline inventory][baseline]; it does not infer runtime compatibility or a performance improvement from source structure.

The seam is justified by multiple clients and machines: the client presents and submits intent; the host owning the selected execution context authorizes and performs it. A desktop platform adapter can access its own clipboard or native picker without acquiring authority over a remote host. A host can run filesystem and provider work without a desktop window. Every route remains bound to the same persistent host identity; another available host is never an automatic substitute.

## Current authority is spread beyond ChatService

[Main][main] creates stores/services, approves roots, validates IPC origin/frame/arity, tracks project-session generations, derives secondary-checkout authorization, protects app-state files, prepares worktrees, captures imports, coordinates dirty-file dialogs and handles quit. Moving only `ChatService` would leave execution authority in the Electron shell. The six IPC channels are `tools:status`, `native-import-capture`, `lifecycle`, `files-watch`, `project`, and `chat`; their responsibilities must all be accounted for.

[Chats][chats] persists metadata, drafts, provider thread identities, original directory identities, scratch ownership and worktree reservations. [ChatService][service] owns live sessions, first-send preparation/uncertainty, scoped request tokens and epoch rejection. [Tools][tools] discovers installed executables, performs stdio RPC and terminates owned process groups. Codex owns transcript history. Replacing any of these with T3’s application event log is a storage/product migration, not a transport substitution.

[Project][project] owns descriptor-backed checkout access, repository/object validation, Git, text/hash limits, watches and worktrees. [The C helper][native] enforces macOS descriptor-relative no-follow operations and native Trash. [FileOperations][operations] journals before mutation, distinguishes applied changes from persistence failures, reconciles stale workspace writes and waits for renderer acknowledgement. [Workspace][workspace] separates host approvals from renderer memory and syncs replacements. [Pure reconciliation][reconcile] is already used by both host and renderer. These are preservation boundaries, not incidental file locations.

[CheckoutView][ui] owns live Monaco buffers, explicit save/conflict UI, shared editable Files/diff models, model remapping after operations and recovery persistence. [ProjectChats][chatstate] polls full snapshots every 300 ms; [Agents][agents] polls catalogue/targets every second; status and worktree display include two-second polling. The baseline’s 25-chat diagnostic produced 175 snapshot calls, 4,375 listener calls and 350 saved-list reads per roughly 2.1 seconds; a roughly 2 MB history produced roughly 14.9 MB of JSON results. These are in-process measurements, **not** IPC bytes, React commits or production heap limits. They justify testing push/summary/detail seams, not claiming a particular speedup. [Measurement definitions and limits][baseline].

## Proposed packages and dependency direction

Names here are tentative source organization, not new product vocabulary. Avoid one package per interface; internal modules are sufficient until a real independent consumer/build boundary exists.

| Proposed unit | Owns and exports | Allowed dependencies and exclusions |
| --- | --- | --- |
| `packages/contracts` | Validated commands, results, errors, stream items, handshake, identity references and DTOs for all three features | Effect Schema/RPC declarations and portable data only; no Node, Electron, React, stores or provider SDK |
| `packages/shared` | Existing pure reconciliation and path-affect/move logic, portable data transforms | Type-only contract dependencies; ordinary TypeScript functions, no Effect runtime requirement for pure callers; no generic utility collection |
| `packages/host` | Authorization, chat/resource orchestration, installed-provider integration, filesystem/Git services, watches, durable repositories, operation recovery, stream publication | Contracts/shared, Effect and injected Node/native capabilities; no renderer or Electron imports |
| `packages/client-runtime` | Host-bound connection registry, scoped session/supervisor, synchronization/reducers/cache, cancellation, command outcome tracking, portable client state access | Contracts/shared, Effect/socket and supplied credential/storage/connectivity hooks; no Node/Electron/Monaco/React imports |
| `packages/effect-codex-app-server` (tracked source) | Adopted protocol/client/generated schema/error transport with provenance | Effect plus supplied process services; host-only process entry points; not the public escode wire protocol |
| `apps/desktop` | Electron composition/bootstrap, native client capabilities, local host-platform wiring; React/Monaco presentation and client-owned view/recovery storage | Supplies adapters to host and client runtime; application entry points select implementations |

A separate `host-platform` npm package is unnecessary now: keep its interfaces/Node-macOS implementations within host subpaths and wire them from the composition root. Likewise desktop client capability interfaces can live with the client boundary and implementation in desktop. This keeps the five real reusable units without inventing a plugin framework. Contracts must not import shared runtime helpers that import contracts back. DTO types may be inferred from schemas with type-only imports in presentation; importing a host class for its shape is removed.

**Effect boundary:** use Layers for the host service graph and scoped resources, Effect for cancellable I/O orchestration, provider sessions, watches, queues and client connections; Schema for untrusted input/output; RPC/Stream for typed commands and subscriptions. Preserve plain functions for `affected`, `moved`, `reconcileSave`, `reconcile`, chat ordering and pure reducers. Keep hooks, focus, tree navigation, accessibility, Monaco models/undo and rendering in React/ordinary TypeScript. React talks to an ordinary snapshot/subscribe/action facade using `useSyncExternalStore`; do not add `@effect/atom-react` merely to connect to Effect. Layer construction happens once per actual owner scope, never on render. [Current store][chatstate], [ordering][order], [pure reconciliation][reconcile], [runtime API evidence][runtime].

Converting synchronous native/Git operations into `Effect.sync` does not make them nonblocking. Preserve descriptor validation while measuring and moving blocking work off the host event loop where necessary. No speculative helper rewrite or weakened check is justified by adopting Effect. [Project][project], [baseline][baseline].

## Host responsibilities across Chats, Files and Source Control

Recommendation: expose domain-specific services under one host identity/authorization/session infrastructure, rather than a generic `operation: string, ...args` router.

- **Projects/contexts:** host owns approved roots, repository/common-directory identity, original/current checkout associations needed for chat setup, saved directory identities, scratch allocation and managed-worktree ownership/reservations. Revalidate before execution and after awaited preparation/confirmation where the existing code does. UI paths and a successful schema decode grant no access. Saved membership remains distinct from open editor tabs. [Main][main], [Chats][chats], [Project][project].
- **Chats:** host owns saved-chat mutations, provider credentials and process sessions, first-send durable intent, uncertain outcome, scoped approvals/input and Stop routing. Export a safe projection of saved metadata plus summaries/detail streams; never export process objects, raw credentials or arbitrary provider internals. Existing `settings: any` and request `params: any` need deliberately validated provider-to-client variants, including an explicit unknown/unavailable presentation path rather than asserting a type. [ChatService][service].
- **Files:** host owns authorized list/read/hash/save, external-change watches, create/move/copy/Trash, native destination checks, durable intent and actual outcome. Client supplies captured text/baseline and explicit user choices; host validates them and serializes mutation/recovery. A `SaveConflict` result must preserve available text, not silently retry an overwrite. Watch notifications invalidate a scoped cache; they are neither proof of disk state nor authorization. [Project][project], [FileOperations][operations].
- **Source Control:** execute Git on the same host and authorized checkout as Files/chats; expose status/diff results through the same contracts/runtime. Preserve staged HEAD-versus-working-copy semantics and the editable new side’s shared Files buffer. Keep UI selection/diff model ownership client-side. Do not add Git mutation features that baseline v1 does not have, or make Git availability a prerequisite for existing chat execution/approved Files restoration. [Project][project], [CheckoutView][ui], [accepted glossary][glossary].
- **Persistence and recovery:** one host owner orders durable chat/context/approval and operation state; process sessions and stream caches are rebuildable runtime state. Journal reconciliation runs before mutations reopen. Separate recovery acknowledgement from transport ACK and provider acceptance. [Workspace][workspace], [FileOperations][operations].

Credentials are split by authority: provider authentication stays on the execution machine (currently installed authenticated Codex); client connection credentials/proof keys stay in the client’s platform store. Host authentication secrets and approved-root records are never client editable. This does not ratify an encrypted-at-rest store, a pairing policy or a new credential dependency; those remain in [authenticated connections](https://github.com/ejjsharpe/escode/issues/56).

## Contracts, synchronization and transport responsibilities

Recommendation: define one protocol group with feature submodules, shared host/context references and typed error categories. Include queries/commands for chat catalogue/targets/draft/context/open/send/answer/Stop, Files list/read/save/operations/recovery acknowledgement, Git status/diff/worktree queries, and subscriptions for catalogue summaries, selected detail, loaded-directory invalidation and Source Control invalidation. Keep native picker and clipboard commands outside this remote domain group.

Each command carries its target host and appropriate saved project/chat/checkout reference, correlation/command identity and expected resource/session revision where required. Replies to provider requests bind host/chat/provider-session/request identity; a transport request ID alone is insufficient. Stop uses the live session owner and remains possible when the directory is unavailable. Roots can remain host-local path fields for display/migration; they are never globally unique identifiers or credentials. Use portable wire values rather than file descriptors, Electron events, Monaco URIs or serialized `Error` instances. Declare validation limits and typed errors for unavailable context, identity change, conflict, stale request, denied authority, incompatibility, overflow/resync and uncertain mutation. Keep diagnostic text separate from safe retry classification. [Existing checks][main], [scoped replies][service], [runtime Schema/RPC evidence][runtime].

Shared client runtime owns one supervisor per desired host, one socket/session per attempt, and replaceable feature subscriptions. It validates host identity/version before admitting data, partitions all caches by host, rejects callbacks from old attempts, exposes connection state and resynchronizes projections. It does not open provider sessions merely because a component subscribes. No component starts a second reconnect loop. T3’s [session][t3-session] and [driver][t3-driver] demonstrate the coherent interface; its [supervisor][t3-supervisor] owns retry/wake/blocked behavior. Adapt those together with model/identity/credential hooks and tests, replacing T3 config/theme/provider projections with escode contracts.

Host streams own snapshot/live handoff and retention; clients own validated reducer application and resume cursors. Use lightweight background summaries with selected-chat detail. Keep full-state coalescing distinct from provider text accumulation. Never coalesce away an approval, terminal boundary, operation fact or unsaved text. Reuse [LiveStreamBudget][t3-budget] with its replay/live and cancellation integration: its next-pull release depends on RPC ACK behavior, and its 1,000-item/8 MiB defaults are upstream values, not escode budgets. Define frame/entity/global/per-client bounds and overload recovery; RPC backpressure does not bound provider queues, socket buffers or all heap. [Full adoption analysis][reuse].

The [synchronization question](https://github.com/ejjsharpe/escode/issues/55) owns exact event algebra, sequencing, snapshot high-water/overlap rules, gaps, cursor durability, receipts/retention and duplicate-command semantics. This report supplies ownership, not an invented protocol resolution. Recommended minimal persistence direction is authoritative saved records + bounded runtime projections and fresh snapshot after host epoch loss; adopt durable replay only where that ticket demonstrates need and recovery semantics. Codex history is not an escode event log. A receipt cannot make the provider RPC and local persistence atomic. After a lost Send result, report uncertainty and reconnect without resending; command-status recovery must not become automatic turn replay.

**Transport adapters:** authenticated loopback WebSocket is the first common path; host RPC handlers call the same services regardless of transport. Remote WebSocket later changes address/auth/secure routing, not domain authority. Keep transport encoding, frame limits and socket resource cleanup separate from snapshot/reducer semantics. Electron IPC still validates sender/main frame/document and shapes for every local capability; schemas do not replace origin validation. Do not bridge unbounded stream events through eagerly draining IPC. If an IPC domain transport is later needed, it must satisfy the same ACK/cancellation/bounds tests rather than adding a parallel semantics path. [Electron security guidance](https://www.electronjs.org/docs/latest/tutorial/security), [current preload][preload], [runtime transport limits][runtime].

Local bootstrap should deliver only the local endpoint and scoped connection material through narrow preload access, validate expected host identity and refuse unsupported protocol versions. Loopback binding alone is not authentication. Browser WebSocket constructors cannot copy arbitrary Node upgrade headers, so future browser authentication needs the complete ticket/cookie/proof design in the authenticated-connections ticket. No LAN listener, remote pairing, TLS deployment or browser/phone interface is delivered in this report or implied by the first seam. [Runtime browser evidence][runtime], [T3 auth closure][reuse].

## Desktop capabilities versus execution-machine authority

Capability discovery must distinguish **client capabilities** (a UI can choose local files, copy text, reveal a local item) from **host capabilities** (a machine can safely perform native Trash, Git, watches or run Codex). Evaluate each action against both sets and its target identity. A remote macOS host may support Trash even when the client is a browser; a desktop client cannot lend its local Trash implementation authority over remote paths.

| Current flow | Proposed owner and same-machine behavior | Desktop connected to a different execution host |
| --- | --- | --- |
| Open project dialog | Desktop invokes native chooser; host verifies chosen local reference/repository and writes approval | A local directory selection cannot approve a remote root. Remote project selection/approval is a separate host-authorized workflow, not a forwarded local path |
| Native File drop/paste | Isolated preload resolves genuine `File`; desktop captures short-lived descriptor-backed `NativeImport`, host validates destination and operation | Native descriptor/token cannot cross machines. Future explicit upload stages bytes/manifest on destination host with validation and recovery; until implemented expose unsupported capability, never interpret a client path on host |
| Files Copy/Cut/Paste and drag | Clipboard holds opaque captured selection reference; host binds source checkout/object identity and validates destination, current session and dirty protections | Namespace token by source host/session. Same-host operations can retain native semantics; cross-host transfer is not ordinary move/cut and requires a later explicit workflow |
| Copy absolute/relative path | Host resolves authorized target/display text; client clipboard writes text | Clipboard belongs to client. Remote absolute path is descriptive host-local text; it grants no local filesystem access |
| Reveal in Finder | Client desktop shell after verifying target is local and permitted | Disable/unavailable when no matching local capability; do not call local `showItemInFolder` with the remote string. Host-side reveal requires separate supported/authorized intent, not an assumed user desktop session |
| Trash | Host filesystem/native adapter performs checked mutation with journal and actual outcome | Execute on target host only when its adapter supports equivalent recoverable Trash semantics; no fallback to permanent delete or client-local Trash |
| Dirty/collision/removal confirmations | Client presents plan; host captures source/destination identity and revalidates explicit answer before mutation | Confirmation must return to the originating host/operation/session and expire or fail if the captured context changed; disconnect is no answer |
| Window/project close and quit | Desktop owns native events and UI; client coordinates flush; host provides active-work/status/shutdown operations | Closing this client is not authority to terminate another machine’s work. Exact permitted actions and prompts remain lifecycle policy |

Current [preload][preload] uses `webUtils.getPathForFile`; Electron [documents](https://www.electronjs.org/docs/latest/api/web-utils) that a JS-created, non-disk-backed File yields an empty path. Current [NativeImport][imports-native] retains descriptors and checks ancestry/object identity; [main][main] expires captures after 60 seconds and clears them on navigation, renderer loss and close. Preserve those protections for local imports, rather than replacing them with a schema accepting arbitrary paths. [Shell API](https://www.electronjs.org/docs/latest/api/shell) reveals files on the machine executing the call; the remote limitations above are engineering inferences from that locality.

Keep macOS `filesystem.c` and its CoreServices Trash path behind a host native-filesystem implementation. “Platform-independent host interface” does not claim current helper portability. A Linux/Windows host or headless Mac needs an explicitly supported implementation or reports the operation unavailable. Do not substitute `shell.trashItem` for the descriptor/object-preserving helper merely because Electron offers one. [Current helper][native], [native race evidence][baseline]. Native dialogs/clipboard/Finder stay desktop client services; host mutation orchestration asks for decisions without importing Electron.

The [lifecycle ticket](https://github.com/ejjsharpe/escode/issues/53) retains ownership of quit/detach, unattended requests and host-stop authority. Internally separate host process, provider session, client connection and view-subscription scopes now. Losing a subscription/socket releases its watches/delivery resources, not provider work. Keep current explicit desktop Stop and Close shutdown and no automatic restart turns until the user accepts an amendment. Finalizers cannot run after process death and do not replace journals or process-group escalation. Existing [shutdown implementation][service] and [lifecycle baseline][baseline] remain constraints.

## Editor ownership and durable records

Recommendation: retain Monaco models, current text/undo, selection, scroll, tree state, visible chat/detail subscriptions and transient pending UI state on the client. The host owns disk bytes, baseline hashes/object identities, saved chat/context/provider associations, approvals, worktree/scratch ownership, command/operation facts and recovery coordination. A host can persist an acknowledged recovery copy without owning the live editor buffer or being allowed to overwrite newer client text. Files and diff editors share the same client buffer as today. [Current model and recovery path][ui].

Current `WorkspaceState` mixes tabs/views, saved-project registry and recovery drafts. Split logical ownership before splitting storage: host registry/approvals versus client workspace view state versus recovery records tagged with host, client/editor identity and revision. Keep local desktop recovery storage/persistence behavior while extracting; moving it to browser storage or synchronizing it to all clients is **not** implied. Shared chat unsent prompts currently live in `Chats` and appear through both Agents/Chats; preserve that in the first slice. Do not silently convert them to client-private drafts just because editor view state is local. [Workspace][workspace], [Chats][chats], [renderer persistence][uistore].

The [multi-client decision](https://github.com/ejjsharpe/escode/issues/57) must decide draft sharing/takeover, simultaneous Sends/replies/saves, visibility of recovery copies and which clients must acknowledge file moves/Trash before journals can retire. The seam must carry origin/revision/operation references and refuse stale overwrites, without choosing last-writer-wins, leases or collaborative editing here. The current single-renderer whole-workspace `persist`/ACK mechanism is not safe to broaden to multiple clients unchanged: one stale snapshot could erase another’s drafts and one ACK could retire recovery needed elsewhere. This is an inference from [current persistence/reconciliation][operations], covered by that existing ticket.

## Persistence identity, versions and crash migration

Current stores use path-based project/checkout references, chat UUIDs/provider thread IDs, dev/inode directory identities, worktree reservations and unversioned JSON shapes. `Workspace` uses queued temporary writes + file sync + rename + directory sync; `Chats` queues temporary-write/rename but does not explicitly sync. There is one durable file-operation journal with completed/uncertain state. Those differences matter: adopting a Scope is not a durability upgrade. [Chats][chats], [Workspace][workspace], [FileOperations][operations].

Recommend the following migration design constraints for the implementation handoff:

1. Persist one installation/execution-host identity before publishing an endpoint or migrating records. Do not derive identity from hostname, URL, port, path, MAC address or live connection. Connection-attempt and host-start epochs are separate transient identities. All chat/context keys and cached/recovery references include the host identity; provider thread ID remains namespaced by host/provider. Restored chats never retarget to another host when offline.
2. Treat existing local records as belonging only to this original installation. Preserve existing chat UUIDs, creation order, project/common-directory grouping, exact checkout paths/dev+inode, provider threads, prompts, initial-send uncertainty, scratch ownership and incomplete worktree reservations. Add a host namespace rather than regenerating product identities. Do not eagerly replace every local path with a new UUID database: path plus host namespace and current physical validation can preserve semantics. Serialized filesystem identity values need an explicit lossless representation; migrations must not round or reinterpret them across runtimes.
3. Add explicit storage format versions distinct from protocol version, entity revision, baseline hash and connection epoch. Validate old/new formats, refuse unsupported newer versions without writing, and retain invalid files for inspection. Migration is idempotent, single-writer, restartable, and produces a verifiable generation manifest/commit marker for related files; repeated launch must not allocate new host IDs/resources or replay first Send. A multi-file rename is not a transaction.
4. Quiesce mutation and recovery writes, preserve a backup of originals, validate and reconcile the existing operation journal against original object identities **before** splitting workspace ownership. Unavailable/replaced contexts retain journal/drafts and remain blocked. Do not acknowledge an ambiguous mutation to make migration finish. Stage destination records and synced metadata, then atomically publish a generation selector only after all records are durable; retain the prior generation for recovery. This is a recommendation for crash-safe multi-file migration, not a claim the current writer supplies transactions.
5. Split saved registry/approval state from client tabs/views and recovery copies with explicit provenance/revision. Preserve acknowledgements and current persisted recovery copies on the original local client/host during initial extraction. Do not broadcast full workspace snapshots as host truth or allow UI memory to manufacture approvals. Dirty text and loaded disk baseline travel together; successful save updates baseline without deleting newer text. Explicit discard is the destructive boundary, not a remote resync.
6. Carry file-operation IDs/facts through model reconciliation, recovery persistence and acknowledgement. Preserve dirty descendants on move, copied drafts, partial Trash outcomes and `persistencePending`; no clearing journals merely because a socket ACK arrived. The multi-client ticket must resolve fan-out/acknowledgement semantics before permitting multiple mutating editors. Retain incomplete reservations and uncertain sends after restart; reconnect reads history and never starts a turn.
7. Prevent concurrent old/new host writers (exclusive owner lock) and reject old binaries against newly versioned writable state. Rollback before post-migration mutations may restore the complete prior generation; after real file/provider side effects, do not restore stale metadata alone. Require a tested reverse migration or retain the new store and report recovery guidance. Backups do not undo provider turns or filesystem mutations.

These are engineering constraints, not a decision to introduce SQLite. Retain JSON repositories behind interfaces initially; a transaction-capable store is an evaluated later option if protocol receipt/replay or multi-client recovery requires it. If selected, import the whole migration/transaction/retention story rather than a Node SQLite convenience function. [Upstream persistence closure][reuse].

Required fault checks: kill before/after host-ID publication, each staged write/manifest switch, native mutation and intent completion, workspace reconciliation and ACK; migrate twice; load unknown/newer/corrupt versions; restore missing/replaced directories; interrupt worktree/scratch preparation; lose provider acceptance result; deliver stale pre-migration persist/ACK; launch competing binaries; rollback with and without later side effects. Assert exact retained text/baselines/IDs, no fresh resources, no prompt replay and no disappearing journal. These are **unrun future checks**.

## Acceptance and decision handoff

The first slice should prove a renderer connected through authenticated local WS, host identity/version validation, a chat summary/detail stream and at least directory listing/watch through the same contract/runtime. Retain filesystem/Git/read/save/conflict/intent semantics behind host adapters while migrating callers in bounded phases; exposing a generic unchecked bridge for unmigrated features would weaken authority. Actual sequencing and scope acceptance belong to [the phased plan](https://github.com/ejjsharpe/escode/issues/58).

Required engineering experiments remain: Effect 4.1.0 + extracted T3 code under Electron CJS/bundling and packaged restricted PATH; Codex schema compatibility/process descendants; slow/stalled clients with measured frame/queue/socket/provider/global bounds; snapshot handoff/gaps/cancellation/old epochs; wrong-host/forged-path/expired-capability attempts; lost command response with no replay; crash migration/reconciliation. Watch disconnect must release subscriptions without killing provider sessions. Verify directory listing/watch and Source Control authorization with the same identity, including no-Git existing contexts. Run existing preservation tests and baseline-relative production IPC bytes/calls, React commits, native/Git activity, latency and retained-memory workloads defined in [baseline follow-up protocol][baseline]. There is no measured improvement or chosen numerical budget in this report.

Candidate ADRs, only after architecture acceptance:

- One host authority for provider/files/Git; client capabilities separated from host-native capabilities, with Effect outside presentation/pure logic.
- Adapt coherent upstream infrastructure with tracked source provenance instead of whole-product fork; chosen exact Effect/runtime combination and upgrade obligations.
- Host identity and versioned persistence migration, with recovery generations and downgrade/write ownership rules.
- Authoritative storage/replay/receipt choice and crash/uncertainty limits, after the synchronization ticket resolves it.
- Host/provider/client/view lifetime separation and shutdown policy, after the lifecycle amendment; multi-client draft/editor conflict policy after live user agreement.

Proposed terminology requiring agreement: **execution host** (authoritative runtime on one machine), **host identity** (persistent installation binding, distinct from route), **client connection** (replaceable authenticated transport session), **provider session** (host-owned Codex connection/process lifetime), **view subscription** (observation lifetime), and **client capability / host capability** (location and authority distinguished). These are explanatory proposals only; GLOSSARY.md remains unchanged. Existing Project, Chat, Chat draft, Recovery draft, File-operation intent, Current checkout and Managed worktree definitions remain authoritative. Do not rename product concepts to T3 “environment/thread” simply because those names occur upstream. [Agreed glossary][glossary].

**Existing ticket ownership, no implicit product answers:** lifecycle/quit/unattended approvals → [closing clients and stopping hosts](https://github.com/ejjsharpe/escode/issues/53); exact stream/receipt/retention protocol → [synchronization](https://github.com/ejjsharpe/escode/issues/55); pairing/trust/revocation/version support → [authenticated connections](https://github.com/ejjsharpe/escode/issues/56); draft visibility, competing Sends/replies, recovery sharing and simultaneous file edits → [multiple clients](https://github.com/ejjsharpe/escode/issues/57); acceptance/phase scope/experiments/ADRs → [phased handoff](https://github.com/ejjsharpe/escode/issues/58). Keep accepted Stop and Close, no resend, no restart turns, explicit save and practical conflict guarantees until amended.

Suggested map gist, for parent review only: “Recommend one host authority across Chats/Files/SCM, portable validated contracts and shared Effect connection/sync runtime, with client/editor state and platform capabilities separated; adapt coherent T3 infrastructure while preserving escode persistence, identity and recovery.”

**New precise questions:** no additional ticket outside existing scope is established. Cross-machine native imports, multi-client operation acknowledgement, generation-safe persistence migration and old-binary writer exclusion are precise engineering subquestions for authenticated connections, multi-client control and phased handoff respectively. Shipping cross-host file transfer is outside current delivery scope. Suggested fog edit: none; carry these known constraints into the existing tickets rather than duplicating them or declaring them unspecified fog.
