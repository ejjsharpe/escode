# Durable state architecture for escode

Research date: 2026-10-31. **Proposal for discussion; no implementation or accepted decision is changed.**

## Recommendation

For the recovery and consistency requirements investigated here, adopt **one host-owned SQLite database for authoritative application metadata, command receipts, resource reservations, client recovery records and file-operation facts**. Use conventional current-state tables with explicit transactions and a small operation state machine. Keep provider history provider-owned, project files filesystem-owned, and the bounded live-output spool separate. The subsequent discussion introduces action-level time travel as a potential requirement that could change the event-sourcing recommendation; see [section 3.1](#31-discussion-follow-up-action-level-time-travel). Restart must still require explicit action before another turn.

These are three independent decisions:

1. **SQLite: recommend yes**, subject to packaged Electron/runtime and failure-injection qualification. The benefit is atomic changes across related application records, indexed access and removing repeated whole-store rewrites. It is not a promise of faster execution or atomic external effects.
2. **Application-wide event sourcing: recommend no for recovery alone; reconsider if action-level time travel is required.** Receipts and operation evidence provide the recovery facts escode needs without making every state change a permanent domain event or maintaining replayable projections. This is not a recommendation to adopt event sourcing later by default.
3. **Owning complete chat history: recommend no for this scope.** SQLite can hold metadata and recovery evidence without taking ownership of every provider transcript. Keep bounded, explicitly partial history behavior; revisit complete history only for an independently accepted product requirement.

The main justification is concrete: escode already has careful individual-file persistence, but its correctness spans several files and renderer storage; a growing receipt array shares a 1 MiB cap with host identity; and a hard process crash leaves a lock file that prevents reopening. SQLite removes some storage machinery, while application recovery rules still have to preserve uncertain effects, unsaved text and exact context identities. See the evidence below.

### What is already sound

It would be inaccurate to say these stores simply overwrite JSON unsafely. The shared atomic writer fsyncs the temporary file before rename and fsyncs the containing directory before resolving. Foundation and chat storage add stronger refusal/poisoning on ambiguous writes. The inspected atomic-write test asserts ordering and error propagation; it is not a power-cut test. [Atomic writer][E-atomic], [test][E-atomic-tests]

The application already separates intended operation from known outcome, retains exact reservations, preserves unsent/recovery text, checks context identity, prevents duplicate durable Send identities from invoking the provider twice, and avoids treating missing source files alone as proof of Trash success. File recovery deliberately reconciles available evidence instead of replaying the operation. Those are application guarantees to retain, not incidental file-store implementation. [Send][E-send], [file recovery][E-operations], [chat allocation][E-chat]

### Concrete limitations and their consequences

1. **Crash availability is weaker than graceful reopen.** `owner.lock` is an empty exclusively created file. There is no PID, lease, OS-held lock or stale-owner recovery. Normal close removes it; a hard process termination leaves it, and the next `open("wx")` fails before receipt recovery. The restart tests generally call `store.close()` first. Existing refusal preserves identity but requires manual intervention after an ordinary hard crash. A stale `.tmp` similarly blocks foundation/chat recovery even if the previous target is valid. Do not delete either blindly. [Open/close][E-foundation], [restart tests][E-send-tests]
2. **Whole-store cost and admission exhaustion are structural.** Each normal Send performs admission, dispatching and accepted/uncertain writes of the complete foundation JSON; receipt reads also clone the whole state and linearly search it. Commands include full prompt text. At roughly fixed receipt size, cumulative serialized bytes grow quadratically with the number retained until the 1 MiB cap; this is complexity analysis, not a benchmark. Startup rewrites the entire store once per unfinished Send. No pruning is implemented. The test intentionally exhausts storage with 100,000-character commands. Create and control receipts compete in the same file; there is no separately reserved Stop capacity there. Outcome text can also grow after admission, so admission must budget for terminal evidence, not only initial bytes. [Foundation][E-foundation], [Send][E-send], [capacity tests][E-send-tests]
3. **Atomic files are not an atomic application state change.** Receipt admission, chat reservation/provider binding, workspace drafts, operation completion and acknowledgement have separate commit points. The current file-operation code handles several of these gaps carefully, but adding domains/clients increases reconciliation cases. A directory fsync cannot combine them into one transaction. A commit failure after rename can also mean the new file is visible while success is unknown. [Chat Send][E-chat-send], [operation sequence][E-operations], [atomic writer][E-atomic]
4. **Client command durability is best effort.** Pending command keys are not explicitly namespaced by host/client IDs. Their random chat IDs reduce accidental collision but do not express ownership. Losing a pending ID while retaining text can leave the client unable to identify the old receipt; this is not an automatic replay path in current code, but a later explicit Send can be ambiguous. Electron documents a DOMStorage flush operation, not an awaitable durable commit result; the host explicitly acknowledges this limitation. [Client][E-client-chat], [preload][E-preload], [host flush][E-main-flush], [Electron session API][D-electron]
5. **Spool bounds are real; reclamation and ownership need work.** It scans every directory entry to count used bytes on each persist, retains obsolete immutable chunks and has no collector for provider-reconstructible bodies. Only `.tmp` debris is removed; indexes name chat/provider but not host/store generation. Index replacement is charged with extra space headroom; no live chunks are evicted to admit output. Repeated updates therefore consume quota eventually even when the displayed body is bounded. This is a predictable limit, not evidence of a measured leak rate. [Spool][E-spool]
6. **The stores have different validation and interrupted-temp policies.** Foundation validates complete records and bounds bytes. Chat loading validates the envelope/array but not every `SavedChat` field. Workspace/journal parse whole JSON and do not preflight an equivalent on-disk size cap; the shared writer opens `.tmp` with `w` and subsequent writes overwrite it. Wire limits do not bound a tampered or accumulated file on disk. SQLite still needs row/schema validation, bounded payload decoding and fail-closed version handling. [Foundation][E-foundation], [chat][E-chat], [workspace][E-workspace], [journal][E-journal], [contracts][E-contracts]
7. **Application durability does not imply project-file durability.** Native stage/copy fsync and JSON journal fsync are not proof that the later filesystem name change survived power loss. Create/move/replace/copy-publication lack explicit parent-directory sync in the reviewed helper; native Trash and Git have their own semantics. Likewise, exclusive ownership JSON creation is not an acknowledged durable write. This is a missing durability claim, not a claim that the OS necessarily loses those operations. [Native helper][E-native], [ownership write][E-checkout-repository]
8. **Current client isolation is a foundation, not a multi-client implementation.** There is one stored desktop `clientId`, one workspace file, one journal, root-based acknowledgement and in-memory batch/baseline protection. Do not replace those with global SQL rows and declare multi-client safety. Preserve independent records and acknowledgements explicitly. [Workspace][E-workspace], [journal][E-journal], [acknowledgement][E-operations], [accepted multi-client constraint][E-spec]

## 2. What the pinned T3 architecture does

### Terms in plain language

A **transaction** makes a set of database writes commit together or roll back together. An **event store** records domain facts in sequence; **event sourcing** derives application state from those facts. A **projection** is the query-friendly current view of that history. An **outbox** stores pending external work in the same transaction as the state change that requires it; a worker performs that work later. The outbox closes the gap between committing intent and remembering to schedule work. It does **not** make a provider call or Git command transactional or exactly once. [SQLite transaction model][D-transaction], [T3 command commit][T-commit], [worker][T-worker]

### Trace: `message.dispatch` through a provider turn

1. **Admission and planning.** The WebSocket handler routes through startup command admission and `ThreadMessageIntake`; thread management ensures required transcript/context state and validates enabled provider selection. `ThreadCommandExecutor` gives keyed thread serialization. The orchestrator checks an existing command receipt, plans events/effects and commits through `EventSink`. A duplicate accepted command returns its recorded sequence/events; the path checks thread identity, but its receipt schema does not contain escode's host/client/payload digest binding. [RPC handler][T-ws], [intake][T-intake], [thread management][T-management], [locks][T-locks], [receipt handling][T-dispatch], [receipt schema][T-receipts]
2. **One database transaction.** `commitThenPublish` wraps `sql.withTransaction`. `commitCommand` reserves the unique receipt, appends normalized events, applies projections and advances projection metadata, enqueues outbox effects, records the accepted receipt and cancels superseded effects. These are inside the same transaction. The application event source is `orchestration_events`; V2 wrappers use the common application repositories, even though older migration definitions contain V2-specific event/receipt tables. [Transaction wrapper][T-commit-wrapper], [command body][T-commit], [event wrapper][T-events], [application event schema][T-event-schema]
3. **Publication after commit.** A publication semaphore orders commit/publication; cancellation masking protects the post-commit handoff. Worker wakeup and subscriber publication are outside the SQL commit. Process death can still occur there: durable outbox rows and cursor-based reads are the recovery mechanisms, not a transactional WebSocket acknowledgement. `accepted` means accepted into orchestration, not necessarily accepted by the external provider. [Publication][T-commit-wrapper], [commit result][T-commit]
4. **Claim and execute.** An `UPDATE ... RETURNING` atomically claims an eligible outbox row, changes it to running, increments attempts and records worker ownership. Claim predicates serialize relevant effects per thread. The worker then calls `ProviderTurnStartService`, outside that claim transaction. That service reads the execution projection, records a current-attempt transition, invokes `session.startTurn`, and records handoff delivery separately. [Outbox claim][T-outbox], [turn start and post-acceptance bookkeeping][T-turn-start]
5. **Result recording.** Provider events go through `ProviderEventIngestor` to guarded EventSink writes; database event/projection updates are transactional there. Separately, the outbox worker records success/failure/retry. If successful process-bound execution cannot be settled, the worker tries to terminalize it rather than requeueing it as replay-safe work. There remains a window between external success and any durable observation of that success. [Ingestor][T-ingest], [worker settlement][T-worker], [settlement-failure test][T-worker-tests]
6. **Restart.** Startup runs runtime recovery before starting the effect worker. Pending/running process-bound turn-start/steer/restart/interrupt/request-response effects are cancelled; selected replay-safe running effects are requeued. Recovery terminalizes stale execution and may enqueue `provider-runtime.continue` when the project setting `continueThreadsAfterServerUpdate` is enabled. That is deliberate T3 product behavior and must not be adopted for escode. [Startup order][T-startup], [reconciliation][T-recovery], [effect categories][T-outbox]

The worker defaults to four concurrent workers and five attempts, with persisted availability times, exponential retry delays and a 30-second liveness poll. In-process execution failures can be retried; the process-bound/replay-safe distinction is also used for post-success settlement and restart. Do not summarize this as either “all effects replay” or “nothing retries.” A copied generic worker would need an explicit escode no-resend policy. [Worker policies][T-worker]

### Where transactions stop

The reviewed V2 `EventSink.commitCommand` does **not** have a separate non-atomic projection commit. One test deliberately violates a projection constraint and asserts rollback of events, projections, receipts and effects. Others inject cancellation/failure around outbox enqueue and post-commit notification and assert consistent projections, outbox rows and publication. This is stronger evidence than assuming correctness from the presence of SQLite alone. Those are source tests, not tests executed for this report. [Projection rollback test][T-foundation-atomic], [publication/cancellation tests][T-foundation-tests]

Larger workflows still span transactions. `ThreadLaunchService` first dispatches thread creation, then an initial-message command with a derived ID, then schedules workspace preparation in a scoped fiber. Worktree preparation, later metadata updates and provider execution cannot be one SQL transaction. A persisted preparing run and receipt-based retries coordinate the gaps. Also, `ProjectionStore.apply` and the raw event append API are not by themselves the whole commit protocol: correctness depends on callers using the surrounding EventSink transaction. [Launch workflow][T-launch], [event append][T-app-events], [projection store][T-projections]

T3 supplies projection verification/rebuild: a schema version and last sequence plus thread/readability checks, then transactional clear-and-replay in 500-event pages. This checks specified invariants, not arbitrary bit-for-bit equivalence of all projection values. Rebuild pages still belong to one long transaction. This is recovery/maintenance machinery; it does not reconstruct unrecorded provider effects, external files or missing events. [Projection maintenance][T-projection-maintenance]

### SQLite configuration, storage growth and runtime cost

The current database is `<stateDir>/statev2.sqlite`, where stateDir is the configured base directory's `userdata` or implicit development directory. Attachments, settings, keybindings, logs and external worktrees remain outside it. The default database setup enables WAL, foreign keys, a 5-second busy timeout, `synchronous=NORMAL`, `checkpoint_fullfsync=ON`, memory temp storage and a 32 MiB journal-size target. New databases enable incremental auto-vacuum. Migrations are compiled through ID 75; histories are checked for known V2 collisions and divergent entries, rather than pretending every unknown build is interchangeable. [Paths][T-config], [SQLite setup][T-sqlite], [migrations][T-migrations]

The custom `nodeSqliteClient` uses Node's synchronous SQLite connection for writes, an Effect semaphore and `BEGIN IMMEDIATE`; reads explicitly marked read-only may use up to four lazy reader workers, retaining one worker for a read transaction. A separate checkpoint worker performs checkpoint I/O and coordinates admission backpressure. Thresholds are 1,000 checkpoint frames and 10,000 backpressure frames; this is not a hard 32 MiB total database quota. Fallbacks return reads/checkpoints to the main connection when worker/runtime support is unavailable. Checkpoint-worker activation checks Node transaction/authorizer support and SQLite's NOOP checkpoint support. [SQLite adapter][T-sql-client]

This is a 1,280-line adapter at the pin, not a tiny dependency-free convenience wrapper. It imports Node built-ins and Effect SQL/reactivity/context primitives; its tests add 463 lines. T3 pins Effect 4.0.5, while escode pins 4.1.0 and Electron 45.1.0. Copying it entails adapting runtime APIs, worker packaging, integer handling, cancellation/transaction scope and tests. It does not require importing T3's provider SDKs, keyring, PTY, browser or server dependencies just to use SQLite. [Adapter and tests][T-sql-client], [adapter tests][T-sql-client-tests], [T3 versions][T-versions], [escode desktop dependencies][E-package], [T3 server dependencies][T-package]

T3 owns an application transcript: messages, turn items, runs, requests, provider sessions/threads/turns and context handoffs appear in events and indexed projections. Provider-native sessions remain separate; “application transcript” is not proof of every native history byte being archived. Growing message/turn-item updates create both event and projection writes; compaction understands which snapshots can be superseded. It retains replay anchors, special subagent prompt references and commanded turn items. A six-hour maintenance loop compacts superseded events, with incremental vacuum passes separately; legacy-import receipts can be removed, while this is not general bounded expiry of current command receipts. Succeeded/cancelled outbox rows are pruned after seven days in batches of 500; failed rows are retained. [Schema][T-v2-schema], [compaction][T-projection-maintenance], [maintenance scheduling][T-db-storage], [outbox retention][T-outbox]

**Inference:** those mechanisms suit T3's richer application-owned conversation/workflow model. Importing them to replace escode's small metadata stores would also import historical event compatibility, projector evolution, snapshot compaction and recovery maintenance. SQL itself does not require any of that.

## 3. Compare the three architectural options

The following is design analysis based on the observed implementations, not benchmark results.

| Criterion | Improve the file stores | SQLite current state + receipts + operation records | Broader event-sourced application |
| --- | --- | --- | --- |
| Crash recovery | Replace stale lock handling; specify generation manifests, temp recovery and multi-file handoffs. Retain existing intent reconciliation. | SQLite handles interrupted database transactions; application reconciles external effects and client obligations. | Same SQL recovery plus event replay/projection verification and workflow recovery. Replay must never mean re-execute provider work. |
| Related metadata consistency | Keep separate files and more reconciliation, or build a shared generation/commit protocol. | Put all related authoritative records in one transaction/database. Simpler acknowledgement and reservation invariants. | Events/projections/outbox/receipts must commit coherently, as T3's EventSink does. An event log alone does not guarantee this. |
| Growing histories and queries | Split receipts, add indexes or scan files; implement retention/compaction and crash-safe index updates. Whole JSON arrays grow expensive. | Indexed status/context/client queries and bounded paging; update one status without reserializing all prompt history. | Efficient projections, but event history and projector evolution also grow. Compaction can compromise audit/replay semantics if poorly specified. |
| Disk writes | Existing full-file rewrites plus syncs; an append journal reduces rewriting but adds recovery/truncation/checkpoint design. | Changed SQL pages, indexes and WAL plus checkpoints. FULL durability has sync costs; blob updates can still be expensive. | Event append plus projection updates and outbox changes; potentially more writes, offset by batching/compaction. No inherent speed win. |
| Multiple clients | Partition files/locks by identity and coordinate all shared operations externally. | Shared host arbitrates; rows keyed by client and revision allow transactional protection/acknowledgement. SQLite is not the network protocol. | Shared ordered event delivery helps views, but client-owned edits and authorization remain separate design problems. |
| Maintenance/testing | Fewer runtime dependencies, more custom persistence failure states. Human-readable JSON is convenient. | Embedded SQLite compatibility, schema evolution, transaction boundaries, backup policy and fault tests. | All SQL obligations plus versioned events, deterministic replay, projector upgrades, compaction and outbox policy. |
| Fit for this proposal | Viable short-term if no storage change is accepted; does not remove cross-file complexity cheaply. | **Best fit for recovery alone:** directly addresses the observed costs and consistency boundaries. | Reconsider for additional history/audit/workflow requirements, including the proposed action-level time travel below. |

Improving files is a real alternative. A correct version would preserve the current fsync discipline, use an OS-held single-host lock, introduce one clear generation commit point, bound/load records incrementally, retain uncertainty and specify safe compaction. Sharding receipts alone fixes neither atomic acknowledgement nor backup consistency. An append-only file plus indexes/checkpoints quickly becomes custom database work. Conversely, SQLite should not become a justification for an ORM, replicated database, generic job engine or complete rewrite of pure reconciliation helpers.

### 3.1 Discussion follow-up: action-level time travel

**Recorded 2026-10-31; potential requirement, not an accepted design.** The user raised returning to just before a specific action. The original recommendation evaluated durable recovery and connected-client catch-up, not this experience. Action-level time travel is a substantial reason to reconsider event sourcing; describing it merely as something to “defer” understates that change in scope.

**Reconstructing an earlier application state and restoring real work are separate capabilities.** A sufficiently complete, retained event history with compatible replay logic can reconstruct the recorded application state at a chosen event boundary. It cannot reconstruct facts it never captured. Returning to before an agent edited a file also requires the earlier file contents or reversible changes, a defined conversation/provider state, and an explicit boundary identifying the action. A “file changed” event alone is insufficient, and one user action may span several events and external effects.

**Observed T3 behavior supports this distinction.** Its checkpoint rollback selects a thread-start or provider-turn target, invokes provider conversation rollback, and separately restores a file checkpoint when requested. It rejects file restoration into a shared workspace, and rolled-back turns remain in its audit history. This is evidence for coordinated checkpoint restoration, not proof that every arbitrary event is a complete restore point. [Checkpoint rollback implementation][T-checkpoint-rollback]

**Design implication:** returning to before an agent turn may be served by conventional SQLite tables plus explicit checkpoints. Inspecting or branching from individual recorded tool actions, saves and workflow changes makes an event-based model more compelling, provided those boundaries and the necessary data are captured. Conventional tables with dedicated revision history can also support time travel; event sourcing offers a common historical model at the cost of retaining compatible events, replay logic and referenced content. The requirement does not automatically justify event-sourcing preferences, drafts or every other application record.

**Proposed restoration constraints:** preserve the original timeline and record a new restoration or branch. Preserve newer unsaved text, conflict baselines and other clients' or agents' work; define isolation and conflict handling before replacing files. External effects such as deployments or sent messages may be irreversible, and provider rollback/fork support must be verified. Retain uncertainty if restoration stops between effects. Neither viewing history, reconnecting nor restarting may resend prompts or resume agent work. An event log alone cannot provide an atomic rollback across SQLite, project files and providers.

Before selecting the broader architecture, specify which boundaries users can choose (turns, tool actions, explicit saves), whether they can inspect, restore or branch from them, which files and conversation state are included, and how long that history must remain available. SQLite adoption, event sourcing and ownership of complete chat history remain independent decisions. The current-state proposal below remains the recovery-focused baseline pending those answers.

## 4. Proposed ownership and minimum data model

All behavior in this section is **recommended design**, not existing implementation.

Use a fresh versioned directory such as `U/durable-state-v1/` with one `state.sqlite` plus SQLite-managed WAL/SHM. Name is illustrative. Do not put unrelated files in the old foundation directory: that implementation rejects unexpected entries. One host owns all authoritative mutation; renderer code never opens the database. Keep validated host methods and pure reconciliation code, replacing persistence behind them.

Initialize identities only in a demonstrably fresh store. A missing database in an established store directory must fail closed rather than letting SQLite's create-if-missing behavior silently allocate replacement identities.

Prefer a single database worker, using packaged Node's built-in SQLite if qualification succeeds. Send typed, bounded database requests to it; keep network/provider/native work outside transactions. Worker death fails in-flight requests as unknown until the host reads durable status. The writer worker owns the complete transaction callback/operation; do not run `BEGIN`, arbitrary interleaved RPC requests, then `COMMIT` across unrelated callers. Start without T3's reader pool and checkpoint-worker framework; add either only for measured need. This is a proposal to remove synchronous disk stalls from Electron main, not a measured performance claim. Node's SQLite API is synchronous; test the actual embedded API, not merely the system Node binary. [Node SQLite API][D-node]

Logical tables/groups should follow real atomic boundaries; this is not a prescription for dozens of new repositories:

| Records | Required identity and purpose |
| --- | --- |
| Store metadata and clients | Storage schema version, stable host UUID, store-generation ID, current admission/recovery epoch; stable client UUIDs and revision counters. Connection/session epochs are separate, temporary identities. |
| Projects, contexts and chats | Stable IDs, exact approved roots, lossless dev/ino strings, ownership kind, provider type/native thread identity, draft/bound state, revisions and timestamps. A path is an attribute, not identity or authority. |
| Resource reservations | Unique reservation ID and immutable intended path/branch/base; preparing/known/uncertain facts and discovered object identity. Remain attached to the original chat after failure. |
| Command receipts | Unique `(host, authenticated principal/client, commandId)`; admission epoch, immutable target/expectations, canonical payload digest and retained required payload; admitted/dispatching/accepted/rejected/uncertain outcome and evidence. Separate large immutable payload from mutable status if it avoids rewriting payload pages. |
| File operations and client obligations | Operation ID, owner, context/source/destination identities, intended bytes/baselines/staging reference, observed outcome, affected clients, per-client applied revision and acknowledgement. |
| Client recovery and view memory | `(hostId, clientId, contextId, file identity/path)` plus independently versioned unsaved text and loaded baseline. Composer keyed by `(hostId, clientId, chatId)`; pending command association stored durably with it. Small view memory can remain a bounded versioned JSON value if no relational query requires columns. |

Validate schemas on both write and read. SQL constraints protect uniqueness, referential links and supported statuses; application checks still enforce root authority, context revisions, payload limits and permitted transitions. Use prepared bindings. Do not silently round filesystem identities through JavaScript `number`; retaining decimal strings matches the existing foundation intent.

**Ownership separation matters more than physical location.** The host may durably store a client's recovery text without letting another client overwrite it or acknowledge its obligations. Shared chat/provider state belongs to the host; unsent composer and file buffers belong to the originating client. Credentials remain provider/OS-owned. For a later disconnected remote client, its local unsent keystrokes necessarily need client-local persistence too; the current single-desktop proposal must not claim a cross-device atomic transaction or offline guarantee.

Keep the spool outside the database initially, but bind its indexes to host/store generation, chat, provider thread and body revision. Publish a durable body reference only after its chunk/index is durable. Add reachable-chunk collection only after proving provider reconstruction or explicit disposal; retain non-reconstructible live output within its quota. A database backup may omit reconstructible cached history, but it must label missing spool coverage and must not attach a foreign generation's chunks.

Retain project files and Git outside the database. SQLite recovery must never restore old file bytes, stage changes, remove resource leftovers or recreate missing contexts automatically. Keep Save explicit, preserve loaded conflict baselines and unsaved text, and preserve no-follow/native descriptor checks.

## 5. Explicit intent, effect, result and acknowledgement boundaries

### Send, scoped reply, Stop and resource preparation

1. **Persist the client's submission identity.** Before admitting a new Send, durably associate the exact command ID, payload and composer revision with that client/chat. The local host can commit that association with admission in one SQL transaction. Only clear composer text if its current revision matches the submitted revision. Later edits always survive.
2. **Admit atomically.** Reauthenticate, check host/client ownership, current epoch, exact context/provider expectations and capacity. In one short transaction, read current rows/revisions, insert the receipt and any required resource reservation/preparation intent. An existing ID returns status; any changed immutable payload/target/expectation conflicts. Return admission separately from provider acceptance.
3. **Record dispatch intent before the relevant effect.** Commit a transition claiming the one current attempt. Preparation may have several explicit boundaries: reserve path, allocate resource, record object identity, create/bind provider thread, start turn. Never hold a database transaction during mkdir, Git, provider startup or `turn/start`. Revalidate exact context at the handoff. A crash between reservation and allocation retains the reservation; it cannot allocate a substitute path.
4. **Execute once in the admitted host lifetime.** Client connection cancellation does not own that work. Losing a result does not create a second attempt. Do not run a generic startup worker over persisted Send/reply/continuation intents. After restart, uncompleted intents become pending reconciliation/uncertain, including apparently undispatched admissions under the accepted conservative policy.
5. **Record known result atomically.** Update receipt, known provider identity/resource facts and client pending-submission status together where they are application records. Only a confirmed rejection before effect may be labelled rejected. A transport error, process exit, timeout or persistence failure after a possible effect is uncertain. Receipt `accepted` should retain escode's meaning of known external acceptance, distinct from the earlier admission acknowledgement.
6. **Acknowledge durable client reconciliation.** Client records the result against the submitted composer revision before releasing its pending identity. The host retains terminal receipt evidence according to retention policy. A lost response causes a status/history read; neither reconnect nor restart resends. Explicit Resolve releases only the client pending association after review, not the receipt/effect evidence. A later explicit Send is a new user action and may repeat effects if the earlier result is unresolved; disclose that locally.

There is necessarily an ambiguous interval between provider acceptance and durable result recording. A provider idempotency token can improve this only if the provider explicitly supports durable, scoped semantics; no such guarantee is assumed here. Matching prompt text in history is useful evidence, not sufficient proof when equal prompts can occur more than once. Unknown provider-thread creation also cannot justify allocating a replacement silently.

Stop remains exact-target cancellation of the captured turn/preparation, usable without a working directory. Reserve control admission/queue/storage headroom separately from Send/body/history traffic. A physically full or failed disk can exhaust even that reserve: the product must specify whether an explicit exact-target emergency Stop is allowed with a visible non-durable outcome. Recommended fallback is a narrowly scoped live Stop/host shutdown capability, never unjournalled Send or approval. This durability exception requires an explicit decision; a fixed quota is not a guarantee of free physical disk.

### Explicit Save, move/copy/Trash and dirty-client acknowledgements

1. **Intent transaction:** validate context/source/destination and the client's expected baseline; persist the operation plus protected recovery versions/affected-client obligations and staging references before mutation. Unknown or disconnected known-dirty clients continue blocking destructive operations unless explicitly resolved.
2. **Filesystem effect:** keep the native identity checks, staging, conflict hash checks and scoped operations. Record the real outcome; do not report an unsuccessful database result as proof the file was unchanged. Never convert unsupported Trash into permanent deletion.
3. **Result transaction:** store observed outcome plus new baseline/path mappings for recovery records together. For Save, retain newer unsaved text and advance the saving client's matching loaded baseline. Other clients retain their original loaded baselines and receive invalidation/conflict information; another client's Save must not silently remove their conflict check. For move, remap dirty descendants and view references without changing their loaded baselines; for copy, retain source text and independent destination drafts; for Trash, retire only work explicitly covered by the successful item and its confirmed choices.
4. **Client acknowledgement transaction:** match `(clientId, operationId, appliedRecoveryRevision)`; retire only that client's obligation. Reject uncertain acknowledgements. Stale snapshots must carry an expected revision so they cannot overwrite reconciled facts; do not infer acknowledgement merely from a missing draft or a root-only request. Lost acknowledgement is harmless repetition.
5. **Restart:** reconcile recorded intent with exact current paths/object identities/content, as current code does. If external evidence cannot establish the outcome, retain drafts/staging and block conflicting writes. Never replay a mutation just because the result row is absent.

This collapses the current journal → workspace → journal-clear *metadata* sequence into fewer atomic changes. It cannot collapse the actual rename/Trash/provider effect into SQL. Preserve existing external-writer race limits: the new database does not make Save or Git worktree removal transactional against unrelated programs.

## 6. Proposed durability contract

### Why T3's WAL setting is not the default to copy

SQLite documents that WAL with `synchronous=NORMAL` preserves consistency but can lose committed transactions after OS crash/power loss; application crash is a different case. WAL with `FULL` syncs each commit; `EXTRA` adds no WAL benefit. `checkpoint_fullfsync` only strengthens checkpoint syncs. `fullfsync=ON` requests the supported macOS full-flush method for all syncs. [SQLite synchronous and fullfsync pragmas][D-pragma]

**Recommendation:** use WAL + `synchronous=FULL`, foreign keys enabled, bounded busy handling and macOS `fullfsync=ON` for the authoritative database. Read back effective settings on every relevant connection and fail qualification if the required mode is unsupported or silently ignored. Keep commits off Electron main and coalesce ordinary recovery snapshots, but never batch an effect ahead of its durable intent. Test latency instead of weakening acknowledgement semantics speculatively. T3's `NORMAL` deliberately exchanges stronger power-loss durability for fewer main-thread commit flushes; that trade-off is poorly matched to an escode receipt that must precede a potentially irreversible provider effect. [T3 setup][T-sqlite]

Apple documents that ordinary `fsync` may leave data in drive caches and that `F_FULLFSYNC` requests flushing those buffers. Neither a successful pragma query nor an API return independently proves controller/firmware/filesystem behavior. SQLite also explicitly depends on trustworthy storage and locking. The contract therefore promises the selected software durability protocol on qualified local storage, not survival of arbitrary hardware failure or dishonest flush implementations. [Apple fsync documentation][D-apple], [SQLite atomic-commit assumptions][D-atomic], [corruption causes][D-corruption]

| Failure | Proposed observable guarantee | Limitation and response |
| --- | --- | --- |
| Renderer/client crash | Last host-acknowledged recovery/composer revision survives; host-owned work continues; pending command status can be recovered by stable client identity. | Unpersisted keystrokes and client-only offline edits remain best effort. New connection is not a new client. |
| Host application crash / worker crash | Completed database commits recover consistently; uncommitted metadata transaction is absent. Stable identities and committed drafts remain. Outstanding effects are reconciled or uncertain, never automatically restarted. | External operation may have occurred without a result. Worker crash after commit but before reply means status read, not repeat. Single-host authority must be reacquired before endpoints open. |
| OS crash | Same metadata contract for acknowledged FULL-mode commits on qualified storage; unsent/draft revisions and receipts recover together. | Current JSON/native paths have not proved this end to end. Filesystem/provider facts must be revalidated, not inferred solely from metadata. |
| Power loss | The configured sync/full-flush protocol is required before a durability acknowledgement; preserve complete committed metadata under its storage assumptions. | Hardware may violate assumptions; external files and provider state are independent. Do not promise absolute hardware durability or that the latest keypress survives. |
| Full disk / quota / I/O error before intent | Reject admission before external execution; preserve existing data and available text. Do not prune uncertainty to make room. | Distinguish application quota from real filesystem exhaustion. Roll back/check transaction state before reusing the connection. |
| Full disk / I/O error after external execution | Preserve previous dispatch intent; show result persistence pending/uncertain; stop further dependent mutations and retain recovery text. | It may be impossible to write the uncertainty marker. The pre-existing intent is the evidence; never require a successful error write to avoid replay. |
| Corrupt or wrong/newer store | Fail closed for mutations; retain originals and offer inspected recovery/backup/export paths. Never initialize over a present unreadable identity store. | Integrity checks cannot prove semantic correctness or recover missing external effects. Any salvage happens on a copy and requires identity/authority reconciliation. |

SQLite error handling needs explicit transaction cleanup: `SQLITE_FULL`, `SQLITE_IOERR`, interruption and memory errors can roll back a statement or the whole transaction depending on circumstances. A failed SQL call does not by itself establish a clean reusable transaction or a known external outcome. [SQLite transaction errors][D-transaction], [result codes][D-errors]

For project-file power-loss durability, a separate native change/qualification is required: fsync staged contents, publish through the checked native operation, sync all required parent directories, and assess macOS full-flush behavior. Cross-directory moves need both relevant directories considered; Git and native Trash need their own supported guarantees. Until qualified, promise the current practical application-crash/conflict behavior for project files and keep the stronger database guarantee explicitly separate.

## 7. Retention, admission epochs and backup/restore safety

### Retention must not re-enable old work

Recommended policy:

- Preserve nonterminal/uncertain receipts, operation facts, reservations, unresolved per-client obligations and non-reconstructible drafts. Running out of budget rejects new work; it does not erase them.
- Bound terminal receipt payloads separately from small deduplication facts. Decide a terminal retention period only after measuring actual usage and recovery needs; T3's seven-day outbox rule is not an escode receipt policy.
- Atomically rotate an admission epoch **before or with** pruning terminal receipts that otherwise could be mistaken for new commands. Reject unknown commands from retired epochs. Duplicate retained IDs still return their receipt after reauthorization; changing epoch/payload does not turn the same ID into new work.
- Generate and durably publish a fresh unpredictable admission/recovery epoch on every host restart and restore before mutation endpoints are exposed. Keep stable host/client/context IDs; do not confuse them with connection, provider-session, admission or spool-generation identities.
- If old receipt detail has expired, return “expired/unavailable; inspect history”, never “not previously executed”. Client code must not replace a retained pending command with a new ID or new epoch automatically.
- Spool collection traverses durable referenced indexes and only reclaims orphaned/reconstructible data. Receipt expiry, navigation-cache eviction and transcript-cache eviction are different policies.

Maintain explicit bounds for database growth, row payloads, worker queue bytes, in-flight writes, spool disk and WAL/checkpoint progress. SQLite WAL permits concurrent readers and a writer, but long readers can delay checkpoints and grow WAL; it does not provide many concurrent writers or network filesystem sharing. Keep database files on a local supported filesystem and serve multiple clients through the host. [WAL behavior][D-wal]

Record the bundled `sqlite_version()` and source/build information. Current SQLite documentation reports a WAL-reset corruption bug fixed in 3.51.3, with some backports; this matters when adding separate writer/checkpoint connections. Do not infer the fix from Electron's version string or T3's feature check for NOOP checkpoint support. Verify the actual bundled fix or supported backport. [SQLite release note][D-sqlite-release]

The independent runtime probe in section 9.1 reported SQLite **3.53.4**, newer than that fix. It establishes the installed build's reported version, not worker or durability qualification.

### Backup and restore

Use SQLite's online backup API, or a supported consistent export, to create the database snapshot; do not copy just a live `.sqlite` file while ignoring its WAL. A completed backup is a consistent database snapshot, not a snapshot of external project files or provider history. [SQLite backup API][D-backup], [WAL persistence][D-wal]

Recommended backup manifest records host/store generation, schema version, backup time, stable client/context identities, pending operations and spool coverage. For essential external spool objects, pin referenced immutable chunks while taking the database snapshot, copy them, verify hashes, then atomically publish the backup manifest. Do not call a backup complete if required unresolved evidence is missing. Prefer leaving the previous valid backup intact until publication finishes.

Restore is an explicit, offline maintenance operation: stop the host/provider processes, keep original database/WAL/spool as evidence, validate a copy, restore as a new recovery generation, rotate admission epochs and credentials as required, then revalidate roots and provider bindings. Initially disallow effect execution while reconciling outstanding or post-backup work. A stale backup may contain no trace of an effect that occurred later; absent receipts cannot establish that nothing happened. Never rerun prepared Send, reply, Git allocation or filesystem operations from the backup. A database copied onto a second machine must not silently impersonate the original live host; explicit identity verification/rebinding is required.

Do not delete or rename hot WAL/journal files to “repair” a live database. SQLite's documented corruption scenarios include mismatched database/journal copies, concurrent restore and broken locking. Salvage tools and `integrity_check` are diagnostics, not authority to discard drafts or revive old commands. [Corruption guidance][D-corruption]

The accepted prerelease policy excludes legacy import. Accordingly, the minimum implementation uses a separate fresh store, leaves old stores/resources untouched and does not silently switch back after any new-store external effect. Whether to preserve existing fresh-format chats/recovery by an explicit one-time import is a **new user decision**; this report does not reinterpret the no-legacy-import amendment as permission to delete current work. [Prerelease amendment][E-spec]

## 8. Minimal coherent implementation sequence for a later effort

1. **Agree the contract and record the decision.** Accept/reject SQLite independently of event sourcing and history ownership; select durability and emergency Stop behavior, retention and fresh-store/import policy. Amend/supersede ADR 0002 only after acceptance. ADR 0001's single-host authority remains valid; amend its extraction boundary only if actually copying new T3 code. Update the foundation specification's storage/runtime gates and glossary descriptions only after vocabulary or behavior is accepted. No accepted ADR/glossary is edited by this report.
2. **Qualify the narrow runtime seam in a disposable store.** Prove built-in SQLite under escode's Electron 45.1.0 packaged CJS host, worker bundling, restricted PATH, Node/SQLite versions, FULL/fullfsync readback, transaction rollback and worker failure. Measure event-loop delay and fsync/commit behavior on recorded hardware. Prefer Node built-in SQLite plus a small typed host adapter; if unsupported, compare one compatible maintained driver rather than importing the entire T3 server. No application-store experiment should consume real provider turns or touch user files.
3. **Introduce one authority and one fresh database generation.** Persist host/client identity and admission epoch before endpoints. Implement crash-released single-host ownership, version checks, atomic bootstrap, failure handling, backup/export and bounded writes. SQLite locking protects SQL; it does not stop two host processes both starting providers. Retain a separate crash-safe host ownership mechanism and test a second launch. Reject unsupported stores before writing.
4. **Move the complete command/context aggregate together.** Host/client identity, chat/provider associations, context revisions, reservations, receipt admission/result and pending composer associations should share the new transaction owner. Adapt `executeSend`, chat preparation, preload/client commands and status lookup together. Remove the replaced JSON/localStorage authoritative paths in that slice; do not dual-write. Exercise lost response, process kill, cap/full-disk boundaries and exact-target Stop. Provider history stays unchanged.
5. **Move file recovery, journal and acknowledgements as one coherent slice.** Replace Workspace/Journal persistence and the corresponding authenticated contracts/client revision handling together. Reuse `affected`, `moved`, `reconcileSave` and operation reconciliation. Persist per-client obligations; test late snapshots and acknowledgements. Keep native mutation checks and explicit-save semantics. Native sync improvements, if selected, get separate fault qualification.
6. **Finish boundedness and integration.** Bind spool indexes to the new generation, implement safe retention/epoch rotation and backup manifests, protect new DB/WAL/SHM/backup paths in Files operations, and delete obsolete writer code. Update callers, exports/build inputs and fixtures. Run affected tests, typecheck/lint/build/package and practical packaged recovery checks; add broader load or multiple-client tests only where required by changed behavior. Record limitations honestly.

The principal touch points are `host/{foundation-state,send,chat,chat-service,workspace,file-operation-journal,file-operations,file-operation-state,file-workflow,live-spool,main,preload}.ts`, `checkout-repository.ts` ownership persistence, native `filesystem.c` only if the external-file durability contract changes, `packages/{contracts,host,client-runtime}`, renderer workspace/chat recovery callers, bundler/worker exports and the focused fixtures/tests listed above. This list describes a later change's complete scope; it is not authorization to implement it now.

Coherent T3 reuse would be its **transaction-plus-publish discipline, SQL error/rollback handling, scoped worker lifecycle, bounded query patterns and focused failure tests**, with pinned provenance and MIT notices. If copying `nodeSqliteClient`, carry and adapt its transaction/reader/checkpoint tests as a unit; do not cherry-pick a semaphore while losing connection affinity/cancellation rules. Its complete event/outbox/restart machinery is a much larger closure that this proposal does not need. [Adapter][T-sql-client], [foundation tests][T-foundation-tests], [license][T-license]

## 10. Decisions remaining and research limits

The user needs to decide:

1. Is action-level time travel part of this effort, and at what boundaries and scope (section 3.1)? Accept SQLite for authoritative metadata independently; compare current-state tables plus checkpoints with an event-based history against that requirement, and decide complete transcript ownership separately.
2. Adopt FULL plus qualified macOS full-flush behavior for acknowledged metadata, and separately define the project-file durability promise?
3. Allow an explicit exact-target emergency Stop when durable receipt storage is unavailable, or fail it closed and rely on explicit host shutdown?
4. Keep the accepted fresh-store/no-import boundary, or authorize a narrow import of current records? Specify which drafts/associations must be preserved before cutover; leave old stores/resources untouched either way.
5. Choose terminal receipt/detail retention and practical capacity budgets after baseline measurements; decide whether consistent backup/export is required before using the new store for valuable work. This report recommends yes.

**Verified here:** repository pins and branch state; required documents; empty open-map query; source-level persistence/command/recovery paths and selected tests in both repositories; official durability/runtime documentation; 62 focused existing escode tests; installed Electron/Node/SQLite version and in-memory driver availability. **Not verified:** T3 runtime tests, a replacement implementation, real provider behavior, packaged database workers, native filesystem/Trash/Git power-loss semantics, fsync latency, physical crash/full-disk/corruption behavior, backup restore, broad multiple-client behavior or performance gains. No dependencies were added by this research and no provider turn was started.

The recommendation is therefore concrete enough for an ADR discussion, while its runtime and failure guarantees remain acceptance work for the subsequent implementation effort.
