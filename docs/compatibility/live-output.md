# Recoverable bounded live output

Delivery for [Stream live output with recoverable bounded history](https://github.com/ejjsharpe/escode/issues/69), under the [approved prerelease amendment](https://github.com/ejjsharpe/escode/issues/61#approved-scope-amendment).

Observed chats use authenticated `chatLive` RPC streams. The old `chatSnapshot` query and renderer detail polling are removed. A subscription captures a bounded snapshot, then supplies numbered batches of appended text, replaced items, removed identities and current control metadata. Snapshot capture and diff construction have no asynchronous gap; changes during the asynchronous authority/context check appear in that capture or the next. Each subscription starts from a complete snapshot under the host-start epoch. The client validates and applies the whole batch before advancing coverage. Overlap is ignored; a gap, changed epoch or malformed batch fails visibly and requires a new view subscription. No transient replay queue is retained: reopening always obtains a bounded snapshot. Ending observation interrupts the stream and drops its body window without stopping the provider.

The host persists immutable content-addressed text chunks and a versioned index bound to the exact chat and provider before exposing newly accumulated text. Chunk files and the containing directory are synced before index publication; the temporary index is synced and atomically renamed, then its directory synced. Fixed 4,096-code-unit segments reuse immutable prefixes. JSON string encoding preserves UTF-16 boundaries. Recovery validates references, hashes, sizes and original identities; it never starts work or attaches a different provider. Interrupted temporary writes are removed on the next write. Complete unindexed chunks remain charged to the quota and cannot be attached by recovery. Corrupt or missing indexed chunks produce unavailable output, retaining the saved association. This slice does not prune chunks or mutate provider history, old stores, projects or worktrees.

Initial limits, rather than measured production budgets:

- Existing provider ingress: 1 MiB per frame before concatenation/parsing; oversized/malformed frames explicitly fail the provider connection.
- Host live window: 1,000 items and 128 KiB encoded items per chat. Crossing it or a spool error stops body accumulation, retains the previous durable window, reports partial/unavailable output and keeps consuming bounded provider events and control. Provider work is never cancelled by spool failure. Reload after completion reads bounded provider-owned history.
- Spool: 64 MiB total, including retained chunks and indexes. Index read/write: 160 KiB; individual chunk reads: 24 KiB. Old revisions and orphaned chunks count toward the quota. No automatic garbage collection is claimed; exhaustion can require a later explicit retention/reconciliation feature.
- Requests: 32 outstanding payloads and 64 KiB encoded request metadata per session. Exhaustion reports unavailable details while retaining Stop.
- Each detail subscription retains one bounded prior snapshot and emits at most once per 100 ms with Effect stream backpressure. Existing admission permits sixteen requests per socket and eight sockets. Each client retains one replacement window per observed chat, guarded at 512 KiB including metadata. Summaries carry no bodies.
- Encoded streaming chunks remain charged until ACK or interruption against the existing 2 MiB connection budget. A 15-second missing ACK reports a coverage reset and interrupts the affected subscription. The underlying Effect WebSocket protocol's `end` hook is a no-op, so explicit interruption is necessary. Provider lifetime and existing control commands are independent of subscriptions; control command migration belongs to later tickets.
