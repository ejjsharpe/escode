# Checkout workspace restoration

Implements [Restore independent workspaces after restart](https://github.com/ejjsharpe/escode/issues/105) for the [checkout/search specification](https://github.com/ejjsharpe/escode/issues/93).

The existing versioned client workspace remains the owner of open checkout membership, active top-level selection, independent sidebar/chat navigation and recovery drafts. The host-owned approval records now retain native checkout directory identities. Restoration and subsequent Files/Git requests check the original canonical path and directory identity, including when Git is unavailable. Missing/replaced directories keep their tab, path, edits and loaded disk baselines; Retry cannot create resources or adopt the replacement. Explicit native opening also refuses to replace a recorded identity. Older path-only approvals require Open project again; production never derives authority from client recovery metadata.

Duplicate checkout membership is rejected before publication. Existing owner/version validation, atomic storage failure behavior and file-operation reconciliation remain authoritative; closed saved projects retain recovery without reopening their editor. No file-tab metadata, composer store or provider lifecycle is duplicated.

Verification extends the owning availability journey with two linked checkouts and another project, independent Files/Source Control/Chats selections, remembered chat text, Agents and checkout selection across repeated restarts, and a replacement directory at the original pathname. Retry leaves replacement bytes intact; returning the original directory permits saving the recovered text. The existing approval-boundary journey now checks path-only approval revalidation. The shared desktop fixture stamps explicitly seeded native choices only when seeding an unversioned test workspace, never during ordinary restart. The existing closed-project/interrupted-move recovery journeys exercise membership alongside journal outcomes. Host workspace tests cover identity retention, refusal to replace recorded approvals and duplicate membership without losing acknowledged recovery.

Detailed file order/view/position/preview restoration belongs to [Restore file workspaces and retain unavailable targets](https://github.com/ejjsharpe/escode/issues/99); interrupted operation matrices and draft capture remain with their separate owners. Recovery remains best effort, with the existing check-before-save and operation-journal limits. Native device/inode identities do not provide backups or stronger filesystem transactions; explicit Quit does not resume agent turns on restart. Manual VoiceOver and live provider turns are excluded from this qualification.

### Availability timeout diagnosis (#105 follow-up)

The unchanged approval-boundary journey (`bun run --cwd apps/desktop smoke -- tests/availability.spec.ts:75 --repeat-each=5`) reproduced two 45-second test timeouts followed by worker teardown timeouts; three repeats passed. A subsequent instrumented repeat stopped at the first Quit: `prepare` succeeded, but workspace `flush` rejected with `Error: App state is unavailable in Files.` The renderer stayed alive and correctly retained its state rather than quitting after failed persistence.

This fixture deliberately keeps application state inside the checkout. Its root directory-watch setup is rejected by the existing protection boundary. The host wrapped that throwing setup in `Effect.sync`, turning an expected denial into an RPC defect that could reject an unrelated concurrent workspace write. No approval or recovery assertion was stale. The repair catches watch acquisition failure and delivers the existing error notification without failing the shared RPC session; installed watches retain their cleanup. No authority checks, Quit preservation gates, assertions or timeouts were relaxed, and #107's separate draft fixture repair is unchanged.

The focused host-client regression holds an actual authenticated workspace write in flight, rejects watch acquisition, checks the watch error, then releases and verifies both that write and a later write on the same socket. Before the fix it failed in 883 ms because the workspace write received the watch defect; after the fix the host-client suite passed. Temporary renderer/test diagnostics were removed.
