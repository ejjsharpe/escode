## Behavior and boundary

Dragging a tree row captures the originating checkout and selected paths immediately. Unselected rows become the source selection; dragging a member of a multiple selection retains that selection. Host capture prunes descendants, records native source and checkout identities, and returns an opaque single-use reference. The browser drag payload carries a separate local session identifier, never filesystem authority. There is one bounded host drag reference, independent of the Files clipboard. Forged, external and cross-checkout drops cannot turn payload paths into authorized sources.

Rows highlight the actual destination folder (a file targets its parent); empty tree space targets the checkout root. A stable three-line status area distinguishes Copy from Move before drop, with native dropEffect feedback. Option at drop determines copying. Hovering a collapsed folder for 650 ms expands it through the existing lazy listing path. Target resolution uses retained or lazy-loaded parent listings. Cancellation, navigation, disabling and unmount clear the drag/timer; generation checks suppress stale pending drop continuations. Inline fields remain non-draggable and tree keyboard commands remain scoped away from text fields and Monaco.

Drag moves ask a host confirmation listing the captured, pruned sources, destination folder and checkout, defaulting to Cancel. Cancel performs no filesystem mutation. Explicit paste has no additional drag prompt. After consent, the same transfer loop handles collisions, dirty destinations, native no-follow/protected boundaries, per-item results and async copying. Live project ownership, checkout, destination-parent and source identities are revalidated before execution, including after confirmation/collision waits. A drag reference is consumed on submission and cannot retry a later drop. Moves and copies use the existing FileOperations journal, batch-fact protection and renderer reconciliation; no native mutation path, dependency or persistence schema was added.

The previous copy-stage identity/publication/uncertainty handling remains untouched. Copies still reconcile already-open clean destinations in place and preserve/report independently dirty destinations. Moves retain available dirty text, view state, destination Monaco identity/language and actual Save paths. Earlier move undo history resets with disclosure; subsequent text undo remains supported. Navigation stays available while transfers run; focus restoration checks the originating visible tree. Existing accessible progress, errors and actual per-item outcomes remain in use.

## R2 correction after independent full Ponytail R1 review

R1 identified a deterministic validation-order defect in the shared clean-file Replace flow: after collision consent, destination Trash ran before revalidating the captured source. Replacing the source inode while the dialog waited could Trash the original destination, then reject the transfer. This user-wait gap was a bug, not the accepted narrow check-to-syscall race.

The shared per-item `validateTransfer` callback now checks live origin/session/Project ownership, checkout/root and destination-parent identities, quitting/closure state, source/destination protection, and captured source identity/type. The initial check and both mutation callbacks reuse it. Replacement Trash invokes it after journal persistence immediately before the native destructive mutation, and also rechecks the destination identity approved in the collision prompt. Transfer execution invokes the same callback. No separate drag mutation route or broader transaction guarantee is introduced. Later native failures after a valid replacement can still report the actual partial Trash/transfer outcomes.

The destructive Replace audit found one clean-destination Trash path, shared by drag copy/move and clipboard copy/cut paste. Duplicate and same-folder copy choose free names; folder/type conflicts do not replace trees. The other host Trash call is the explicit deletion flow, and the native file-operation move/rename path rejects occupied destinations. Ordinary Save uses its separate established conflict/baseline contract. No other destructive transfer Replace path was found.

Two new real Electron/disk regressions hold the collision dialog, retain the captured source inode at another path, create a distinct replacement inode, then choose Replace through real Option-drag and tree-focused clipboard Copy/Paste. They require original destination bytes and inode at the same disk path, unchanged replacement source bytes/inode, the retained old source bytes, no native Trash/move/copy command and an honest captured-source error without success. These tests first run against the prior built app to establish the failure, then against the fix. Dialog answers are controlled; the filesystem and native command observations are real.
