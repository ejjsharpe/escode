# SQLite file recovery (#122)

Workspace recovery and the file-operation journal require the host-owned SQLite database. There is no no-database or JSON recovery path. Workspace snapshots retain available text, loaded disk baselines, file identities and client revisions. Operation facts retain required Save intent before native replacement and completed outcomes before baseline handoff. Each record replacement is transactional and stale writers are rejected. Filesystem effects remain outside SQLite; recovery reconciles current files without replaying Save. Checkout identity validation, conflict choices and the existing external-writer race limit remain unchanged.

Recovery bodies are capped at 16 MiB per record with the existing 64-request worker queue. These are admission limits, not production capacity qualification. Database/WAL/SHM and establishment-marker paths are protected from project file operations. Old workspace/journal JSON bytes are neither read, imported, written nor deleted. Project approvals remain in their existing host-owned store.

Host fixtures now use real temporary SQLite stores. Packaged fixtures seed and inspect SQLite recovery records; fault/delay probes target the worker request/response boundary instead of JSON renames. Fixture crash cleanup follows the receipts lock established by the SQLite installation. Inspection uses a read-only connection, avoiding another worker's startup reconciliation while the app is running.

The full host suite was not repeated after that clean merge. The integration branch itself is not modified. No ticket closure or PR was performed.

The checks establish bounded application-crash and workflow behavior. They do not establish physical full-disk or power-loss survival, latency, production capacity, exhaustive multi-client/revocation qualification, or human/native accessibility acceptance. WAL NORMAL may lose recent transactions after OS failure or power loss. Broader packaged regression coverage remains outside these focused checks.
